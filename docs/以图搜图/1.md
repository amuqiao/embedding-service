生产级项目（看架构怎么做）

Immich（immich-app/immich）：自托管相册，智能搜索和人脸聚类都是 CLIP/ArcFace 向量存在 Postgres 里。值得注意的是它出于性能考虑从 pgvector 换到了 pgvecto.rs，后来又跟进到 VectorChord——如果你的量级在百万张以上，它的取舍过程本身很有参考价值。代码里 embedding 服务和检索是拆开的，工程结构比较清晰。

技术选型上的几点提醒

检索质量主要取决于 embedding 模型而不是数据库。CLIP 是基线，SigLIP / EVA-CLIP 在以图搜图上通常更好；纯"找相似图/找重复图"的场景，DINOv2 往往比 CLIP 更合适（CLIP 偏语义，DINOv2 偏视觉相似）。
索引用 HNSW，距离一般选 cosine（记得先归一化）。
图片量大时看一下 halfvec（fp16，省一半空间）和二值量化 + 重排的做法，pgvector 0.7 之后支持。

pgvector 支持情况

server/src/enum.ts 里现在只剩两个向量扩展：vchord（VectorChord）和 vector（pgvector）。环境变量 DB_VECTOR_EXTENSION 接受 vectorchord | pgvector，不设置则自动探测，优先级 VectorChord > pgvector。

版本约束（constants.ts）：Postgres >=14，pgvector >=0.5 <1。

索引建法在 utils/database.ts 的 vectorIndexQuery()，两条分支写得很清楚：

sql
-- pgvector 分支
CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)
WITH (ef_construction = 300, m = 16)

-- VectorChord 分支
CREATE INDEX ... USING vchordrq (embedding vector_cosine_ops) WITH (options = $$
  residual_quantization = false
  [build.internal]
  lists = [N]
  spherical_centroids = true
$$)

顺带一提：VectorChord 本身是构建在 pgvector 的 vector 类型之上的，文档明确说迁移到 vchord 之后不要卸载 pgvector。所以不存在"Immich 抛弃了 pgvector"这回事，更准确的说法是默认走 VectorChord，pgvector 作为受支持的备选。

以图搜图确实有

POST /search/smart 接受 query（文本）或 queryAssetId（图搜图）二选一。走 queryAssetId 时直接取该资产已存的 embedding，不重新推理。检索 SQL 核心就一行（search.repository.ts）：

sql
ORDER BY smart_search.embedding <=> $embedding

相关的三套向量检索：

smart_search 表 → 文搜图 / 图搜图（clip_index）
face_search 表 → 人脸聚类与检索，带 maxDistance 阈值（face_index）
duplicate.repository.ts → 重复照片检测，同样是 <=> + 距离阈值

模型侧是独立的 Python ML 服务（ONNX），可选模型包括 SigLIP、SigLIP2、nllb-clip 系列——后者是多语言的，如果你要做中文文搜图值得注意。

是否值得借鉴

值得看的：

多扩展抽象。同一份业务代码通过 vectorIndexQuery() + getVectorExtension() 支持两种扩展，启动时检查版本范围、自动 CREATE EXTENSION、版本升级时自动 ALTER EXTENSION 并重建索引（database.service.ts）。你如果担心后续要换扩展，这个分层方式可以直接抄。
索引重建策略。reindexVectorsIfNeeded() 会随数据量调整 lists 参数，VECTORCHORD_LIST_SLACK_FACTOR = 1.2 留了缓冲避免频繁重建。
CJK 处理。tokenizeForSearch() 对中日韩字符做 bigram 切分，用在新加的 OCR 搜索上——做中文项目大概率用得上。
ML 服务与主服务解耦，embedding 生成走异步 job 队列。

要注意的：

技术栈是 NestJS + Kysely + TypeScript，代码量很大，它是个完整相册产品而不是参考实现，直接照搬成本高。看 search.repository.ts、utils/database.ts、database.service.ts 这三个文件基本就够了。
只支持库内以图搜图（拿已有资产的 embedding），没有"上传一张任意图片直接检索"的接口，要这个功能得自己加一步实时推理。
AGPL-3.0，如果你做的是对外提供服务的商业产品，注意条款。

方案二看着更好，但有个我一直强调的风险：它是"以视觉为中心"的模型。这意味着文本塔是为了对齐图像而训练的，拿它做纯文本对文本的匹配（你的描述搜索正是这个），效果不一定比 BGE-M3 这类专门的文本模型好。这必须实测。
