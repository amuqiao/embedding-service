# 素材平台向量检索服务 — 技术方案 v2（通义多模态方案）

> 相对 v1 的变更：模型方案由「DINOv2 + 独立文本模型」改为统一使用通义多模态向量 API。
> 这是一次**收益明确的简化**，同时解锁了原方案不具备的文搜图能力。

---

## 一、变更摘要

| | v1 方案 | v2 方案（本文档） |
|---|---|---|
| 图像编码 | DINOv2（本地部署） | 通义多模态 API |
| 文本编码 | 多语言文本模型（本地部署） | 同一个通义多模态 API |
| 向量空间 | 两个独立空间，互不相通 | **同一个空间** |
| 向量维度 | 图 768 / 文 1024，不一致 | **统一 768** |
| 文搜图 | 不支持 | **支持** |
| 图文融合向量 | 不支持 | 支持（可选） |
| 模型部署 | 需要 GPU、需要维护推理服务 | 无需部署 |
| 视频素材 | 需另选模型 | 同一模型即可支持 |

**未变的部分**：服务边界、职责划分、候选集由后端提供、只返 ID + 分数、断点续跑的导入机制。架构主干不变，只换了编码层的实现——这正是当初做编码层抽象的目的。

---

## 二、模型与参数

**选型：`tongyi-embedding-vision-flash-2026-03-06`（华北 2 北京）**

| 项 | 值 | 对本项目的影响 |
|---|---|---|
| 向量维度 | 768（默认）/ 512 / 256 / 128 / 64 | **取 768**，flash 版本的上限 |
| 文本长度上限 | 1,024 Token | AI 描述 60–120 字约 100–200 token，用户查询 200 字约 300 token，**均在范围内** |
| 图片大小 | 建议 ≤5 MB，最大 10 MB | **素材原图可能超限，需预处理**（见第六章） |
| 图片格式 | JPEG / PNG / WEBP / BMP / TIFF / ICO / DIB / ICNS / SGI，支持 URL 或 Base64 | OSS 公网 URL 可直接传 |
| 视频 | MP4 / MOV / WEBM 等，≤50 MB，H.264/H.265 | 为将来的视频素材预留 |
| 单次请求元素数 | ≤20（图片≤64、视频≤8，但总元素受 20 限制） | **可批量，一次最多 20 条** |
| 语言 | 中、英、日、韩等 30+ 种 | 中英双向检索无需额外处理 |
| 单价 | 0.00015 元/千 Token | 见成本估算 |
| RPM / TPM | 1,200 / 9,600,000 | worker 需自带限流 |
| 免费额度 | 无，且不支持开启 | 需先确认账号余额 |

**成本估算**：按每张图约 1,000 token 计，10 万张素材全量建索引约 **15 元**。即使百万级素材也仅百元量级。**成本不构成任何决策因素**，可以放开手测试和重建。

### 为什么选 flash 而非 plus

plus 版维度更高（1152）、文本上限相同（1024 Token）、单价 0.0005 元（约 3.3 倍）。但对素材检索这类任务，768 维已足够，且 pgvector 存储和计算开销更低。

建议先用 flash 跑通并评测，若效果不达标再切 plus——编码层只需改一个模型名和维度常量。

## 三、核心变化：一个向量空间

这是 v2 与 v1 最本质的区别。

v1 中图像向量和文本向量分属两个空间，**绝对不能互相比较**。v2 中两者由同一个多模态模型产出，**共处同一空间，可以自由组合检索**。

由此产生一个「查询模态 × 目标模态」的矩阵：

| 查询内容 | 检索目标 | 得到的功能 | 产品对应 |
|---|---|---|---|
| 图像 | 图像向量 | 图搜图 | 4.6.b |
| 文本 | 文本向量 | 描述搜索 | 4.6.c |
| **文本** | **图像向量** | **文搜图（新）** | 原方案不具备 |
| 文本 | 图像 + 文本向量 | 融合召回（新） | 见下 |
| 图像 | 文本向量 | 以图搜描述 | 暂无场景 |

### 融合召回：一个值得做的产品增强

用户输入一段描述时，可以**同时**检索两类向量再合并排序：

- 命中**文本向量** → 匹配到 AI 描述里的业务属性（「正式程度：半正式」「适合白人、拉丁裔」「场合：宴会」）
- 命中**图像向量** → 匹配到描述里没写出来的视觉特征

这两类信息互补：业务属性只存在于文字中，模型看图提取不到；而视觉细节（发丝光泽、层次感）文字描述往往写不全。合并召回能同时覆盖。

实现上就是查两次取并集，按分数归一后合并。**建议作为实验项验证收益，不进第一版。**

## 四、数据模型

### 向量表

三张表结构完全一致，**共享同一个向量空间**，分表只是为了索引清晰和查询意图明确：

```sql
CREATE EXTENSION IF NOT EXISTS vector;

-- 素材图像的向量
CREATE TABLE image_embedding (
  entity_id   text PRIMARY KEY,
  embedding   vector(768) NOT NULL,
  model_name  text NOT NULL,
  updated_at  timestamptz NOT NULL DEFAULT now()
);

-- 素材 AI 描述的向量
CREATE TABLE text_embedding (
  entity_id   text PRIMARY KEY,
  embedding   vector(768) NOT NULL,
  model_name  text NOT NULL,
  updated_at  timestamptz NOT NULL DEFAULT now()
);

-- 图 + 描述的融合向量（可选，第二阶段验证）
CREATE TABLE fused_embedding (
  entity_id   text PRIMARY KEY,
  embedding   vector(768) NOT NULL,
  model_name  text NOT NULL,
  updated_at  timestamptz NOT NULL DEFAULT now()
);
```

**关键概念：表决定「搜什么」，查询向量决定「用什么搜」。** 因为空间统一，任何查询向量都可以检索任何一张表。文搜图就是「用文本编码出的向量去查 image_embedding」，不需要任何特殊结构。

其余设计与 v1 一致：

- `entity_id` 是后端提供的不透明字符串，本服务不解析
- **不存分类、标签等任何业务字段**，过滤由后端通过候选集完成
- `model_name` 存在行上，支持换模型时的灰度过渡
- 建议 `ALTER COLUMN embedding SET STORAGE EXTERNAL` 关闭 TOAST 压缩

### 索引

```sql
CREATE INDEX ON image_embedding USING hnsw (embedding vector_cosine_ops)
  WITH (ef_construction = 300, m = 16);
-- text_embedding、fused_embedding 同理
```

若所有检索都携带候选集（几百到几千 ID），暴力精确计算仅需几毫秒且**比 HNSW 更准**，索引可暂缓。

### 任务表

```sql
CREATE TABLE index_task (
  entity_id    text NOT NULL,
  image_url    text,                   -- 保留，用于自助重建
  text_content text,                   -- 保留，用于自助重建
  status       text NOT NULL DEFAULT 'pending',
  retry_count  int  NOT NULL DEFAULT 0,
  error        text,
  updated_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (entity_id)
);
CREATE INDEX ON index_task (status, updated_at);
```

保留 `image_url` 和 `text_content` 使本服务具备**自行全量重建**的能力，换模型或换维度时无需惊动后端。

## 五、对外接口

统一前缀 `/v1`。相对 v1 的主要变化是 search 接口引入了 `target` 参数以支持跨模态检索。

### 1. `PUT /v1/embeddings/{entity_id}`

**职责**：为单个素材建立或更新向量。幂等。

```jsonc
// 请求
{
  "image_url": "https://oss.../a1.jpg",       // 可选
  "text": "铜红色中长卷发，侧分设计...",         // 可选
  "vectors": ["image", "text", "fused"]        // 生成哪几种，默认 ["image","text"]
}

// 响应 200
{
  "entity_id": "a1",
  "vectors": ["image", "text"],
  "model": "tongyi-embedding-vision-flash-2026-03-06",
  "dimension": 768
}
```

**实现要点**：三种向量可以**在一次 API 调用中全部拿到**——把三个 content 对象放进同一个 input 数组：

```python
input_data = [
    {"image": image_url},                # → 图像独立向量
    {"text": text},                      # → 文本独立向量
    {"text": text, "image": image_url},  # → 融合向量
]
```

同一对象内的多模态内容会融合为一个向量，单模态对象各自产出独立向量。这样一个素材只消耗一次请求配额。（此行为需在联调时实测确认，见第八章。）

**后端触发时机**：
- 新素材入库
- 素材图片被替换
- AI 描述被重新生成（产品文档：「每次重新上传资源时将重新生成描述」）
- 音频素材只传 `text`，`vectors` 传 `["text"]`

### 2. `POST /v1/embeddings:batch`

**职责**：批量建索引，用于 Dropbox 存量迁移与全量重建。

必须支持**部分成功**：

```jsonc
{ "results": [
  { "entity_id": "a1", "status": "done" },
  { "entity_id": "a2", "status": "failed", "error": "IMAGE_TOO_LARGE" }
]}
```

内部按 20 条一批调用上游 API，并按 RPM 1200 限流。

### 3. `DELETE /v1/embeddings/{entity_id}`

**职责**：删除该素材的全部向量。删除不存在的 ID 也返回 204（幂等，便于重试）。

支持 `?vectors=image` 只删指定类型。

### 4. `POST /v1/embeddings:batchDelete`

**职责**：批量删除。

### 5. `POST /v1/search` — 核心接口

**职责**：接收查询内容与候选范围，返回排序后的 ID 列表。

```jsonc
// 请求
{
  "target": "image",                  // 搜哪类向量: image | text | fused
  "query": {                          // 查询内容，三选一
    "text": "一头蓬松的棕色卷发",
    "image_url": "https://...",
    "image_base64": "...",
    "entity_id": "a1"                 // 用库内已有向量，零推理零下载
  },
  "candidate_ids": ["a1", "a2"],      // 可选，不传则全库检索
  "exclude_ids": ["a1"],              // 可选，图搜图时排除查询图自身
  "top_k": 50,
  "min_score": 0.0                    // 可选
}

// 响应
{
  "results": [ { "entity_id": "b7", "score": 0.83 } ],
  "model": "tongyi-embedding-vision-flash-2026-03-06"
}
```

`target` 与 `query` 自由组合，覆盖全部检索场景：

| target | query | 场景 |
|---|---|---|
| `image` | `image_url` | 图搜图（4.6.b） |
| `text` | `text` | 描述搜索（4.6.c） |
| `image` | `text` | 文搜图（新增能力） |
| `image` | `entity_id` | 库内素材找相似，无需下载和推理 |

**响应只含 ID 和分数**，不含任何业务字段。后端拿 ID 回自己库中查详情并做权限过滤。

**分数语义必须写入接口文档并永不变更**：`score = 1 - cosine_distance`，范围 0–1，**越大越相似**。这是最容易产生对接事故的地方。

### 6–8. 对账与自检

- `GET /v1/embeddings/{entity_id}` — 查单条状态（存在哪些向量、模型、更新时间）
- `POST /v1/embeddings:exists` — 传一批 ID，返回持有/缺失，供后端定期对账
- `GET /v1/embeddings/ids?target=&cursor=&limit=` — 游标分页拉全量 ID，用于反向对账清理幽灵向量
- `GET /v1/meta` — 返回模型名、维度、各表记录数、索引状态

### 不属于本服务

ID / 名称搜索、搜索历史、输入框交互、分类与标签筛选、结果详情拼装与权限过滤——均由前后端负责，不经过本服务。

## 六、工程要点

### 图片大小是首要工程问题

上游限制单张建议 ≤5 MB、最大 10 MB。素材平台的原图很可能超限，且模型内部本来就会缩放，传原图纯属浪费带宽和 token。

处理优先级：

1. **首选：让后端提供预览图 URL**。只要短边不低于 512 即可，建索引速度能快一个数量级
2. **次选：利用阿里云 OSS 的图片处理参数**，在 URL 上拼接缩放指令，服务端直接拿到小图，无需自己下载压缩
3. **兜底：本地下载后压缩再以 Base64 传输**。最慢，但对格式和尺寸完全可控

用户查询上传的图片同样要走这个预处理。

### 限流与批量

- 单次请求元素总数 ≤20，因此批量导入按 **20 条一批**
- RPM 1200 × 20 = 理论 24,000 条/分钟，10 万素材约 4–5 分钟跑完
- worker 必须自带令牌桶限流，避免打爆配额触发 429
- 需实现指数退避重试，失败写回 `index_task.error`

### 查询侧缓存

用户搜索时需实时编码查询内容，多一次外网往返。热门查询词的向量应缓存（内存 LRU 即可），key 为 `模型名 + 内容哈希 + 维度`。库内以图搜图（传 `entity_id`）直接取现成向量，无需调用上游。

### 依赖外部服务的后果

上游 API 不可用时本服务的检索会失败。需与后端约定降级策略（返空？回退关键词搜索？）。这是 v2 相对 v1 引入的新风险——v1 本地模型不会有这个问题。

## 七、待验证项（自测，不需要等任何人）

按优先级，全部在第二阶段用离线素材完成：

1. **相似度分布**。分别统计人工判定「相关」与「无关」两组样本的分数分布，观察分离点，据此反推阈值。**产品文档中的「相似度大于 90」大概率不可直接使用**——向量余弦相似度不是直觉上的百分比，无关内容也常有 0.3–0.7 的分数，直接用 0.9 很可能几乎搜不出结果。这个数字必须测出来。

2. **模板化描述是否降低区分度**。产品文档为描述制定了高度统一的句式（固定顺序、标准词表、60–120 字）。若所有「脸」的描述都同构，句式本身会占据向量的大部分能量，真正起区分作用的形容词反而被稀释，所有向量挤在一小块区域。需实测验证。若成立，建议把标准词表里的枚举维度（脸型、眉形、场合、正式程度、华丽程度、适合人群）改为后端的结构化标签用于筛选，向量只承担无法枚举的语义。

3. **查询与文档的句式不对称**。索引侧是模板化结构描述，查询侧是用户自由书写的口语（界面提示「输入一段描述，告诉我你想要的资源图片」）。两者差异很大。若效果不佳，可考虑查询侧做一次轻量 LLM 改写，或索引侧额外存一份精简描述。

4. **文搜图能否替代或补充描述搜索**。对比三条路径在同一批查询上的表现：文→文本向量、文→图像向量、以及两者合并召回。

5. **融合向量的实际收益**。对比 `fused` 与 `image` + `text` 分别检索的效果差异。

6. **flash 是否够用**。若不达标再对比 plus（1152 维，3.3 倍单价）。

7. **纯文本任务是否该换模型**。`qwen3.7-text-embedding` 在 CMTEB 上分数明显更高，且支持 `text_type`（区分 query/document）和 `instruct`（任务指令）这两个对检索很有价值的特性。代价是它与视觉模型**不同空间，会失去文搜图能力**。若描述搜索的效果差距显著，可考虑描述搜索单独用它，图像链路仍用视觉模型——编码层抽象天然支持这种混搭。

### 需要向后端 / 产品确认

| # | 事项 | 说明 |
|---|---|---|

## 九、推进顺序

### 第一阶段：搭骨架（不依赖任何确认项）

1. 建库建表（三张向量表 + 任务表）
2. 编码层：`TongyiEncoder` 实现，封装独立向量与融合向量两种调用
3. 图片预处理模块（尺寸检查、压缩、格式转换）
4. 三组核心接口：写入、删除、检索
5. `index_task` 断点续跑与限流重试

### 第二阶段：跑数据、定参数

6. 灌入现有离线素材，走完整链路
7. 完成第七章的 1–4 项验证，**产出阈值与最终模型组合的结论**
8. 与产品共同建立评测集（数十条真实查询 + 人工标注的期望结果，定义如「top 10 中至少含 3 个相关结果」的可量化标准）

### 第三阶段：对接与上线

9. 输出 OpenAPI 文档，与后端确认第八章各项
10. 联调
11. Dropbox 存量迁移（建议安排在业务低峰期一次灌完，可规避存量与增量并发的一致性问题）
12. 上线，开启增量通道与定期对账

**第一、二阶段不需要等待任何人。** 先搭起来跑一批数据，恰恰是解开那些未定项最快的路径——阈值定多少、用哪个模型组合，本就该用数据说话而非开会决定。
