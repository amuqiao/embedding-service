**结论**
不要把 [app/jobs/types/audio_stem_separation/executor.py](/Users/admin/Code/fastapi-best-ai-architecture/app/jobs/types/audio_stem_separation/executor.py:374) 直接当“模型服务”部署。它现在是 **业务 Job executor**：读 OSS 输入、校验 WAV、加载本地 ONNX、分段推理、合成 WAV、写回 OSS。组长说的“业务和模型服务分开”是对的：这个 Job 服务应该保留任务状态、OSS、回调、重试；Triton 服务只负责 GPU 推理。

**推荐架构**
```text
调用方
  |
  v
FastAPI Job 服务
  - 创建 job / 状态机 / callback
  - 下载 OSS WAV
  - 校验 sha256、44100Hz、stereo、duration
  - 切 7.8s chunk
  - 调 Triton 推理
  - overlap-add 合成
  - 写 drums/bass/other/vocals 到 OSS
  |
  v
PAI-EAS Triton 模型服务
  - 加载 4 个 htdemucs ONNX expert
  - 输入 float32 tensor: mix
  - 输出 tensor: stems
```

阿里云 PAI-EAS 的 Triton 部署方式是：把 Triton model repository 放到同地域 OSS，目录里每个模型有数字版本目录和 `config.pbtxt`，然后在 EAS 里用 Triton 部署指向这个 OSS 路径；副本数和资源规格在 EAS 部署参数里选。([help.aliyun.com](https://help.aliyun.com/zh/pai/deploy-a-triton-server-model-service))

**`cms-video-analyzer-triton-master` 有没有参考价值**

但它的业务是 speaker embedding，不是 htdemucs 音源分离；不要照搬它的模型输入输出和预处理。

**哪些放 Job 服务，哪些放 Triton**
```text
Job 服务处理：
- OSS URL Ref 校验、下载、sha256
- WAV 解码/编码，soundfile/ffmpeg 相关逻辑
- 采样率、双声道、时长限制
- 长音频切 chunk
- 4 个 expert 输出取 target row
- overlap-add 拼回完整 stems
- 结果上传 OSS
- job 状态、重试、callback、错误码

Triton 处理：
- ONNX 模型加载
- GPU/ONNX Runtime 推理
- 可选：非常轻量的 tensor 后处理
```

这么拆的原因是阿里云 Triton 镜像是模型服务镜像，不是你的业务运行环境。Python Backend 虽然能自定义逻辑，但阿里云文档明确提醒：Python Backend 下 `max_batch_size` 动态批处理不自动生效，需要自己在 `execute` 里处理 requests；`instance_group` 也不能替你控制 CPU/GPU，需要代码里显式搬设备。([help.aliyun.com](https://help.aliyun.com/zh/pai/deploy-a-triton-server-model-service)) 另外 Python Backend 部署还要求配置 `/dev/shm` 共享内存，并通过 `prepare.pythonRequirements` 安装 Python 依赖。([help.aliyun.com](https://help.aliyun.com/zh/pai/deploy-a-triton-server-model-service)) 所以 `soundfile`、`libsndfile`、`ffmpeg`、OSS SDK、业务 DB 这些东西尽量别塞进 Triton。

**并发怎么做**
```text
并发入口有三层：

1. Job 服务队列
   控制同时有多少 audio_stem_separation job 在跑。

2. Triton 单副本内部
   instance_group count 通常先设 1。
   这个模型显存和输出都大，盲目加 count 可能 OOM。

3. EAS 副本数
   真要并发吞吐，优先横向加副本。
```

不要一开始就指望 `dynamic_batching`。你当前模型签名看起来是固定 batch `1`，也就是 `[1,2,343980]`；如果 ONNX 第一维不是动态 batch，就不能简单把 `max_batch_size` 改成 4。`cms-video-analyzer-triton-master` 里的 `w2vbert` 能配 `max_batch_size: 4`，是它的模型和配置按可 batch 的方式设计了，见 [w2vbert/config.pbtxt](/Users/admin/Downloads/Code/cms-video-analyzer-triton-master/models/w2vbert/config.pbtxt:1)。

**部署步骤**
1. 在本地准备 4 个 ONNX：`htdemucs_ft_drums.onnx`、`bass`、`other`、`vocals`。
2. 为每个模型写 `config.pbtxt`，先用 `max_batch_size: 0`。
3. 按 Triton model repository 结构上传到同地域 OSS。
4. 在 PAI-EAS 选择 `Triton 部署`，模型配置选择 OSS 路径，选择 GPU 规格和副本数。([help.aliyun.com](https://help.aliyun.com/zh/pai/deploy-a-triton-server-model-service))
5. 默认 HTTP 是 8000；如果要 gRPC，需要切到自定义部署，把端口改成 8001 并启用 gRPC。([help.aliyun.com](https://help.aliyun.com/zh/pai/deploy-a-triton-server-model-service))
6. Job 服务用 `tritonclient` 调 EAS endpoint，并带 `Authorization` token；HTTP 调用时阿里云示例要求 endpoint 不带 `http://` scheme。([help.aliyun.com](https://help.aliyun.com/zh/pai/deploy-a-triton-server-model-service))

**主要坑**
- **别把 Job executor 整个搬进 Triton**：那会把 OSS、DB、callback、业务错误码都塞到模型服务里，边界会乱。
- **不要 silent fallback 到 CPU**：组长要模型服务，GPU 不可用就应该失败暴露，而不是悄悄变慢。
- **网络传输很大**：一个 chunk 输入约 2.75MB；如果每个 expert 都返回完整 `[1,4,2,343980]`，输出更大。后续最好让模型只返回目标 stem，或加轻量后处理减少回传。
- **Triton Python Backend 安装受限**：Python 包还能尝试 `pythonRequirements`，系统库和 ffmpeg 类依赖不一定好装。
- **版本目录必须是数字**：`1/`、`2/`，数字越大版本越新；`config.pbtxt` 要和模型目录名一致。([help.aliyun.com](https://help.aliyun.com/zh/pai/deploy-a-triton-server-model-service))
- **并发不是越大越好**：先压测单副本单实例显存、p95、吞吐，再调 Job 并发和 EAS 副本数。
- **HTTP/gRPC 地址格式不同**：阿里云文档专门提示两者 endpoint 格式不同，填错会 DNS 或 client 报错。([help.aliyun.com](https://help.aliyun.com/zh/pai/deploy-a-triton-server-model-service))

最小可落地方案：先部署 4 个纯 ONNX Triton 模型；Job 服务保留当前音频处理和拼接逻辑，只把 `self.sessions[stem].run(...)` 替换成远程 Triton infer。这样最符合“业务服务调用模型服务”，也避开 Triton 镜像里装一堆音频/业务依赖的问题。
