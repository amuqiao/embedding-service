
**继续梳理：收口后的核心对象**

建议只保留这几类概念：

```text
Platform Core
Tool
Business Package
Platform Meta API
```

不要再引入“基础能力包”。

**1. Platform Core**

平台内核是服务运行地基，不可插拔：

```text
app/core
app/api 通用 envelope / auth / error
app/jobs 平台状态机 / worker / callback / billing
app/ai 模型目录 / provider / pricing
app/object_storage 对象存储抽象
app/repositories 平台通用 repository
```

它的原则是：

```text
平台内核不 import 具体业务包
平台内核只提供注册点和运行时能力
```

**2. Tool**

工具包是内部可复用动作，不是业务能力：

```text
app/tools/
  object_storage.py
  media_audio.py
  media_image.py
  dashscope_embedding.py
```

工具特点：

```text
- 不暴露 HTTP route
- 不直接对业务方可见
- 由业务包调用
- 可以有 ToolDefinition
- 默认注册
- 不做 ENABLED_TOOLS 配置
```

示例：

```text
object_storage_read:1
image_download_validate:1
audio_decode_normalize:1
```

**3. Business Package**

业务能力包是唯一可插拔单元：

```text
app/business_packages/
  asset_intelligence/
  audio_stem_separation/
  poster_title_image/
  tagged_text_translation/
```

一个业务包可以包含：

```text
0..N routes
0..N job_type
0..N errors
0..N schemas
0..N services
0..N repositories
0..N prompts
0..N storage adapters
```

所以单个 job type 也是业务包：

```text
audio_stem_separation
= 一个业务包
= 只有一个 job_type

asset_intelligence
= 一个业务包
= 多个同步接口 + 多个 job_type
```

**4. Platform Meta API**

平台基础接口单独保留，不算业务包：

```text
GET /languages
GET /models
GET /prompt-templates
```

它们继续在：

```text
app/api/routes/meta.py
```

语义是：

```text
服务级元信息
默认存在
不随业务包卸载
```

**最终依赖图**

```text
业务包
  ├─ 调用 app/jobs 提交/执行 Job
  ├─ 调用 app/tools 执行底层动作
  ├─ 调用 app/ai 访问模型
  ├─ 调用 app/object_storage 读写对象
  └─ 调用 app/core 使用配置/错误/日志

工具包
  ├─ 调用 app/object_storage
  ├─ 调用 integrations
  └─ 调用底层第三方库

平台内核
  └─ 不依赖具体业务包
```

**业务包注册模型**

收口后每个业务包只暴露一个入口：

```text
app/business_packages/asset_intelligence/register.py
```

负责声明：

```text
这个包叫什么
有哪些 routes
有哪些 job_type
有哪些 error specs
需要哪些 tools
需要哪些模型能力
```

平台启动时：

```text
读取 ENABLED_BUSINESS_PACKAGES
  -> 加载业务包 register.py
  -> 业务包注册 routes / job_types / errors
  -> 平台注册默认 tools
  -> freeze registries
  -> validate registries
  -> 启动 API / worker
```

**配置收口**

只暴露一个业务包开关：

```env
ENABLED_BUSINESS_PACKAGES=
```

含义：

```text
为空
  -> 默认加载全部业务包

asset_intelligence,audio_stem_separation
  -> 只加载这些业务包
```

不再暴露：

```env
ENABLED_JOB_TYPES=
ENABLED_TOOLS=
ENABLED_CAPABILITIES=
```

`job_type` 是否外部可创建，由业务包内部的 `JobTypeSpec` 决定：

```text
visibility=public
role=root
  -> 可外部创建

visibility=internal 或 role=leaf
  -> 只能内部 workflow 使用
```

**业务包内部建议结构**

以 `asset_intelligence` 为例：

```text
app/business_packages/asset_intelligence/
  register.py
  errors.py

  api/
    routes.py
    schemas.py

  image_tagging/
    executor.py
    schemas.py
    prompt.py

  tag_translation/
    executor.py
    schemas.py
    prompt.py

  vector_indexing/
    service.py
    repository.py
    schemas.py

  vector_search/
    service.py
    repository.py
    schemas.py

  storage_adapter.py
```

`register.py` 做统一装配：

```text
register_errors()
register_job_types()
include_routes()
declare_required_tools()
declare_required_model_capabilities()
```

**不建议做的事**

不要做：

```text
app/jobs/types/asset_image_tagging
app/jobs/types/asset_tag_translation
app/api/routes/asset_vector.py
app/services/asset_vector.py
app/repositories/asset_vector.py
```

这会把一个业务包拆散。

也不要做：

```text
foundation capability
```

因为会和 `tools` 概念重叠。

也不要做：

```text
ENABLED_TOOLS
```

工具不是业务开关。

**最小实现顺序**

```text
第 1 步：新增 BusinessPackage 定义
第 2 步：新增业务包注册器
第 3 步：平台启动改成加载业务包
第 4 步：迁移现有 job_type 为业务包
第 5 步：移除/弱化 ENABLED_JOB_TYPES
第 6 步：保留 app/tools 默认注册
第 7 步：让 routes 也能由业务包注册
第 8 步：补 registry contract tests
第 9 步：再接 asset_intelligence
```

**最终心智**

```text
平台负责运行机制
工具负责底层动作
业务包负责业务能力
配置只控制业务包是否加载
```

这就是本次收口的核心。
