# 脚本职责和边界梳理

本文用文字可视化梳理 `scripts/` 的入口边界。核心目标是区分“事实源入口”和“编排入口”，避免同一能力在多个脚本里各自实现，形成维护分叉。

## 先理解一件事

脚本入口不是按“谁会调用谁”来分层，而是按“谁拥有某个领域能力的事实源”来分层。

```text
事实源入口
  -> 拥有某个领域的命令面和行为规则
  -> 负责真正判断、校验、执行或输出领域事实
  -> 其他脚本需要该能力时，只能编排或复用它

编排入口
  -> 负责把多个事实源入口按场景串起来
  -> 不重新实现被编排入口的内部判断
  -> 不把 recipe、运行环境适配或业务流程误写成新事实源
```

最典型的例子：

```text
run.sh
  -> 日常 recipe 编排入口
  -> 调用 deploy.sh / dev.sh / verify.sh
  -> 不是进程生命周期、compose 部署或验证规则的事实源

dev.sh
  -> 宿主机 API / worker 生命周期事实源

deploy.sh
  -> compose-deps / compose-full 部署形态事实源

verify.sh
  -> 一次性验证任务事实源
```

因此，不能因为 `run.sh up dev` 会启动依赖、迁移、启动 API / worker，就把这些细节搬进 `run.sh`。`run.sh` 只负责编排稳定入口。

## 当前脚本全景

```text
scripts/
  run.sh
    日常快捷 recipe 编排

  dev.sh
    宿主机 API / worker 生命周期事实源
    -> scripts/dev/

  deploy.sh
    docker compose 部署形态事实源
    -> compose-deps
    -> compose-full

  verify.sh
    一次性验证事实源
    -> scripts/verify/

  k8s.sh
    已部署 Pod 内手动运维入口
    -> 当前 Pod 环境编排
    -> PostgreSQL / Redis 连接检查编排
    -> Alembic current / heads / migrate
    -> OSS 显式检查

  redis.sh
    Redis 只读排障事实源
    -> 内部下沉实现是 scripts/redis_diag/

  jobs.sh
    Job 只读查询与排障事实源
    -> scripts/jobs/

  job-ops.sh
    Job 写操作运维入口

  load.sh
    项目级压测入口

  triton-bench.sh
    Triton 推理服务直压入口

  real-flow.sh
    手动真实模型 / 对象存储流程验证入口

  models.sh
    本地模型资产下载、路径和必需文件检查
```

## 事实源关系图

下面这张图比“脚本列表”更重要。它说明了能力归属。

```text
日常开发 recipe
  run.sh
    -> deploy.sh up compose-deps
    -> dev.sh migrate
    -> dev.sh start api
    -> dev.sh start worker
    -> verify.sh ...

本地宿主机进程
  dev.sh
    -> API / worker start / stop / restart / status
    -> 不启动或停止 PostgreSQL / Redis
    -> 不管理 compose-full

compose 部署形态
  deploy.sh
    -> compose-deps: 只管理 PostgreSQL / Redis
    -> compose-full: 管理 API / worker / PostgreSQL / Redis
    -> 不管理宿主机 API / worker 生命周期

Redis 排障
  redis.sh
    -> Redis URL / PING / server version
    -> command capability
    -> memory / keyspace / top keys
    -> Stream / broker key / consumer group / pending / lag

Pod 内运维
  k8s.sh
    -> 使用当前 Pod 注入的 DATABASE_URL / REDIS_URL
    -> Redis 检查只编排 redis.sh
    -> 不自己维护 Redis 诊断逻辑

Job 排障
  jobs.sh
  -> PostgreSQL 中的 Job / attempt / callback / timeline 事实
    -> 需要 Redis broker 证据时复用 redis.sh 的排障能力
    -> 不自己维护 Redis 实例诊断逻辑
```

## Redis 边界为什么要独立

Redis 不是 Job 的子能力，也不是 K8s 的子能力。它是多个运行形态都会依赖的基础设施。

错误模型：

```text
jobs.sh redis
  -> 容易让 Redis 排障被误认为只服务 Job

k8s.sh check redis 内联 Python
  -> 容易让 Redis 排障被误认为只服务 Pod

jobs.sh / k8s.sh 各自实现 Redis 判断
  -> 同一个 Redis 事实出现多个判断源
  -> server version / Stream capability / key type / lag 规则会漂移
```

正确模型：

```text
redis.sh
  -> Redis 排障一级入口和事实源
  -> 下沉实现位于 scripts/redis_diag/

k8s.sh
  -> Pod 场景编排
  -> 显式使用当前 Pod 注入的 REDIS_URL 调用 redis.sh

jobs.sh
  -> Job 场景编排
  -> 从 Job 语境读取配置后复用 redis.sh 的 broker key 诊断能力
```

这和 `run.sh` 的位置类似，但不要混淆：

```text
run.sh
  -> 编排入口
  -> 不是事实源

redis.sh
  -> Redis 排障事实源入口
  -> 其他入口编排它
```

更准确的类比是：

```text
dev.sh      是宿主机进程生命周期事实源
deploy.sh   是 compose 部署形态事实源
redis.sh    是 Redis 排障事实源
run.sh      是 recipe 编排入口
k8s.sh      是 Pod 运维编排入口
```

## 入口职责表

| 入口 | 类型 | 负责 | 不负责 |
|---|---|---|---|
| `run.sh` | 编排入口 | 日常 recipe，例如 `up dev` / `down dev` / `status dev` | 进程管理细节、compose 细节、Redis 诊断规则 |
| `dev.sh` | 事实源入口 | 宿主机 API / worker 生命周期、迁移、状态、本地端口探测 | 启停 Docker 依赖、管理 compose-full、远程生产运维 |
| `deploy.sh` | 事实源入口 | `compose-deps` / `compose-full` 部署形态 | 宿主机 API / worker 生命周期、K8s 资源 |
| `verify.sh` | 事实源入口 | 一次性验证任务、脚本 help / syntax / tests 编排 | 服务生命周期管理、业务修复 |
| `k8s.sh` | 编排 + Pod 运维入口 | Pod 内连接检查、Alembic 状态和手动迁移、OSS 显式检查 | 创建 K8s 资源、维护 Redis 诊断规则、发布编排 |
| `redis.sh` | 事实源入口 | Redis 连接、版本、命令能力、内存、keyspace、Stream 和 broker key 证据 | Job 状态查询、Pod 选择、自动修复 Redis |
| `jobs.sh` | 事实源入口 | Job / attempt / callback / timeline 只读排障 | 创建、取消、重试、补偿 Job；维护 Redis 实例诊断规则 |
| `job-ops.sh` | 写操作运维入口 | 明确授权的 Job 写操作 | 只读观察、Redis 实例诊断 |
| `load.sh` | 事实源入口 | 项目级 API / Job 链路压测 | Triton 直压、生产发布 |
| `triton-bench.sh` | 事实源入口 | Triton 推理服务直压 | FastAPI Job、DB / Redis / OSS / callback |
| `models.sh` | 事实源入口 | 本地模型资产下载、路径、必需文件检查 | 模型推理、真实业务流程 |
| `media.sh` | 事实源入口 | 本地音视频素材探测、校验和准备 | 下载模型、提交 Job、上传对象存储 |
| `tools.sh` | 辅助入口 | 无默认持久副作用的小型开发工具 | 生命周期、部署、Job 排障、Redis 排障 |

## 判断一个新能力放哪里

先问三个问题：

```text
1. 这个能力属于哪个领域？
   -> 进程生命周期 / compose 部署 / Redis 排障 / Job 排障 / 压测 / 模型资产 / 媒体素材 ...

2. 它是在“拥有事实”，还是只是在“串联事实源”？
   -> 拥有事实：放到对应事实源入口
   -> 串联事实源：放到编排入口

3. 它是否会让两个入口维护同一套判断？
   -> 会：不要新增；改为调用既有事实源
```

可视化判断：

```text
需要新增功能
  |
  v
是否已有领域事实源？
  |
  +-- 是 -> 放入该入口或由该入口下沉到内部模块
  |         例如 Redis 排障 -> redis.sh
  |
  +-- 否 -> 是否只是串联多个入口？
            |
            +-- 是 -> 放入 run.sh / k8s.sh 等编排入口
            |
            +-- 否 -> 才考虑新增顶层 *.sh
```

## 不应该做的事

```text
不要把 recipe 塞回事实源
  例：不要让 dev.sh 负责 compose-deps 编排。

不要把事实源复制到编排入口
  例：不要让 k8s.sh 内联 Redis Stream / memory / keyspace 判断。

不要把基础设施排障绑定到业务入口
  例：不要把 Redis 实例诊断主入口放到 jobs.sh 下。

不要为兼容旧路径保留两套逻辑
  例：redis.sh 和 jobs.sh 各自实现 broker key 判断。

不要新增 silent fallback
  前置条件不满足时直接报错，便于定位。
```

## 当前 Redis 设计的核心结论

```text
Redis 排障事实源
  ./scripts/redis.sh
    -> 内部实现下沉到 scripts/redis_diag/cli.py

Pod 内 Redis 检查
  ./scripts/k8s.sh check redis
    -> 显式使用当前 Pod 的 REDIS_URL
    -> 编排 ./scripts/redis.sh check --show-url --no-broker-key

Job broker 证据
  ./scripts/jobs.sh broker
    -> 保持 Job 排障入口语义
    -> 读取 jobs.sh 自己的配置链路
    -> 复用 redis.sh 的 broker key 诊断能力
```

一句话总结：

```text
事实源入口负责“这个领域到底怎么判断”；
编排入口负责“在这个场景下按什么顺序调用哪些事实源”。
```
