StemSplitio / htdemucs-ft-onnx · 音乐源分离

把一首完整的歌，拆回四条独立音轨

HTDemucs-FT 是 Meta（Facebook Research）Demucs v4 的微调版本，也是目前开源音乐源分离（Music Source Separation）的标杆模型之一。StemSplitio 将其导出为 ONNX 格式，摆脱 PyTorch 依赖，便于跨平台、跨语言部署——包括部署到阿里云的推理服务上。

任务 4-stem 源分离 架构 双域 U-Net + 跨域 Transformer 采样率 44.1 kHz / 双声道 MUSDB-HQ SDR ≈ 9.0 dB 格式 ONNX（onnxruntime 推理）
Section 1

这是个什么模型？

Demucs（Deep Extractor for Music Sources）是 Meta 开源的音乐源分离模型系列。发展到 v4 时，架构演进为 HTDemucs（Hybrid Transformer Demucs）：在"时域 + 频域"双分支混合结构的瓶颈处引入了跨域 Transformer。而 htdemucs_ft（fine-tuned）是在 HTDemucs 基础上针对每一个 stem 分别微调得到的版本——官方实现里它实际是 4 个模型组成的"模型袋"（bag of models），每个模型专精一个音源，分离质量更高（MUSDB-HQ 测试集 SDR 约 9.0 dB，对比基础版 htdemucs 约 8.4 dB），代价是推理计算量约为基础版的 4 倍。

模型接收 44.1 kHz 立体声混音波形，输出四条同样长度的立体声波形：

🥁 drums

鼓与打击乐。瞬态密集、宽频段，时域分支对它贡献最大。

🎸 bass

贝斯。能量集中在低频，频域分支的低频分辨率是关键。

🎹 other

其他所有乐器（吉他、钢琴、合成器、弦乐……），最"杂"的一轨。

🎤 vocals

人声。谐波结构清晰，是卡拉OK/翻唱等应用最关心的一轨。

StemSplitio/htdemucs-ft-onnx 这个仓库做的事情，是把上述 PyTorch 模型导出为 ONNX（Open Neural Network Exchange）格式。这样一来：推理只需要 onnxruntime，不需要装 PyTorch；可以在 C++ / C# / Java / Node / 移动端等环境运行；也能对接 TensorRT、OpenVINO 等加速后端——非常适合做成云上的独立推理服务。

Section 2

架构可视化：为什么叫 "Hybrid Transformer"

音乐信号有两副面孔：波形（时域）擅长表达瞬态和相位（鼓点、attack），频谱（频域）擅长表达音高与谐波结构（人声、贝斯）。HTDemucs 不做二选一，而是两条 U-Net 并行，在最深处用 Transformer 让两个域互相"对话"。

频域分支

对输入做 STFT（n_fft=4096, hop=1024），把复数谱的实部/虚部当作通道（CaC，Complex-as-Channels）送入 2D 卷积编码器。5 层编码逐层在频率轴上下采样，直到频率维被压缩成 1，此时频域特征的形状和时域分支对齐——这正是两个域可以在瓶颈处融合的前提。解码后经 iSTFT 还原为波形。

时域分支

就是经典 Demucs 的 1D 卷积 U-Net：编码器逐层做步长为 4 的卷积下采样，解码器用转置卷积还原。它直接建模采样点，保留了频域表示容易丢失的相位与瞬态信息，对鼓这类打击乐尤其重要。

跨域 Transformer（模型名字里的 "T"）

在两条 U-Net 的最深处（时间分辨率已被压缩约 1024 倍），交替堆叠两种注意力层：自注意力让每个域在长达约 7.8 秒的感受野内建模长程依赖（比如整段副歌的人声连续性）；交叉注意力让频域特征查询时域特征、时域特征查询频域特征，两个"视角"互相校准。位置信息用 2D 正弦位置编码注入。

"FT" 微调版的特殊之处

htdemucs_ft 用了额外训练数据、并为每个音源单独微调出一个专家模型。推理时 4 个专家各跑一遍，各取所长拼出最终结果。这解释了两件事：① 它比基础版慢约 4 倍；② ONNX 导出物可能是一个打包后的模型，也可能是分 stem 的多个 .onnx 文件——部署前先看仓库文件列表确认。

Section 3

ONNX 版本：导出时发生了什么

把 HTDemucs 导出成 ONNX 不是一句 torch.onnx.export 就完事，有两个关键工程点，直接影响你写部署代码的方式：

① STFT / iSTFT 通常被移出模型

ONNX 算子集对 torch.stft / istft（复数运算、中心填充等）支持不完善，所以社区的 Demucs ONNX 导出普遍采用的做法是：ONNX 图只包含神经网络主体，STFT 在前处理、iSTFT 在后处理，由宿主代码（Python/C++）完成。典型的模型 I/O 形如：

具体到 StemSplitio 这个导出：输入/输出的名称、数量、形状以模型卡（Model Card）和仓库文件为准。拿到 .onnx 文件后，先用下一节的"体检脚本"打印 I/O 签名，再按签名写前后处理——这一步能避免绝大多数部署踩坑。若该导出已把 STFT 融入图内（部分导出用 Conv 实现 DFT 矩阵来规避算子限制），则宿主侧无需再做 STFT。

② 长音频必须分段 + 重叠拼接

模型训练时的段长约 7.8 秒（44.1kHz 下约 343,980 个采样点），且 Transformer 的注意力开销随长度平方增长。因此整首歌不能一次性喂给模型，标准做法是：切成固定长度的片段，相邻片段重叠 25%，推理后用加权窗（如三角窗）做 overlap-add 拼回，消除接缝处的咔哒声。官方还有 shifts 技巧（随机时移多次推理取平均）进一步提升质量，代价是成倍的耗时。

第二步：完整分离脚本（分段 + 重叠拼接）

separate.py · 以"波形进、4 stems 出"的导出为例
import numpy as np
import soundfile as sf
import onnxruntime as ort

SR        = 44100
SEG_LEN   = int(7.8 * SR)          # 训练段长 ≈ 7.8 s
OVERLAP   = 0.25                     # 25% 重叠
STEMS     = ["drums", "bass", "other", "vocals"]

def load_audio(path):
    wav, sr = sf.read(path, dtype="float32", always_2d=True)
    wav = wav.T                                      # (C, T)
    if wav.shape[0] == 1:                            # 单声道→双声道
        wav = np.repeat(wav, 2, axis=0)
    assert sr == SR, f"请先重采样到 44100Hz（当前 {sr}）"
    return wav

def separate(model_path, wav):
    sess = ort.InferenceSession(model_path, providers=[
        "CUDAExecutionProvider", "CPUExecutionProvider"])
    in_name = sess.get_inputs()[0].name

    # —— 归一化（Demucs 惯例：按整体均值/方差）——
    ref  = wav.mean(0)
    mean, std = ref.mean(), ref.std() + 1e-8
    wav_n = (wav - mean) / std

    T      = wav_n.shape[-1]
    stride = int(SEG_LEN * (1 - OVERLAP))
    out    = np.zeros((4, 2, T), dtype=np.float32)
    weight = np.zeros(T, dtype=np.float32)
    win    = np.concatenate([                        # 三角窗做加权拼接
        np.linspace(0, 1, SEG_LEN // 2, endpoint=False),
        np.linspace(1, 0, SEG_LEN - SEG_LEN // 2)]).astype(np.float32)

    for start in range(0, T, stride):
        end   = min(start + SEG_LEN, T)
        chunk = wav_n[:, start:end]
        if chunk.shape[-1] < SEG_LEN:                # 末尾补零到固定长度
            pad   = SEG_LEN - chunk.shape[-1]
            chunk = np.pad(chunk, ((0, 0), (0, pad)))
        x = chunk[None]                              # (1, 2, SEG_LEN)

        y = sess.run(None, {in_name: x})[0][0]       # (4, 2, SEG_LEN)

        n = end - start
        out[..., start:end]  += y[..., :n] * win[:n]
        weight[start:end]    += win[:n]
        if end >= T: break

    out /= np.maximum(weight, 1e-8)
    return out * std + mean                          # 反归一化

if __name__ == "__main__":
    wav   = load_audio("song.wav")
    stems = separate("model/htdemucs_ft.onnx", wav)
    for name, s in zip(STEMS, stems):
        sf.write(f"out_{name}.wav", s.T, SR)
        print("saved", name)
若体检脚本显示模型是"双输入 / 双输出"（波形 + 频谱进，时域 + 频域出），在上面循环内加两步：喂入前对 chunk 做 STFT 组装第二个输入；取出后对频域输出做 iSTFT，与时域输出相加再进行 overlap-add。若仓库是按 stem 拆分的 4 个 onnx 文件，则对每个文件各跑一遍，各取对应的那条输出。
Section 5

部署到阿里云

音源分离是计算密集 + 单次耗时较长（htdemucs_ft 处理一首 4 分钟歌曲：GPU 约十几秒到一分钟量级，纯 CPU 可能数分钟）的任务，建议按"异步任务"而不是"同步 HTTP 请求"来设计。阿里云上有四条主流路径：

方案适合场景GPU 支持特点
PAI-EAS
模型在线服务		正式生产、需要弹性伸缩的推理服务✅ T4 / A10 等专为模型推理设计，自带自动扩缩容、蓝绿发布、监控；支持自定义镜像部署，最省运维
ECS + GPU流量稳定、想完全掌控环境✅ gn6i(T4) / gn7i(A10)最灵活，自己装 Docker 跑服务；成本随实例包月/按量，无弹性时利用率是关键
函数计算 FC
GPU 实例		调用低频、突发流量、想按量付费✅（GPU 函数）冷启动需拉大镜像（onnxruntime-gpu 镜像常 >3GB），务必开启镜像加速/预留实例
ACK（K8s）已有容器平台、多模型多服务编排✅运维成本最高，适合平台化团队

下面以最常用的组合落地：Docker 镜像 → 推送 ACR（容器镜像服务）→ 部署 PAI-EAS，音频文件通过 OSS 中转。

Step 1 · 编写推理服务（FastAPI）

app.py · 接收 OSS 路径，分离后回传 OSS
import os, uuid, tempfile
import oss2, soundfile as sf
from fastapi import FastAPI
from pydantic import BaseModel
from separate import load_audio, separate, STEMS, SR   # 复用上一节的代码

app = FastAPI()

auth   = oss2.Auth(os.environ["OSS_AK_ID"], os.environ["OSS_AK_SECRET"])
bucket = oss2.Bucket(auth,
                     "https://oss-cn-hangzhou-internal.aliyuncs.com",  # 同地域用内网端点，免流量费
                     os.environ["OSS_BUCKET"])

MODEL = "/app/model/htdemucs_ft.onnx"

class Job(BaseModel):
    input_key: str            # OSS 上的输入音频路径，如 uploads/song.wav

@app.get("/healthz")
def healthz():
    return {"ok": True}

@app.post("/separate")
def run(job: Job):
    tmp = tempfile.mkdtemp()
    src = os.path.join(tmp, "in.wav")
    bucket.get_object_to_file(job.input_key, src)

    stems  = separate(MODEL, load_audio(src))
    job_id = uuid.uuid4().hex[:12]
    keys   = {}
    for name, s in zip(STEMS, stems):
        p = os.path.join(tmp, f"{name}.wav")
        sf.write(p, s.T, SR)
        key = f"results/{job_id}/{name}.wav"
        bucket.put_object_from_file(key, p)
        keys[name] = key
    return {"job_id": job_id, "stems": keys}

生产上建议再进一步：/separate 只入队并返回任务 ID，由后台 worker 消费（MNS / RocketMQ / Celery），客户端轮询或走回调——避免长音频触发网关超时。

Step 4 · 验证与上线检查

健康检查

EAS 会给服务分配访问地址与 Token：curl -H "Authorization: TOKEN" https://xxx.pai-eas.aliyuncs.com/api/predict/demucs-separation/healthz

端到端测试

先把一首测试歌曲传到 OSS，POST /separate 带上 input_key，确认 4 个 stem 文件出现在 results/ 下且可正常播放、无接缝噪声。

超时与并发

网关/客户端超时调到覆盖最长音频的处理时间；EAS 上将单实例并发设为 1~2（GPU 推理排队优于并行争抢显存），靠横向扩容承接流量。

弹性与成本

EAS 开启按 QPS/GPU 利用率的自动扩缩容，低谷缩到 0 或 1 个实例；调用极低频时改用函数计算 GPU + 预留实例更省钱。

安全

AK/SK 不写死在镜像里——用环境变量注入，或给 EAS 绑定 RAM 角色走 STS 临时凭证；OSS 桶设为私有，结果用签名 URL 下发。

Section 6

性能与成本优化

手段做法收益 / 代价
Execution ProviderGPU 上 providers 顺序写 ["TensorRTExecutionProvider","CUDAExecutionProvider","CPUExecutionProvider"]；TensorRT EP 首次会编译引擎，记得开启引擎缓存TensorRT 常有 1.5~3× 提速；首次加载慢
FP16GPU 上用 fp16 版模型或 TensorRT fp16 模式显存减半、提速明显，音质几乎无损
INT8 量化onnxruntime.quantization 动态量化，CPU 场景收益大速度↑ 体积↓，但源分离对精度敏感，务必 A/B 试听 SDR 回归
减少 shifts线上服务把 shifts 设为 0 或 1（离线高质量导出再用大 shifts）每减一个 shift 少一整遍推理
会话复用InferenceSession 进程内只建一次（模块级单例），开启 graph_optimization_level=ORT_ENABLE_ALL免去每请求数秒的模型加载
CPU 线程CPU 部署时设 intra_op_num_threads = 物理核数，容器内配合 CPU limit避免超卖导致的抖动

规格参考（估算，务必以实测为准）

  • GPU（T4 / A10）：4 分钟歌曲的 htdemucs_ft 全 4-stem 分离通常在数十秒量级；A10 明显快于 T4。
  • CPU（8 vCPU）：同样任务可能需要数分钟，仅适合离线批处理或低频调用。
  • 显存：单实例单并发下 8~16 GB 显存较稳妥；segment 越长显存越高。
