# Smoke/E2E Runtime Specification v1

本文定义一套可跨项目复用的端到端测试规范。目标是把服务生命周期、端到端验证和排障查询拆开，让每个项目都能用同一套心智模型组织测试入口，而不是把启动服务、构造数据、调用 HTTP、查数据库、清理和诊断全部塞进一个脚本。

本文中的关键字含义：

- **MUST**：接入本规范时必须满足。
- **SHOULD**：强烈建议满足；不满足时需要在项目 smoke README 中说明原因。
- **MAY**：可选能力，适合项目按复杂度逐步引入。

## 文档边界

本文是目标规范，不是当前实现事实清单。已经落地的能力应记录到 `docs/current/`，外部调用方可以依赖的 HTTP 合同应记录到 `docs/contracts/`，后续实施拆分应记录到 `docs/plans/`。

本文负责定义：

- smoke/E2E runtime 的职责边界。
- 跨项目统一的 CLI 合同。
- scenario 生命周期。
- artifacts、终端摘要和 exit code 规范。
- 项目接入时的验收标准。

本文不负责定义：

- 某个项目的服务启动 runbook。
- 某个项目的业务排障手册。
- 某个本地调试脚本的兼容策略。
- 具体 RabbitMQ、OSS、Triton、provider 或 `.env` 字段。

## 核心模型

测试入口按职责拆成三类：

```text
run.sh / dev.sh / deploy.sh / deploy script
  -> 环境生命周期
  -> 启动、停止、重启、状态、检查

python -m smoke
  -> 端到端验证
  -> 调 HTTP API、轮询、断言、输出证据

job.sh / debug.sh / admin.sh / diagnostics script
  -> 排障查询
  -> 查 DB、查 timeline、查 outbox、查状态
```

这三类入口不能互相吞并职责。尤其不要让一个脚本同时负责：

```text
启动服务 + 初始化数据 + 调 HTTP + 查 DB + 清理 + 诊断
```

这类脚本短期方便，但长期会把项目绑定到某个本地环境、某个 `.env`、某个消息队列、某个对象存储或某个业务流程，导致其他项目无法复用。

## 测试分层

项目测试分为三层，不能互相替代：

| 层级 | 目标 | 特征 | 入口 |
|---|---|---|---|
| Unit / Contract | 快速验证纯逻辑、协议、schema、边界条件 | 离线、确定性、可并发、适合 CI baseline | `pytest` / 单元测试框架 |
| Integration | 验证本项目和局部依赖的组合行为 | 可使用本地 DB、mock 外部 provider 或受控测试依赖 | `pytest tests/integration` / 项目自定义 gate |
| Smoke / E2E | 验证已经运行的真实服务链路 | 走 HTTP、真实依赖、耗时、产出证据、适合人工验收或发布前 gate | `python -m smoke` |

`smoke` MUST 与 `pytest` 分离。`pytest` 应保持快、离线、确定性；`smoke` 面向真实环境和真实外部依赖，允许慢，但必须输出可排障证据。

CI 默认只跑 Unit / Contract 和可控 Integration。真实外部依赖 smoke SHOULD 作为手动验收、发布前环境 gate 或显式标记的环境测试运行，不应伪装成稳定单元测试。

## 规范边界

`python -m smoke` 只验证已经运行的服务是否按外部合同工作。

它负责：

- 读取项目配置。
- 检查目标服务是否可访问。
- 构造 E2E 输入。
- 通过 HTTP API 提交业务请求。
- 轮询业务状态直到终态。
- 对业务结果做断言。
- 保存请求、响应、轮询、callback、timeline 和错误摘要等证据。
- 用稳定 exit code 表达结果。

它不负责：

- 启动、停止或重启服务。
- 启动 worker、模型服务、Triton、RabbitMQ、Redis、PostgreSQL 或其他依赖。
- 执行数据库 migration。
- 直接修改业务数据库来推进主流程。
- 替代单元测试、合同测试、migration 检查、lint 或脚本语法检查。
- 把项目专属的本地调试脚本变成跨项目标准。

## 标准 CLI

实现本规范的项目统一提供：

```bash
ENV_FILE=.env uv run python -m smoke \
  --base-url http://127.0.0.1:8121 \
  --timeout 7200 \
  --poll-interval 5 \
  <scenario> [scenario args...]
```

项目可以使用自己的配置入口，例如：

```bash
CONFIG_FILE=config.yaml uv run python -m smoke \
  --base-url http://127.0.0.1:18080 \
  --timeout 7200 \
  --poll-interval 5 \
  workspace
```

`ENV_FILE`、`CONFIG_FILE`、对象存储、消息队列和业务 provider 都是项目差异；统一的是 `python -m smoke` 入口、通用参数和场景生命周期。

运行配置的优先级必须稳定：

```text
显式 CLI 参数
  > 显式配置文件参数，例如 --env-file / CONFIG_FILE
  > 环境变量
  > 项目默认值
```

最终生效配置 MUST 以脱敏形式写入 artifacts，例如 `env.redacted.json` 或 `config.redacted.json`。同一条命令不应因为调用者 shell 中的隐式环境差异而产生不可解释的行为。

通用参数：

| 参数 | 要求 |
|---|---|
| `--base-url <url>` | v1 必须支持。目标服务 HTTP base URL。 |
| `--env-file <path>` | v1 建议支持。读取本地环境变量配置；项目也可以提供 `CONFIG_FILE` 等等价配置入口。 |
| `--timeout <seconds>` | v1 必须支持。整个场景的最大等待时间。 |
| `--poll-interval <seconds>` | v1 必须支持。轮询间隔。 |
| `--output-dir <dir>` | v1 必须支持。证据输出根目录。 |
| `--json` | v1 必须支持。终端输出机器可读 summary。 |

命令面分为 support commands 和 business scenarios。

support commands 不属于完整业务 E2E 场景，不要求执行七阶段 lifecycle；它们负责暴露运行前检查和场景清单：

| 子命令 | 要求 |
|---|---|
| `health` | MUST 提供等价能力。检查服务进程级可用性，例如 `/health`。 |
| `ready` | MUST 提供等价能力。检查依赖级可用性，例如 DB、队列、外部 provider。 |
| `list` | MUST。列出当前项目支持的 smoke 场景、场景说明和主要依赖。 |

business scenario 才是完整 E2E 场景：

| 子命令 | 要求 |
|---|---|
| `<scenario>` | MUST。执行业务场景。场景参数由项目定义，必须遵守七阶段 lifecycle。 |

`list` 和 `summary.json` MUST 输出一致的场景元数据：

| 字段 | 含义 |
|---|---|
| `name` | 稳定场景名。 |
| `type` | `capability`、`workflow`、`callback`、`provider_probe` 等。 |
| `acceptance_class` | `business_e2e`、`plumbing`、`exploratory` 等。 |
| `dependencies` | 所需服务和外部依赖，例如 DB、broker、OSS、worker、model service。 |
| `destructive` | 是否包含破坏性 setup/cleanup；默认必须是 `false`。 |
| `supports_resume` | 是否支持分阶段恢复。 |

示例：

```bash
uv run python -m smoke capability --capability separate
uv run python -m smoke workflow --phase all
uv run python -m smoke workspace --episodes 0001 0004 --provider minimax
uv run python -m smoke callback --run-id <run-id>
```

## Python 参考结构

以下是 Python 项目的参考落地结构，不是跨语言项目的唯一实现方式。只要满足 CLI、lifecycle、artifacts、exit code 和职责边界，其他语言可以采用等价目录。

推荐目录结构：

```text
smoke/
  __main__.py
  context.py
  client.py
  artifacts.py
  assertions.py
  scenarios/
    health.py
    ready.py
    audio_stem_job.py
    workspace.py
    callback.py
  README.md
scripts/
  smoke.sh
```

文件职责：

| 文件 | 参考职责 |
|---|---|
| `smoke/__main__.py` | CLI 入口，只做参数解析、配置加载、scenario 分发和 exit code 映射。 |
| `smoke/context.py` | 统一保存 base URL、timeout、poll interval、output dir、env/config、trace id 等运行上下文。 |
| `smoke/client.py` | HTTP client，只封装外部 API 调用，不放业务流程。 |
| `smoke/artifacts.py` | 创建结果目录，写入 request、response、polls、summary、错误摘要等证据。 |
| `smoke/assertions.py` | 通用断言工具，例如状态终态、字段存在、callback 匹配、超时判断。 |
| `smoke/scenarios/` | 业务场景实现，每个场景遵守统一生命周期。 |
| `smoke/loaders.py` / `smoke/srt.py` | 可选。纯解析辅助，例如 JSON/SRT loader；必须可离线单测。 |
| `smoke/fixtures/` | 静态默认输入和小型 fixture。不得放 secret，不得放随环境变化的 URL。 |
| `smoke/results/` | 本地运行证据目录，必须 gitignore。 |
| `smoke/README.md` | 当前项目 smoke 使用说明和场景列表。 |
| `smoke/SCENARIOS.md` | 可选。复杂业务的人工场景矩阵、验收观察点和排错路径。 |
| `scripts/smoke.sh` | 可选薄入口，只显示项目级帮助或转发到 `python -m smoke`。 |

`scripts/smoke.sh` 只能是 thin wrapper。允许提供 `-h|--help|help` 项目级说明，但业务执行路径必须直接转发：

```bash
#!/usr/bin/env bash
set -euo pipefail
# 可选：处理 -h|--help|help 并输出 Usage
exec uv run python -m smoke "$@"
```

不要在 shell wrapper 中写业务流程、数据库查询、环境初始化或复杂分支。

## 可复用实践

从现有视频配音服务的 smoke 体系中，可以抽象出以下可复用实践。

### HTTP-only Client

`smoke/client.py` SHOULD 是薄 HTTP client：

- 只封装服务对外 HTTP API。
- 不导入业务 backend、repository、service 或 ORM。
- 本地 HTTP client SHOULD 关闭环境代理继承，例如 `httpx.Client(trust_env=False)`，避免 localhost 请求被代理、`.netrc` 或系统环境污染。
- API 方法命名应贴近外部合同，例如 `submit_capability`、`get_job`、`create_series`、`get_action`。

### Fixture 只放静态默认

`smoke/fixtures/` SHOULD 只放静态默认值：

- 小型 JSON。
- 小型 SRT / 文本 fixture。
- 稳定的业务默认参数，例如 language、granularity、provider slug。

不得放：

- secret。
- access key。
- 临时签名 URL。
- 会过期的 OSS/CDN URL。
- 大型媒体文件。
- 某个开发者本机绝对路径。

真实 URL、token、bucket、provider key 和本地文件路径应来自 CLI 参数或项目配置。

### Chain Mode 与 Manual Mode

顺序型业务可以同时提供两种输入模式：

```text
chain mode
  -> 不传 source 参数
  -> 从 raw fixture 和上游 artifacts 组装输入
  -> 适合按固定链路逐步验证

manual mode
  -> 显式传 source 参数或 --data
  -> 覆盖 fixture / chain 输入
  -> 适合临时换素材、复现线上问题、验证单能力
```

规范要求：

- chain mode MUST 把缺失上游结果报成清晰错误，例如“先运行 capability X”。
- manual mode MUST 由显式参数触发，不应靠隐式环境变量切换。
- modifier 参数 MAY 在两种模式下叠加，例如 `--provider`、`--model`、`--language`。
- chain mode 的中间结果也必须进入本次 artifacts，不应只覆盖写入固定文件。
- 已声明的场景或能力缺少必要 fixture / wiring 时 MUST fail fast。不要静默回退成 `{}` 或空输入，除非该场景在 `list` 和 README 中明确标注为 exploratory。

### Capability 与 Workflow 分面

复杂业务可以把 smoke 场景拆成两个分面：

```text
capability
  -> 单能力任务
  -> submit job
  -> poll job terminal
  -> assert output

workflow / workspace
  -> 业务编排场景
  -> create domain aggregate
  -> launch business action
  -> poll action terminal
  -> assert final business delivery
```

规范要求：

- 单能力场景和工作流场景 MUST 共享同一套 runtime、artifacts 和 exit code。
- 工作流场景可以分 phase 执行，例如 `create`、`analyze`、`dub`、`all`，但每个 phase 都要有独立 summary 和 artifacts。
- phase resume 所需状态必须写入 artifacts，并明确哪些字段可被后续 phase 读取。

### Scenario Matrix

复杂业务 SHOULD 提供 `smoke/SCENARIOS.md`，记录人工验收矩阵：

- 场景名称。
- 输入 fixture。
- 命令。
- 期望关键输出。
- 需要人工观察的日志、timeline、audit 或媒体结果。
- 常见失败原因和排查入口。

`SCENARIOS.md` 是人工验收指南，不替代 `summary.json`、assertions 或 exit code。

场景矩阵中的命令、路由、PASS 文案、领域术语和排障路径 MUST 随代码变更同步。接口或流程改名时，文档 drift 应被测试、review checklist 或 verify gate 捕获。

## Scenario 生命周期

每个 business E2E 场景必须显式按七个阶段组织。

```text
preflight
  -> prepare
  -> submit
  -> poll
  -> assert
  -> collect evidence
  -> cleanup
```

### 1. preflight

检查运行前置条件。

必须检查：

- `--base-url` 格式合法。
- 服务 `health` 或 `ready` 可访问。
- 必要配置存在，例如 token、bucket、provider、callback secret。
- 外部依赖满足场景要求，例如对象存储、消息队列、worker、模型服务。

preflight 只做检查，不应推进业务状态。

preflight 失败应按原因返回不同 exit code：

- 服务不可访问或 `/ready` 不通过：`3`。
- 外部 provider、对象存储、模型服务、worker 或消息队列不可用：`4`。
- 必要配置缺失：`2`。

### 2. prepare

准备输入数据。

常见动作：

- 读取 fixture。
- 上传输入文件。
- 生成 idempotency key。
- 生成 trace id。
- 构造 request payload。
- 启动本进程内的测试 callback receiver。

prepare 可以产生外部副作用，例如上传测试文件，但必须把副作用记录到 artifacts，方便失败后排查。

prepare 阶段 SHOULD 记录输入来源：

- 来自 fixture。
- 来自 chain 上游结果。
- 来自手工 CLI 参数。
- 来自配置文件。

同一场景不得同时让多个来源静默竞争；优先级必须写清楚。

如果某个场景使用降级输入，例如“缺少 target srt 时用 source srt 代替”，该场景 MUST 标注为 plumbing check。plumbing check 只能证明链路连通，不能作为业务正确性验收。

每次 smoke run MUST 拥有可追踪的唯一命名空间：

- run id。
- idempotency key。
- trace id。
- 远端对象存储前缀。
- callback path 或 callback correlation id。
- 业务对象 external id。
- resume pointer。

cleanup 只能处理当前 run 明确拥有的资源。共享环境不得依赖固定业务 id、固定对象存储路径或固定 callback endpoint 来区分运行。

### 3. submit

只通过外部 HTTP API 提交业务请求。

要求：

- 不直接写业务数据库。
- 不直接调用 service/repository 内部函数。
- 不绕过认证、幂等、schema 校验或路由层。
- 保存 request 和 submit response。

### 4. poll

轮询业务状态直到 terminal。

要求：

- 轮询间隔使用 `--poll-interval`。
- 总等待时间受 `--timeout` 限制。
- 每次 poll 的状态、进度、消息和时间戳写入 `polls.json`。
- 超时时保留最后一次响应。

### 5. assert

判断场景是否真正成功。

不能只看 HTTP 200。至少断言：

- 业务状态是预期终态。
- 必要输出字段存在。
- callback、manifest、timeline 或其他关键证据与本次 run 匹配。
- 错误终态能输出清晰原因。

用户显式请求的场景动作没有执行时 MUST 判定失败。例如请求添加 overlap、指定 provider、指定 episode、指定 phase，但前置条件不足导致该动作被跳过，不能只打印 warning 后返回通过。

### 6. collect evidence

保存完整证据。

无论成功还是失败，都要尽量保存：

- summary。
- request。
- submit response。
- polls。
- final state。
- callback。
- timeline 或等价诊断信息。
- redacted env/config。
- error summary。

证据是 E2E 测试的核心产物。终端摘要只负责告诉人“去哪里看证据”。

collect evidence 阶段 SHOULD 尽量补齐诊断视图，但不能为此改变主流程状态。可以查询：

- Public status API。
- dev/debug audit API。
- callback receiver 记录。
- timeline / action steps / job attempts 等只读诊断入口。

如果项目没有只读诊断 API，不应在 smoke 中直接查 DB 伪装成外部验收。

### 7. cleanup

可选阶段，默认不要删除证据。

cleanup 只做不会破坏排障的收尾动作，例如关闭本进程内 callback server、释放临时端口、关闭 HTTP client。是否删除远端测试数据必须由场景显式配置，不能默认执行。

破坏性前置或清理必须独立于默认 smoke：

- drop database。
- rebuild migration。
- 删除共享对象存储目录。
- purge queue。
- 清理线上或共享环境数据。

这些动作 MAY 出现在单独 runbook 中，但不能作为 `python -m smoke <scenario>` 的默认行为。

## Artifacts 规范

每次运行创建独立目录：

```text
smoke/results/20260730-194500-audio-stem-job/
  summary.json
  request.json
  submit-response.json
  polls.json
  final-state.json
  callback.json
  timeline.json
  env.redacted.json
  error.json
```

推荐 `summary.json` 结构：

```json
{
  "scenario": "audio-stem-job",
  "status": "passed",
  "phase": "assert",
  "started_at": "2026-07-30T19:45:00Z",
  "finished_at": "2026-07-30T19:45:28Z",
  "duration_seconds": 28.3,
  "run_id": "fc70a937-0632-4e99-9539-b2c565fbc7b8",
  "terminal_status": "succeeded",
  "artifacts": "smoke/results/20260730-194500-audio-stem-job",
  "error": null
}
```

命名规则：

```text
<YYYYMMDD-HHMMSS>-<scenario>[-<short-run-id>]
```

敏感信息必须脱敏：

- token。
- secret。
- password。
- access key。
- signature。
- authorization header。
- callback secret。

禁止用固定路径覆盖保存本次运行的主证据，例如只写：

```text
smoke/results/<capability>.json
smoke/results/workspace.json
```

这类固定文件 MAY 作为“resume pointer”或“latest pointer”，但完整证据 MUST 写入独立 run 目录。否则失败后无法比较多次运行，也无法支持 CI 归档。

终端默认输出人读摘要：

```text
SMOKE PASS
scenario     audio-stem-job
run_id       fc70a937-0632-4e99-9539-b2c565fbc7b8
status       succeeded
duration     28.3s
artifacts    smoke/results/20260730-194500-audio-stem-job
```

失败摘要：

```text
SMOKE FAIL
scenario     audio-stem-job
phase        poll
reason       timeout
run_id       fc70a937-0632-4e99-9539-b2c565fbc7b8
artifacts    smoke/results/20260730-194500-audio-stem-job
```

`--json` 模式输出机器可读 summary，方便 CI 解析。

## Exit Code 规范

| Exit Code | 含义 |
|---|---|
| `0` | 通过。 |
| `1` | 场景失败，例如业务终态失败、callback 不匹配、断言失败。 |
| `2` | 参数错误或配置缺失。 |
| `3` | 服务未 ready。 |
| `4` | 外部依赖不可用。 |
| `5` | 超时。 |

CLI 参数解析错误必须返回 `2`。业务失败不要返回 `2`，否则 CI 无法区分“用法错误”和“服务行为失败”。

异常映射要求：

- 不要用一个顶层 `except Exception` 全部返回 `2`。
- HTTP submit 被服务拒绝属于场景失败或配置错误，必须按响应语义映射。
- poll timeout 必须返回 `5`。
- 断言失败必须返回 `1`。
- 服务 ready 失败必须返回 `3`，不要继续执行场景。

## 场景实现约束

新增场景时必须满足：

- 场景名称稳定，适合长期出现在 CI 和文档中。
- 场景参数只表达业务输入，不泄漏本地调试脚本细节。
- `submit` 阶段只走 HTTP API。
- 所有阶段都有清晰 phase name，失败时能定位到阶段。
- 所有外部副作用写入 artifacts。
- 超时、依赖不可用、断言失败使用不同 exit code。
- 场景实现不要导入 shell 脚本。
- 场景实现不要把 worker、模型服务或消息队列生命周期管理混入 smoke。
- 场景可以包含人工观察点，但自动断言不能为空；至少要判断业务终态和关键输出字段。
- 直接调用上游第三方服务的 probe 必须隔离到独立命令或独立模块，标注为 provider probe，不得混入业务服务 E2E 主入口。
- 可复用解析器、loader、payload builder 等纯辅助逻辑必须有离线单元测试。

Python 场景实现可以采用以下参考结构：

```python
async def preflight(ctx): ...
async def prepare(ctx): ...
async def submit(ctx, prepared): ...
async def poll(ctx, submitted): ...
async def assert_result(ctx, final): ...
async def collect_evidence(ctx, result): ...
async def cleanup(ctx): ...
```

阶段函数可以共享 typed context，但不要依赖全局可变状态。

## 项目接入标准

`tasks-platform` 当前按本规范落地：

```bash
ENV_FILE=.env uv run python -m smoke \
  --timeout 7200 \
  --poll-interval 5 \
  audio-stem-job \
  --task-name audio_stem_separation
```

```bash
ENV_FILE=.env uv run python -m smoke \
  --timeout 7200 \
  --poll-interval 5 \
  audio-stem-job \
  --task-name audio_stem_separation_triton
```

这两条命令属于同一个 `audio-stem-job` scenario，通过 `--task-name` 切换 CPU worker 和 GPU/Triton worker。场景不启动服务、不启动 worker、不执行 migration、不查库推进流程；服务生命周期由 `run.sh` / `dev.sh` / `deploy.sh` 负责，排障查询由 `job.sh` 负责。

一个项目接入本规范时，至少要提供：

- `python -m smoke --help`。
- `python -m smoke list`。
- `python -m smoke health`。
- `python -m smoke ready`。
- 至少一个业务场景。
- `scripts/smoke.sh` thin wrapper，若项目需要 shell 入口。
- `smoke/README.md`，说明配置、场景和 artifacts。
- `smoke/SCENARIOS.md`，若业务需要人工验收矩阵。
- 针对 CLI help、参数解析、exit code、artifacts 写入的最小测试。
- 针对 fixture loader、SRT/JSON parser、chain input builder 等纯辅助逻辑的离线测试。
- 针对 smoke README / SCENARIOS 命令漂移的最小检查；至少在 review checklist 中覆盖。

## 反模式

不要这样做：

- 在 `scripts/smoke.sh` 里写复杂 shell 流程。
- 在 smoke 里启动 worker 或模型服务。
- 在 smoke 里直接查 DB 来判断主流程成功。
- 在 smoke 里静默吞掉依赖不可用，继续跑出误导性失败。
- 成功时不保存证据，只打印一段日志。
- 失败时只输出 stack trace，不输出 phase、reason、run_id 和 artifacts。
- 把项目本地调试脚本命名为跨项目规范入口。
- 把清理逻辑默认设为删除远端证据。
- 只把最终响应打印到终端，不写 artifacts。
- 把所有错误都映射成 exit code `2`。
- 用固定 `results/<capability>.json` 覆盖主证据。
- 让 smoke 导入业务 backend 模块来“方便复用函数”。
- 让 fixture 里保存 secret、临时 URL 或开发者本机路径。
- 把 provider 直连探针混在业务服务 E2E 场景里。
- 默认执行 drop/rebuild/purge 这类破坏性前置。
- 用户显式要求的动作没执行时只 warning 仍返回通过。
- 把 plumbing check 当成业务验收通过。
- 文档里的 smoke 命令、路由、PASS 文案和领域术语长期不校验。

## 验收清单

实现本规范后，至少检查：

- `python -m smoke --help` 能看到通用参数。
- `python -m smoke list` 能列出场景。
- `python -m smoke health` 和 `ready` 能区分进程可用与依赖可用。
- 业务场景包含七个阶段。
- 成功和失败都会创建 artifacts 目录。
- `summary.json` 包含 scenario、status、phase、duration、artifacts。
- 终端摘要不泄漏 secret。
- exit code 符合规范。
- `scripts/smoke.sh` 只是 thin wrapper。
- `run.sh`、`dev.sh`、`deploy.sh` 不调用 smoke 作为生命周期的一部分。
- `job.sh`、`debug.sh`、`admin.sh` 不承担 E2E 场景执行职责。
- `smoke/client.py` 不导入业务 backend。
- `smoke/fixtures/` 不包含 secret、临时 URL 或本机绝对路径。
- chain mode 缺少上游结果时错误清晰。
- manual mode 能显式覆盖输入。
- 固定 latest/resume 文件不是唯一证据来源。
- plumbing check 有明确标注。
- 显式场景动作未执行会失败。
- 破坏性 setup 不在默认 smoke 路径。
- smoke 文档命令与当前 CLI 没有明显漂移。
