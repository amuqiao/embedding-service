JOB KERNEL · 心智模型讲解

跟一个请求走完整条 Job 链路

这套异步 Job 机制不是一张表、一条队列，而是四本各自独立的账，外加一个周期巡检的角色。看懂这五个角色怎么配合，比记住每个字段更重要。

本文是 docs/current/job-kernel.md 的配套讲解，负责建立心智模型；字段名、默认值、约束、状态枚举等 事实以 job-kernel.md 和代码为准，两者冲突时以 job-kernel.md 为准。
概览

四本账 + 一个巡检员

系统看起来复杂，是因为它同时维护四本独立的账，每本账回答一个不同的问题；理解"为什么不能合并成一本账"，就理解了大半个 Job 内核。

job_aggregates

门面账 — 外部唯一看到的真相：状态、进度、结果、错误。

job_execution_attempts

干活账 — 这次执行谁在干、干到哪、能不能重干。

dispatch_outbox

派工账 — worker 有没有真的收到"去执行"的通知。

callback_outbox

通知账 — 调用方有没有真的收到"完成了"的通知。

RECOVERY

周期巡检，不单独持有业务事实，只对比这四本账，把卡住的地方按各自账本自己的规则往前推一步——绝不发明新的业务结果，绝不绕开 attempt lease 直接改终态。

为什么不能合并成一本账？

因为这四件事的失败方式、重试对象、重试预算完全独立：派工失败（Redis/Taskiq 发不出去）不代表业务失败，不该消耗业务重试次数；通知调用方失败（对方 5xx）不代表 Job 失败，更不该让状态回退；干活失败该不该重干，取决于 job_type 自己的策略，跟前两者无关。

Part 1

跟着一次提交走一遍

以一次普通（非 workflow）提交为例，比如 poster_title_image。

1.1 提交 — 先问"这是不是同一件事"
调用方带 client_request_id 发起请求。服务端对 caller_id + client_request_id 加事务级 advisory lock，查有没有未删除的同 key 记录。
同 key · 指纹一致→按 idempotency_mode 返回已有 Job / 报冲突 同 key · 指纹不同→CLIENT_REQUEST_ID_CONFLICT 没有记录→视为新请求，继续
1.2 接单 — 容量门禁
持锁统计 active_jobs（queued + 仍持有 active attempt 的 running），未超过 MAX_ACTIVE_JOBS 才放行。放行后 Job、首个 attempt、首条派工意图在同一事务写入，提交后才触发外部发布——数据库先落地，再触发外部效果。
1.3 派工 — Dispatch outbox 三级跳
"Job 已创建"和"worker 已知道要执行"是两件事，中间隔着一次可能失败的 Redis/Taskiq 发布。
pending→ leased→ published 发布成功；若长期无人 claim（orphan），巡检重发同一个 attempt_id
leased→ retrying→ dead_letter 发布失败：额度未耗尽先重试，耗尽后进入死信，不再自动重发
1.4 干活 — Attempt 执行权
worker 收到 attempt_id 后先"抢执行权"：Job.active_attempt_id 精确匹配 + Job 为 queued + Attempt 为 pending 才能抢到，抢到发一个 lease_token。之后所有进度、终态写入都必须带着这个 token 去匹配数据库当前的 lease——对不上就失败。这就是"同一 attempt 任一时刻只有一个 worker 能写"的实现方式，纯靠数据库条件更新，不需要分布式锁。

已知的边界

心跳只在写进度时顺带续约，不是独立线程持续续约——如果模型调用中间很长一段时间没有进度点，lease 有可能在此期间不被续约到（见 Part 7）。

1.5 交卷 — 终态与结果
成功或失败都要求"当前 lease 仍然有效"才能写终态。
succeeded→清空 active_attempt_id，写 result，顺手建 callback_outbox
failed（不可重试）→清空 active_attempt_id，写 error，顺手建 callback_outbox

这个不变量不靠代码自觉：数据库 CheckConstraint 锁死"终态时 active_attempt_id 必须为空"，反之亦然。

1.6 通知 — Callback outbox
Job 终态之后，如配置 callback_url，负责把终态告诉调用方，但结果不反向影响 Job。
pending→delivered 2xx + 合同要求的 JSON ack
retrying→dead_letter 额度耗尽；无论哪种结果，Job 自己的 status / result / error 都不会因此改变
Part 2

出问题时——三套"重试"分别保护什么

这是最容易混的地方：三套机制都叫 retry，但对象、触发条件、重试预算完全独立，互不消耗对方的额度。

出错发生在哪一步谁来决定重试重试的是什么
派工：Taskiq publish 失败dispatch_outbox 自己的策略重新发布同一个 attempt_id
干活：worker 执行失败 / 超时job_type 声明的 retry_policy为同一个 Job 创建下一个 attempt
通知：callback 投递失败callback_outbox 自己的策略重新投递同一份 callback 内容

判断"干活失败要不要重试"

can_retry = 这次失败的 error.code 命中该 attempt 的 policy_retryable_error_codes 且 Job 还没被判定为最终 failed 且 purpose_attempt_no < policy_max_attempts 命中 → 创建 next attempt（同一个 retry_chain_id，previous_attempt_id 指回上一个） Job 回到 queued，重新走一遍 1.3–1.5 没命中 → Job 进入 failed，不再有下一次
attempt purposemax_attempts默认可重试错误码实际含义
workflow_orchestration
root 负责编排的那次 attempt		 3 JOB_STATE_TRANSITION_CONFLICT
TASKIQ_PUBLISH_FAILED		 只在这两类冲突/发布错误时重试编排本身
business_execution
真正跑业务逻辑的那次 attempt		 1 （空） 默认失败一次就是最终失败，不会自动重跑

只有某个 job_type 自己在 executor 里声明更宽松的 retry_policy，business_execution 才会有额外重试——比如 poster_title_image_style_probe / poster_title_image_generate_item 声明了 max_attempts=2，只对 MODEL_CALL_TIMEOUT / OSS_FETCH_FAILED / OSS_WRITE_FAILED 三类瞬时错误放宽一次。这是按 job_type 主动选择的例外，不是全局规则——因为重跑会不会造成重复计费或重复产物，只有 job_type 自己知道，所以没有一个全局的"失败重跑 N 次"开关。

Part 3

Recovery 巡检员——能修什么，不能修什么

周期性任务（默认 60 秒一轮），每轮只做一件事：看数据库里已经落地的事实，补一个本该发生但没发生的动作。

卡在哪一步怎么发现怎么救
worker 抢到 attempt 后失联（崩溃 / 重启 / 网络分区）lease_expires_at 已过期判定 attempt 失败 → 走 Part 2 的重试判断
Taskiq publish 失败或消息丢失到期未发布 / 发布后长期无人 claim重新发布同一个 attempt_id
Job 已终态但 callback_outbox 缺失终态 root 找不到对应 outbox补建 callback_outbox
callback 投递失败，到了重试时间next_attempt_at 已到重新投递
workflow root 该推进但没推进没人调用过 reconciler补建 ready child 或收敛终态
AI 调用账本长期停在 pending超过 stale 阈值仍未终态标记失败，避免 billing 卡死

明确不做的事

  • 不会根据 provider 侧的外部状态去猜"其实已经成功了"
  • 不会重放一个已经 succeeded 的业务结果
  • 不会绕开 attempt lease 直接改 Job 的业务终态
  • 不会把一个已经判定 do_not_retry 的 Job 重新拉回 queued

Recovery 只能修"账本之间没对齐"的问题，修不了"业务本身该不该重跑"——后者的决定权始终在 job_type 声明的 retry policy 里，创建 attempt 时就已经固化成 snapshot。

已知缺口 · 未收敛

dispatch publish 重试耗尽进入 dead_letter 后，missing-dispatch 巡检会看到 outbox 已存在而不补建，due-dispatch 巡检又不会选中已 dead_letter 的行——这条路径目前不会让 Job 自动收敛到明确终态，可能长时间停在 queued。记录在 docs/plans/job-kernel-reliability-review.md 的 P1 项，属于"知道、还没修"。

Part 4

一个 Job 可能其实是一串 Job

workflow 类型的 job_type 提交后看起来是一个 Job，内部实际是一个 root + 若干 internal child，root 自己不干业务活，只负责编排。

public root Job
attempt purpose = workflow_orchestration
↓ 冻结的 workflow_plan.nodes[].depends_on
child A（无依赖，先创建）
↓ 依赖满足后才创建
child B（depends_on: A）
child C（depends_on: A）

child 带 workflow_node_key，重复调用编排不会为同一个节点建两个 child（幂等约束保护）；visibility=internal 的 job_type 任何环境都拒绝外部直接提交或查询。

每次 child 终态变化都会触发一次收敛判断

先看必须依赖已完成、状态失败的 required child 有 → fail_fast 直接判 root failed；allow_partial 看有没有至少一个成功 再看依赖已满足但还没创建的 child 有 → 创建它们（同样受 workflow_node_key 幂等约束保护） 所有 required child 都成功 → 汇总结果，root 标记 succeeded 都不是以上情况 → 只更新 root 的加权进度百分比，继续等

child 失败不会自动重跑整个 workflow，也不会重跑已经成功的 child——root 的失败是编排层看到子结果后的一次终态收敛判断，不消耗、也不触发 root 自己的 execution attempt retry。

Part 5

生命周期终点——软删除是"一整个家庭"一起消失

root Job + 它所有的 internal child 被当作一个不可拆分的单位处理软删除，前提是这个家庭已经完全"定型"。

只有同时满足才允许软删除： root 处于 succeeded/failed，且没有 active attempt callback 没配置，或终态 callback 已 delivered/skipped/dead_letter 所有 child 都没有未终态或仍持有 active attempt 的记录 软删除同一事务做两件事： job_aggregates：root + 所有 child 的 deleted_at/deleted_reason 一起写 job_submission_keys：root 的幂等键一起标记删除（释放 client_request_id）

job_execution_attempts / dispatch_outbox / callback_outbox / job_audit_events 都不单独维护删除状态，是否可见完全跟随关联 Job 的删除状态——审计链路永远完整，删除只影响查询视图。恢复（restore）按整个家庭恢复，并检查 caller_id + client_request_id 是否已被新提交的 Job 占用，占用了就拒绝，不会静默覆盖。

Part 6

配置到底分几层？

配置看起来乱，是因为分布在三个完全不同的层次，混着读才觉得杂乱；分开看，每一层只回答一个问题。

1

.env 里真正暴露给你调的主控项

MODEL_CALL_TIMEOUT_SECONDS 一次 AI 调用最多等多久 · MAX_ACTIVE_JOBS 系统同时能接多少活跃 Job · CALLBACK_TIMEOUT_SECONDS 一次 callback 请求最多等多久
（CALLBACK_SIGNING_SECRET 是必填密钥，不是策略参数）

2

job_type 自己在代码里声明的策略

不进 .env，因为每个业务不一样：retry_policy（业务失败要不要重试）、timeout_seconds（这个 job_type 单次执行超时上限）

3

内部派生值和固定常量

既不进 .env，也不由某个 job_type 决定：worker soft/hard timeout、stale running 阈值（从第一层派生），dispatch/callback outbox 的重试次数与退避策略（代码常量）

为什么第三层要派生，不直接暴露成配置？

因为这几个值之间有硬性的先后顺序要求，各自独立配置很容易配出"worker 还没跑完，recovery 就已经把它当成 stale 抢救"这种自相矛盾的组合。以默认值 MODEL_CALL_TIMEOUT_SECONDS=300s 为例：

第一层之外的旧键（JOB_MAX_EXECUTION_ATTEMPTS、JOB_ORPHAN_TIMEOUT_SECONDS、CALLBACK_MAX_DELIVERY_ATTEMPTS 等）写进 .env 会直接 fail-fast——不是"写了没用"，是"写了直接报错启动不了"，逼着改配置的人去改对层次。

Part 7

现在还没做到的事

骨架是对的：四本账分离、attempt lease 保护写入、恢复循环补缺口、root/child lineage 有数据库约束、软删除不动物理数据。但按"多租户、高并发、长任务、真金白银计费"的生产标准，还有明确知道、还没关闭的缺口：

  • caller 身份靠请求头自报，不是从凭证派生，多租户下能被伪造
  • MAX_ACTIVE_JOBS 并发闸门锁窗口偏窄，理论上能被并发投递击穿
  • dispatch dead-letter 收敛缺口（见 Part 3）
  • 长任务执行期间没有独立心跳续约线程，只靠进度点顺带续约

完整清单、风险分级和验收标准见 docs/plans/job-kernel-reliability-review.md——本文只负责"骨架讲得通"，硬不硬化是另一个独立决策。

附

高频问题

execution attempt retry、dispatch publish retry、callback delivery retry，到底怎么分？
看失败发生在谁的动作上：worker 执行本身失败 → execution retry；worker 根本还没收到通知 → dispatch retry；调用方没收到终态通知 → callback retry。三者互不消耗对方次数，一次 execution attempt 里可能发生好几次 dispatch retry。
worker 进程直接崩溃了会怎样？
持有的 attempt lease 会在 job_stale_running_seconds 之后过期，Recovery 下一轮扫描会判定这个 attempt 失败，再走一遍 Part 2 的重试判断——不会一直卡在 running，但要等 lease 过期那一刻，不是立刻发现。
同一个 attempt 会不会被两个 worker 同时执行？
不会。claim_attempt_for_execution 要求 Job.active_attempt_id 精确匹配这个 attempt 且状态为 pending，抢到之后其他 worker 的 claim 一律落空；即使 Taskiq 重复投递同一条消息，第二次 claim 也会因状态已是 running 而拿不到。
为什么 business_execution 默认 max_attempts=1，失败了不会自动重跑？
要不要重跑取决于这次失败有没有产生外部副作用（模型已计费、OSS 已写入一半），这个判断只有具体 job_type 知道，所以默认最保守：失败一次就是失败，除非该 job_type 自己声明了对哪些错误码放宽。
软删除之后数据还在吗？
在。软删除只写 deleted_at/deleted_reason，不删行；attempts/dispatch_outbox/callback_outbox/audit_events 完全不受影响，只是普通查询和排障命令默认看不到，需要走 ./scripts/jobs.sh deleted-* 专门查看。
workflow 的 internal child 能被外部直接提交或查询到吗？
不能。visibility=internal 的 job_type 在任何环境下都拒绝外部直接提交；child Job 也没有独立的对外查询入口，调用方只能查 root Job。
