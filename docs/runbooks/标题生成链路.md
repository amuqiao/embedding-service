# 标题图生成链路排障手册

本文用于定位 `poster_title_image` 从接单到透明标题图产物返回的链路问题，重点解释 Prompt 模板加载、服务端内部 Prompt 拼接、标题换行合同、workflow 子节点和结果返回边界。

本文面向联调、排障和维护人员。完整 HTTP 字段、状态、错误和 Callback 合同以 [`../api/poster-title-image-delivery-api.md`](../api/poster-title-image-delivery-api.md) 为准；本文不重复维护完整接口表。

如果目标是实际创建一次真实 `poster_title_image` Job、上传参考图、等待终态、查询 billing 或下载输出图，先看 [`poster-title-image 真实流程本地验证.md`](poster-title-image%20真实流程本地验证.md)。本文只负责真实 Job 已进入链路后的阶段定位和证据解释。

## 文档职责

本文负责：

- 建立 `poster_title_image` 从 root Job 到内部 child Job 的链路模型。
- 说明 `style_probe`、`generate_item`、`join` 三类内部节点分别排查什么。
- 说明公开 Prompt 模板和服务端内部 Prompt 拼接的边界。
- 给出常见现象到排查阶段的定位顺序。

本文不负责：

- 不维护完整 API 字段表、Callback 签名、费用字段和响应样例；这些以 [`../api/poster-title-image-delivery-api.md`](../api/poster-title-image-delivery-api.md) 为准。
- 不复制 Prompt 全文；默认 Prompt 事实源是 [`../../app/jobs/types/poster_title_image/prompts.yaml`](../../app/jobs/types/poster_title_image/prompts.yaml)。
- 不复制 Pydantic schema 全字段；请求和结果 schema 事实源是 [`../../app/schemas/jobs.py`](../../app/schemas/jobs.py)。
- 不重写通用 Job 查询方法；通用查询顺序见 [`jobs使用与排障手册.md`](job/jobs使用与排障手册.md)。
- 不维护 `real-flow.sh` 执行步骤；真实流程验证见 [`poster-title-image 真实流程本地验证.md`](poster-title-image%20真实流程本地验证.md)。

## 先理解这件事

标题图生成链路里有 4 个容易混淆的对象：

| 对象 | 谁控制 | 作用 |
|---|---|---|
| `style_probe` | 服务默认模板，可被 item 覆盖 | 从参考标题图提取可复用字形风格 |
| `additional_prompt` | 服务默认模板，可被 item 覆盖 | 补充标题图质量、背景和风格要求 |
| `layout_rules` | 服务默认模板，可被 item 覆盖 | 只表达视觉排版偏好，不控制换行 |
| `title_text` | 调用方请求字段 | 唯一调用方硬分行来源，LF `\n` 的位置就是硬分行位置 |

调用方通过 `GET /prompt-templates` 能看到和覆盖的仍只有 3 段 Prompt 模板：

```text
style_probe
additional_prompt
layout_rules
```

换行规则不放在这 3 段返回模板里。服务端会在生成图片前，根据 `items[].title_text` 动态派生内部高优先级换行片段，并拼入最终发给模型的 Prompt。

## 总体流程

```text
调用方 POST /jobs
  |
  | job_type = poster_title_image
  | items[].title_text
  | items[].reference_image
  | items[].prompt_overrides 可选
  v
请求校验
  |
  | 校验 title_text 的 LF、空行和最大硬分行数
  | 校验 prompt_overrides 不能控制换行或换行位置
  v
workflow root
  |
  | 拆出 style_probe child
  | 拆出 generate_item child
  | 最后 join 汇总
  v
style_probe
  |
  | 读取参考图
  | 用 style_probe Prompt 提取字形风格描述
  v
generate_item
  |
  | 加载默认 Prompt 模板
  | 合并 item 覆盖
  | 根据 title_text 派生 line_break_rules
  | 拼最终内部 Prompt
  | 调用生图模型
  | 绿幕后处理为透明 PNG
  | 写入 OSS
  v
join
  |
  | 汇总每个 item 的图片对象
  v
Job 查询结果 / Callback
```

## 先看哪个状态

排查时先区分 HTTP 请求是否成功和 Job 是否成功：

```text
HTTP 200
  只表示服务已接收或成功返回查询结果
  不表示标题图已经生成成功

job_status
  才是任务业务状态
```

常见状态入口：

| 状态 | 先看什么 |
|---|---|
| `queued` | 看 root Job 是否已被 dispatcher/worker 领取；再看是否有 child Job 生成 |
| `running` | 看 child Job 进度；当前 `running` 可返回已成功 item 的 `job_result` 增量快照 |
| `succeeded` | 看 `job_result.items[]`、每个 item 的 `images[]` 和 OSS URL Ref |
| `failed` | 先看 `job_error`；如果失败前已有 item 成功，`failed` 也可带成功 item 的增量快照 |

## 请求数据进入服务端

调用方创建任务的完整字段合同见 [`../api/poster-title-image-delivery-api.md`](../api/poster-title-image-delivery-api.md)。排查标题链路时，先关注 `job_params.items[]` 中这些字段：

| 字段 | 排查意义 |
|---|---|
| `item_id` | 关联请求 item、workflow item 节点和返回结果 |
| `language` | 决定标题语种和最终 Prompt 中的语言提示 |
| `title_text` | 标题正文，也是唯一调用方硬分行来源 |
| `reference_image` | style probe 和生图参考图输入 |
| `prompt_overrides` | 可覆盖风格、附加视觉偏好和视觉排版偏好，但不能控制换行 |

### JSON 里的 `\n` 如何解析

调用方在 HTTP JSON 请求体中应使用 JSON 字符串转义序列 `\n`：

```json
{
  "title_text": "主标题\n副标题"
}
```

服务端 JSON parser 解析后，应用代码拿到的是一个真实 LF 换行字符：

```text
主标题
副标题
```

不要把字面量反斜杠加 `n` 当作业务值传入：

```json
{
  "title_text": "主标题\\n副标题"
}
```

上面这种 JSON 解析后，服务端拿到的是可见字符 `\n`，不是 LF 换行字符，因此不会被当作硬换行位置。

如果调用方使用语言对象并交给 JSON 序列化器处理，通常只需要在语言字符串中表达换行，由序列化器输出合法 JSON。不要手写非法多行 JSON 字符串，也不要使用 HTML `<br />`。

## 请求校验

`PosterTitleImageItemParams` 会校验 `title_text`：

```text
只允许 LF \n 作为换行字符
不支持 CRLF
不支持 HTML <br />
不允许空行
当前默认最多 2 行，也就是最多 1 个 LF
```

`prompt_overrides.additional_prompt` 和 `prompt_overrides.layout_rules` 也会被校验：它们只能补充视觉或风格偏好，不能定义、添加、删除、合并、拆分、重排或调整 `title_text` 的硬分行位置。

这条边界很重要：调用方想指定硬换行，只改 `title_text`；不要在 `layout_rules` 或 `additional_prompt` 里写“单行”“两行”“在某个词后换行”等指令。

## Prompt 模板加载

标题图任务的默认模板来自 [`../../app/jobs/types/poster_title_image/prompts.yaml`](../../app/jobs/types/poster_title_image/prompts.yaml)。

当前模板包含 3 个块：

| Prompt block | 用途 |
|---|---|
| `style_probe` | 分析参考标题图，只提取字形本身的风格 |
| `additional_prompt` | 要求输出高质量标题文字、绿幕背景和可后处理图层 |
| `layout_rules` | 标题区视觉排版偏好，例如大、居中、安全边距、不裁切 |

服务端会读取这 3 个默认块。生成单个 item 时，内部 Prompt 组装逻辑会先判断 item 是否传了 `prompt_overrides`：

```text
layout_rules =
  item.prompt_overrides.layout_rules
  或默认 layout_rules

additional_prompt =
  item.prompt_overrides.additional_prompt
  或默认 additional_prompt
```

`style_probe` 的覆盖在风格探针阶段生效；`layout_rules` 和 `additional_prompt` 在标题图生成阶段生效。

## 服务端内部 Prompt 拼接

最终发给生图模型的 Prompt 不是直接等于 3 段返回模板，而是由服务端内部模板 `PROMPT_TEMPLATE` 拼出来。

简化结构如下：

```text
Generate a high-resolution standalone title graphic.

== STYLE ==
{style_desc}

== TEXT ==
Exact text to render: {title_text}
Language: {language}
Reproduce every character exactly...

== LAYOUT ==
Placement context:
{layout_rules}

Line break contract:
{line_break_rules}

Scale:
Render the title LARGE...

== TECHNICAL REQUIREMENTS ==
{background and image requirements}
{additional_prompt}
```

其中：

| 变量 | 来源 |
|---|---|
| `style_desc` | `style_probe` 子任务从参考图提取 |
| `title_text` | 调用方请求字段 |
| `language` | `items[].language` 和服务端语种目录 |
| `layout_rules` | 默认模板或 item 覆盖 |
| `line_break_rules` | 服务端根据 `title_text` 动态派生 |
| `additional_prompt` | 默认模板或 item 覆盖 |

`line_break_rules` 是服务端内部片段，不通过 `GET /prompt-templates` 返回给调用方。

## 换行规则如何派生

服务端使用 `title_text.split("\n")` 识别真实 LF。

### 没有 LF

```text
title_text = "这是一个很长的标题"
```

服务端派生的内部规则含义是：

```text
调用方没有指定硬换行。
模型可在标题区域需要时自然自动换行。
最大行数仍受服务端限制。
该规则优先于 layout_rules 或 prompt_overrides 中的冲突偏好。
```

这里的“可自动换行”不是承诺一定拆成多行，而是允许模型在画布、标题区域和可读性需要时换行。

### 有 LF

```text
title_text = "主标题\n副标题"
```

服务端派生的内部规则含义是：

```text
调用方指定了硬换行。
LF 字符同时决定行数和硬分行位置。
第 1 行：主标题
第 2 行：副标题
模型必须保持这些行，不得合并、重排、增加额外换行或继续拆分某一行。
该规则优先于 layout_rules 或 prompt_overrides 中的冲突偏好。
```

也就是说，`主标题\n副标题` 不是“建议模型换成两行”，而是“第一行到 `主标题` 结束，第二行从 `副标题` 开始”。

## Workflow 子节点定位

`poster_title_image` root Job 本身不直接调用模型；它会编排内部 child Job。

内部节点类型：

| 节点 | job type | 作用 |
|---|---|---|
| `probe.<index>` | `poster_title_image_style_probe` | 对参考标题图做风格探针 |
| `item.<safe item_id>.<digest>` | `poster_title_image_generate_item` | 对单个 item 生成标题图 |
| `join` | `poster_title_image_join` | 汇总所有 item 结果 |

style probe 会按 `reference_image.sha256 + effective style_probe prompt` 复用，所以 probe 节点数不一定等于 item 数。多个 item 使用同一张参考图和同一份有效 `style_probe` Prompt 时，可以共享一个 `probe.<index>`。

item 节点依赖 probe 节点。排查单个 item 时，先找对应 `item.<safe item_id>.<digest>`，再看它依赖的 `probe.<index>` 是否成功。

## Style Probe 阶段

`style_probe` 子任务会读取参考标题图，并调用文本/多模态模型生成 `style_desc`。

这个阶段只提取字形风格，例如：

```text
笔画粗细
材质纹理
颜色和描边
字体结构
字形内部光照和质感
```

它不应把背景、牌匾、边框、外发光、烟雾、阴影或其它非文字载体吸收到风格描述里。

## 标题图生成阶段

`generate_item` 子任务会：

```text
读取 reference_image
读取 style_probe 结果 style_desc
读取默认 Prompt blocks
合并 item prompt_overrides
根据 title_text 派生 line_break_rules
拼出最终内部 Prompt
调用生图模型
```

生图模型返回绿幕背景标题图后，服务端会做后处理：

```text
绿幕背景图片
  -> remove green background
  -> transparent PNG title layer
  -> write to OSS
  -> build OSS URL Ref
```

当前业务输出目标是透明 PNG 标题图层；绿幕背景是服务端内部后处理路径，不是对调用方暴露的输出形态。

单个 item 的成功条件包括：

- 每次候选图生成都成功。
- provider 单次必须返回且只返回 1 张图。
- 绿幕后处理成功得到透明 PNG。
- OSS 写入成功并生成 URL Ref。
- 返回图片数量等于 `model_options.draw_count`。

只要某个候选图失败，或 provider 单次返回图片数量不是 1，该 item 就不能标记为 `succeeded`。

## OSS 写入与产物检查

输出对象 key 的业务段形态是：

```text
poster-title/{root_job_id}/{item_id}/title-layer.png
poster-title/{root_job_id}/{item_id}/title-layer-2.png
```

如果配置了 output target prefix，最终 OSS key 会带上该 prefix。

产物检查重点：

| 项 | 期望 |
|---|---|
| `content_type` | `image/png` |
| `sha256` | 输出 PNG 原始内容 hash |
| `public_url` / `internal_url` | 指向同一个 OSS object |
| 图片语义 | 透明背景标题图层，不是合成海报 |

## 结果汇总与返回

每个成功 item 会生成一个或多个图片对象，数量由 `model_options.draw_count` 决定。完整响应结构以 [`../api/poster-title-image-delivery-api.md`](../api/poster-title-image-delivery-api.md) 为准；排障时只需要确认这些事实：

- `join` 子任务会汇总所有 item 结果，形成 root Job 的 `job_result`。
- 调用方通过 Job 查询或终态 Callback 获取结果。
- 服务端不会把最终内部 Prompt 返回给调用方。
- 调用方拿到的是 Job 状态、费用摘要和 OSS URL Ref 图片结果。

`batch_summary` 和 `items[]` 的关系：

- `succeeded` 终态：所有请求 item 都有成功结果。
- `running` 快照：`items[]` 可只包含已成功 item。
- `failed` 快照：如果失败前已有 item 成功，`items[]` 可包含成功子集；失败原因仍看 `job_error`。
- 全部 item 失败时，root Job 进入 `failed`。

## Callback 与费用旁路

Callback 和费用不是标题图生成成功的主判定依据：

- Callback 投递失败不会把已成功 Job 改成失败。
- `job.cost` 是 Job 级费用快照，不是 provider 调用明细。
- 费用细节以 billing 查询入口为准。

排查顺序建议：先确认 `job_status` 和 `job_result`，再看 Callback 投递摘要和费用状态。

## 常见现象到排查顺序

| 现象 | 优先排查 |
|---|---|
| 创建任务返回 `INVALID_INPUT` | 看 `title_text`、OSS URL Ref、语种、模型、`draw_count` 和 prompt override 是否触发 schema 校验 |
| Job 一直 `queued` | 看 worker 是否运行、root Job 是否被 dispatch、是否生成 child Job |
| Job `running` 但只有部分图片 | 看对应 item child 是否仍在执行或失败；`running` 快照只保证返回已成功 item |
| Job `failed` 但 `job_result.items[]` 有图片 | 这是部分成功快照；失败原因看 `job_error` 和失败 child |
| 所有 item 失败 | 看 `POSTER_TITLE_IMAGE_ALL_ITEMS_FAILED` 或 child 的模型/OSS/后处理错误 |
| 有 OSS 写入日志但查询结果没有图片 | 看 `join` 是否成功、item child 返回图片数量是否等于 `draw_count` |
| Callback 失败但 Job `succeeded` | 看 Callback delivery 摘要；不要按 Callback 投递结果判断标题图生成失败 |
| 图片文字换行不符合预期 | 先看 `title_text` 里是否是真实 LF；再确认 `layout_rules` 或 `additional_prompt` 没有试图控制换行 |

## 维护检查清单

修改标题生成链路时，按下面顺序检查：

1. 改 `title_text` 换行规则时，同步检查 `app/schemas/jobs.py`、服务端换行合同派生逻辑、API 文档和测试。
2. 改公开 Prompt block 时，确认 `layout_rules.default_content` 不重新暴露换行控制词，例如 `LF`、`line break`、`title_text` 或 `Maximum lines`。
3. 改 Prompt 拼接结构时，确认内部换行合同仍高于 `layout_rules` 和 `prompt_overrides`。
4. 改输出格式或后处理时，确认 API 文档仍只承诺透明 PNG 标题图层，不泄漏内部绿幕实现为调用方合同。
5. 改结果结构时，同步 `docs/api/poster-title-image-delivery-api.md` 和相关 contract tests。

只改 Prompt 文案、`title_text` 换行合同或 schema 时，建议最小验证：

```bash
uv run pytest tests/test_poster_title_image.py tests/test_contract.py
./scripts/verify.sh check
```

修改 Job 内部执行、workflow 编排、对象存储写入、后处理或结果汇总时，还应运行模板 Job workflow 验证：

```bash
./scripts/run.sh up dev
./scripts/verify.sh workflow-smoke
./scripts/run.sh down dev
```
