# 独立服务抽取与流程说明

本文说明 `cms-novel-localize` 作为小说本地化 AI 能力层时，如何承接业务后端的 3 类 Job，并在服务内部完成自动分块、Celery workflow、结果合并和产物写入。

## 核心结论

本服务是无状态的 AI 能力服务。这里的“无状态”指 API 层不维护用户登录态、不理解业务项目归属、不保存前端页面状态；服务内部仍然保存 AI Job 状态、work item 状态和执行结果，用于异步执行、状态查询和 callback。

对业务后端来说，小说本地化流程是 3 个业务步骤：

```text
step1 本地化
step2 本地化校验
step3 英文翻译
```

对本服务来说，它们是 3 类独立 Job：

```text
novel_localization.step1_localize
novel_localization.step2_review
novel_localization.step3_translate
```

业务后端负责决定什么时候调用哪个 Job，并在每次 `POST /jobs` 时传入完整输入、完整 `prompt.blocks`、输出位置和 callback。业务后端不需要知道该 Job 内部是否分 chunk、是否生成映射表、是否使用 Celery canvas、如何 merge。

## 服务职责

本服务负责：

```text
返回模型列表
返回默认 Prompt 模板
接收本次 Job 的 input / prompt / output / callback
校验 job_type、model_id、prompt.blocks、input hash
读取 oss_object 输入
自动决定 p1 / p5 执行策略
创建内部 work items
使用 Celery task / chain / chord 执行 Job 内部 workflow
合并分块结果
将本地化正文和英文翻译写入对象存储
返回 Job 状态、artifacts、signals
向业务后端发送 callback
```

本服务不负责：

```text
用户系统
业务项目列表
业务项目详情
用户 PromptConfig 保存
业务步骤状态机
上一步结果长期保存
用户是否接受 optimization_prompt
是否重跑 step1
前端页面状态
```

这个边界来自：

```text
docs/小说本地化AI能力层接口文档v3.md
docs/小说本地化AI能力层_后端对接接口文档.md
```

## 对后端的调用模型

业务后端只面向稳定接口：

```text
GET  /health
GET  /api/v1/novel-localization-ai/models
GET  /api/v1/novel-localization-ai/prompt-templates
POST /api/v1/novel-localization-ai/jobs
GET  /api/v1/novel-localization-ai/jobs/{job_id}
```

一次 Job 请求必须包含：

```text
job_type
model_id
input
output
callback
prompt.blocks
metadata
```

首版不暴露：

```text
options
execution_mode
runtime_prompt_blocks
```

原因是执行策略属于服务内部能力。业务后端不需要选择 `p1`、`p5`、chunk size 或 canvas 拓扑。

## Job 内部执行模型

当前实现已经把 `jobs.process` 从单次模型调用升级为 workflow dispatcher。

主路径如下：

```text
POST /jobs
  |
  v
写入 ai_jobs
  |
  v
Celery jobs.process
  |
  v
读取 input
  |
  v
Job Planner
  |
  |-- p1: whole work item
  |
  |-- p5: memory / chunk / merge / scan work items
  |
  v
写入 ai_job_work_items
  |
  v
Celery canvas
  |
  v
finalize job
  |
  v
写 artifacts / mark_succeeded / callback
```

外部仍然只看到一个 `job_id` 和一个 Job 状态。`ai_job_work_items` 是内部执行细节，用于记录 chunk、project memory、merge、scan 等工作单元。

## p1 与 p5

服务内部根据输入文本长度自动选择执行策略。

```text
p1
  单个 whole work item
  适合短文本

p5
  多个 work item
  适合长文本
  服务内部自动 split、fan-out、merge
```

当前配置项：

```text
NOVEL_LOCALIZATION_P1_MAX_CHARS=5000
NOVEL_LOCALIZATION_CHUNK_SIZE=4500
```

这些配置只影响服务内部执行策略，不进入接口契约。

## 三类 Job 的内部流程

### step1 本地化

短文本：

```text
whole localize
  |
  v
localized_text -> localized.txt
notes
```

长文本：

```text
memory work item
  |
  v
chunk localize work items
  |
  v
merge
  |
  v
localized_text -> localized.txt
notes
project_memory
```

`project_memory` 参考 demo 项目中的 Trunk 1 / mapping table 思路，但面向独立能力层做了边界调整。服务不会把它挂到业务项目上，而是作为 step1 的 result artifact 返回给业务后端。业务后端如果希望 step2 / step3 使用同一份项目记忆，需要在后续 Job 的 `prompt.blocks.work_note` 中显式传回：

```text
<project_memory>
{...step1 返回的 project_memory JSON...}
</project_memory>
```

这样每个 Job 请求仍然是完整输入，本服务不需要知道业务项目 ID，也不会隐式读取“上一步项目状态”。

### step2 本地化校验

短文本：

```text
whole review
  |
  v
review_summary
optimization_prompt
signals.passed
```

长文本：

```text
chunk review work items
  |
  v
merge review
  |
  v
review_summary
optimization_prompt
signals.passed
```

`status=succeeded` 只表示校验 Job 执行成功，不表示业务校验通过。业务是否通过看 `signals.passed`。

如果请求的 `work_note` 中包含 `<project_memory>...</project_memory>`，每个校验 chunk 会自动注入这份已冻结项目记忆。

### step3 英文翻译

短文本：

```text
whole translate
  |
  v
translated_text -> translated.txt
```

长文本：

```text
chunk translate work items
  |
  v
merge translation
  |
  v
scan
  |
  v
translated_text -> translated.txt
```

如果请求的 `work_note` 中包含 `<project_memory>...</project_memory>`，每个翻译 chunk 和最终 `scan` 都会注入这份已冻结项目记忆。`scan` 只做合并后的一致性扫描和轻量修正，不负责重写业务风格。

## 与 demo 项目的关系

demo 项目 `title` 中已经存在小说本地化基础能力，尤其是：

```text
backend/app/pipeline/workflows/novel_loc_workflow.py
backend/app/pipeline/workers/novel_loc_worker.py
backend/app/services/novel_loc_service.py
backend/app/infrastructure/novel_loc/prompts.yaml
```

独立服务复用的是 demo 的执行思想，而不是 demo 的业务项目模型。

| 对象 | demo 项目 | 当前独立服务 |
|---|---|---|
| 对外单位 | project / step | job |
| 调用方 | demo 内部后端和前端 | 外部业务后端 |
| 项目状态 | demo 自己管理 | 业务后端管理 |
| 输入来源 | project / step 上下文 | POST /jobs 的 input |
| Prompt 来源 | demo 内部配置 | POST /jobs 的 prompt.blocks |
| 内部执行 | workflow / canvas | Job 内部 workflow / canvas |
| 产物归属 | demo 项目 step | OSS artifacts |

关键区别是：独立服务不能通过 `project_id` 查原文，也不能通过 `step_code` 查上游结果。所有输入都必须来自本次请求的 `source.oss`。

## Prompt 与 work_note

接口文档要求每个 `job_type` 都有 3 个 prompt block：

```text
system
user
work_note
```

业务后端从 `GET /prompt-templates` 读取默认值，并保存自己的 PromptConfig。用户修改后的 PromptConfig 也由业务后端保存。

本服务在执行时只使用 `POST /jobs` 传入的最终 `prompt.blocks`。服务不会自动补默认 Prompt，也不会替业务后端把 `optimization_prompt` 写回 `work_note`。

重跑 step1 时，业务后端应把 step2 返回的 `optimization_prompt` 合并到 `work_note.content` 或 `user.content`，然后重新创建 `novel_localization.step1_localize` Job。

## 后续演进

当前已经形成真正的独立能力服务内核，但仍有后续增强空间：

```text
将默认 Prompt 从 Python 常量迁移为 YAML 或数据库资产
把 mapping 输出解析为结构化 JSON
增强 chunk merge 质量
增加 work item 查询或内部诊断接口
接入真实 OSS
完善 callback 死信和投递审计
补充长文本失败重试策略
```

这些都是服务内部演进，不应破坏后端对 `POST /jobs` 和 `GET /jobs/{job_id}` 的调用契约。
