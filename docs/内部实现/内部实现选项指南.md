# 内部实现选项指南 — AI 能力层架构

## 文档目的

本文档说明小说本地化 AI 能力层**如何在内部实现 Job 执行**，包括不同的执行策略、并行处理、中间扫描等。这些都是**对后端完全透明的**实现细节。

---

## 核心原则

- ✅ **后端只关心 API 契约**：输入格式、输出格式、错误码
- ✅ **AI 层内部实现自主选择**：单步/分块、Canvas/直接链、有无扫描
- ✅ **对后端完全隐形**：后端无需知道 Job 内部如何执行

---

## 执行策略选择

### 策略 1：单步执行模式（P1）

#### 触发条件
- 输入文本字符数 < 5000（去空格后计算）

#### 执行流程

```
输入文本
    ↓
检测字符数 < 5000
    ↓
创建单个 Celery task（whole）
    ↓
单次 LLM 调用
    ↓
直接返回结果
```

#### 实现细节
- **Work Item 类型**：1 个 `whole` work item（chunk_index=0）
- **Celery 拓扑**：无 Canvas，直接 `app.task.delay()`
- **LLM 调用**：1 次
- **Merge 步骤**：无，直接返回

#### 代码位置
- `app/services/job_planner.py:_build_plan_p1()`
- `app/tasks/jobs.py:execute_work_item_task()` 处理 kind='whole'

#### 后端感知
- ✅ 应该能看到：Job 从 queued → running → succeeded
- ✅ 应该能看到：result 中有 artifacts（大文本在 OSS 中）
- ❌ 不应该假设：Job 会分块、会有中间扫描、progress 会经过 30%/60% 等特定值

---

### 策略 2：分块执行模式（P5）

#### 触发条件
- 输入文本字符数 >= 5000（去空格后计算）

#### 执行流程

**Step 1（本地化）为例**：

```
输入文本（≥5000 字符）
    ↓
自动分块（按段落、按字符数限制）
    ↓
生成 chunk_registry = [
    { chunk_index: 1, text: "...", char_count: 4500 },
    { chunk_index: 2, text: "...", char_count: 3200 },
    ...
]
    ↓
创建 WorkItems：
  - memory:0（仅 step1）→ 生成项目记忆表（映射表）
  - chunk:1, chunk:2, ... → 并行处理各块
  - merge:N+1 → 汇总结果
  - scan:N+2（仅 step3）→ 一致性扫描
    ↓
执行 Celery Canvas：
  chain(
    execute(memory:0),  # 串行：先生成映射表
    chord(              # 并行：所有块
      [execute(chunk:1), execute(chunk:2), ...],
      execute(merge)    # 汇合：合并所有块
    )
  )
    ↓
Merge 将各块结果按 chunk_index 排序后拼接
    ↓
返回合并后的结果
```

#### 实现细节

| 组件 | 说明 |
|---|---|
| **分块算法** | 段落为单位（`\n\n` 分隔），累积字符数至 ~4500，不切段落 |
| **Work Items** | memory(0) + chunk(1..N) + merge(N+1) + 可选 scan(N+2) |
| **Canvas 拓扑** | chain → cord → group 组合，memory 串行后 chunks 并行 |
| **并行度** | 由 Celery worker 数决定，通常 2-8 并发 |
| **Merge 逻辑** | 按 chunk_index asc 排序，用 `\n\n` 拼接 artifacts |
| **Memory（映射表）** | step1 的 memory task 调用 LLM 生成人物/地名/文化规则 |

#### 代码位置
- `app/services/job_planner.py:_build_plan_p5()`
- `app/services/job_workflow.py:build_canvas()`
- `app/tasks/jobs.py:execute_work_item_task()` 处理 kind='memory'/'chunk'/'merge'
- `app/services/job_workflow.py:merge_work_items()`

#### 后端感知
- ✅ 应该能看到：progress_percent 从 0% → 10% → 30% → 90% → 100%
- ✅ 应该能看到：result.signals 中 project_memory_frozen=true（step1）
- ❌ 不应该假设：progress 必定经过 30%，或并行度是多少

---

### 策略 3：扫描执行模式（仅 step3）

#### 触发条件
- Job type = step3_translate
- 使用 P5 分块模式

#### 额外流程

```
chunks 并行翻译完成
    ↓
merge 汇总各块英文翻译
    ↓
创建 scan:N+2 work item
    ↓
调用 LLM 进行一致性扫描：
  - 检查人名是否一致（如 "Shen Yan" vs "沈砚"）
  - 检查术语是否一致（如 "元婴" 统一翻译）
  - 检查分块边界是否衔接
    ↓
扫描 task 返回修订后的英文文本
    ↓
merge task 使用扫描结果作为最终 translated_text
```

#### 实现细节

| 组件 | 说明 |
|---|---|
| **何时扫描** | step3 + P5 模式 + chunk 数 > 1 时自动触发 |
| **扫描 Prompt** | 独立的轻量 prompt，注入 project_memory（冻结的映射表） |
| **扫描结果** | 返回修订后的完整英文文本 |
| **Canvas 拓扫** | chord 结构：chunks 并行 → scan 串行 → finalize |

#### 代码位置
- `app/services/job_workflow.py:_first_scan_payload()`
- `app/services/job_workflow.py:merge_work_items()` step3 分支
- `app/services/job_workflow.py:execute_work_item()` kind='scan' 分支

#### 后端感知
- ✅ 应该能看到：result.signals.merge_scan_applied=true
- ❌ 不应该假设：英文文本一定被修改，或扫描逻辑是什么

## 参数配置

### 可配置项（在 config.py）

```python
# 分块阈值
NOVEL_LOCALIZATION_P1_MAX_CHARS = 5000  # < 此值用 P1

# 分块大小
NOVEL_LOCALIZATION_CHUNK_SIZE = 4500  # 每块目标字符数

# Celery 并行度（取决于 worker 数）
CELERY_CONCURRENCY = 4  # app.conf.worker_concurrency

# 超时设置
JOB_QUEUE_TIMEOUT_SECONDS = 600  # 排队超时
JOB_EXECUTION_TIMEOUT_SECONDS = 1800  # 执行超时
```

### 这些配置是否会改变后端 API？

❌ **否**。这些是内部优化参数，后端无需修改。

## Project Memory（映射表）的生命周期

### 何时生成
- 仅在 step1_localize 的 P5 模式下，执行 memory task

### 内容
```json
{
  "characters": [
    { "cn_name": "沈砚", "en_name": "Shen Yan", "title": "protagonist" },
    ...
  ],
  "places": [
    { "cn_name": "青牛镇", "en_name": "Green Ox Town", ... },
    ...
  ],
  "glossary": [...],
  "style_guide": "保留原名拼音，避免过度美国化",
  "cultural_rules": [...],
  "continuity_notes": [...]
}
```

### 如何注入到后续块
1. Memory task 完成后，结果保存在 work_items[kind='memory'].result_payload
2. Chunk tasks 执行时，读取 memory task 的结果
3. 在 system prompt 前置注入：`append_context_to_prompt(memory, system_prompt)`
4. LLM 在处理每块时都遵守映射表

### 何时冻结
- 在 merge step1 的结果时，将 memory 写入 result.artifacts（如有）

### 后端如何使用
- 当 step1 返回 project_memory artifact 时，业务后端可以：
  - 保存到自己的数据库（可选）
  - 在 step2/step3 的 work_note 中注入（可选）
  - 用于人工审核（可选）

## Work Items 的生命周期

### 存储位置
- 表：`ai_job_work_items`
- 包含：job_id, name, kind, chunk_index, status, celery_task_id, input_payload, result_payload, error_payload

### 生命周期
```
创建（status=queued）
    ↓
执行中（status=running）
    ↓
成功（status=succeeded, result_payload=<json>）
或失败（status=failed, error_payload=<json>）
```

### 后端是否应该查询 work_items？

❌ **不应该**。

- work_items 是内部实现细节
- 后端仅应查询 jobs 表
- 如需排障，才读 work_items（通过内部日志，不通过 API）

## 错误处理和重试

### 单个 work item 失败
- 若某个 chunk task 失败，整个 Job 标记为 failed
- Error 返回给后端：`{ code: "MODEL_CALL_FAILED", message: "...", details: {...} }`

### Celery 任务重试
- 默认 CELERY_MAX_RETRIES = 0（不重试）
- 若需重试，由业务后端判断：重新 POST /jobs 创建新 Job（client_request_id 去重）

### Callback 重试
- Callback 发送失败时重试 3 次（10s/30s/60s）
- Callback 重试是**通知层**的容错，不影响 Job 本身的状态

## 监控和日志

### 后端可观测的指标

```python
# 从 GET /jobs/{job_id} 响应
job = {
    'job_id': '...',
    'status': 'running',
    'progress_percent': 30,
    'progress_text': '正在执行 chunk',
    'created_at': '2026-06-07T...',
    'started_at': '2026-06-07T...',
    'finished_at': None  # 未完成
}
```

### 后端不应该依赖的指标

- progress_text 的具体文案（可能改变）
- job.started_at - job.created_at 的精确值（波动）
- Work Items 的中间状态（内部实现）
- Celery task 数量或 IDs（内部实现）

## 扩展点

### 未来可能的改进

| 改进 | 影响 | API 破坏性 |
|---|---|---|
| 分块算法改进（如引入 NLP 分句） | 分块数/大小可能改变 | ❌ 无 |
| Canvas 从 Chord 改为 Group + Loop | 执行顺序可能改变 | ❌ 无 |
| 并行度动态调整 | 不同输入的并行度不同 | ❌ 无 |
| 增加中间扫描（step2） | 新增 progress 阶段 | ❌ 无 |
| 改进 LLM 调用（如缓存、batch） | 执行时间改变 | ❌ 无 |
| 支持其他 LLM 厂商 | ai_gateway 改变 | ❌ 无 |

所有这些改进都**不需要**后端改动 API 调用方式。

## 最佳实践

### 后端在设计时应该
✅ 依赖 5 个 API 接口的请求/响应格式  
✅ 依赖 result.artifacts[] 和 result.signals{}  
✅ 依赖 error.code 和错误码清单  
✅ 依赖 job_id、status、progress_percent  

### 后端在设计时不应该
❌ 硬编码 progress_text 值  
❌ 查询 work_items 表或假设其结构  
❌ 假设 Job 的执行顺序（并行无序）  
❌ 依赖 progress_percent 的具体阶段值（如必定 30%）  

---

## 总结

- **P1 模式**：小文本，单步执行，无分块
- **P5 模式**：大文本，分块并行，含 merge
- **扫描**：step3 额外的一致性检查
- **全部透明**：后端无需知道哪种模式，对 API 无影响
- **灵活迭代**：AI 层可随时改进执行策略，不破坏契约
