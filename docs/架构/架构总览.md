# AI Job 服务架构总览

本文说明当前 AI Job 服务的主干架构：调用方如何提交单个异步 Job，服务如何通过 Taskiq 投递执行尝试，`JobExecutor` 如何承载具体能力，结果和 Callback 如何交付，以及系统如何依赖 PostgreSQL 账本完成恢复与收敛。

## 文档职责

本文负责建立架构心智模型和模块边界，帮助新接入者理解“一个请求如何变成一个可恢复的 AI Job”。字段级接口合同见 [`../接口层/http-api-extension-standard.md`](../接口层/http-api-extension-standard.md)，新增 `job_type` 的标准步骤见 [`../接口层/job-type-extension-standard.md`](../接口层/job-type-extension-standard.md)，Taskiq 数据模型细节见 [`../设计文档/taskiq-job-model-design.md`](../设计文档/taskiq-job-model-design.md)。

本文不记录临时排查过程、生产平台发布流程、业务系统编排逻辑或具体 `job_type` 的业务参数。

## 一、核心心智模型

本服务是无状态 AI 能力层，不是业务流程系统。

```text
业务后端 / BFF
  ├─ 管理用户、项目、稿件、审核状态和业务步骤
  ├─ 决定何时创建、重试或放弃某个业务动作
  └─ 调用本服务创建单个 AI Job

AI Job Service
  ├─ 校验鉴权、公共 Job 外壳、job_type、job_params 和 Callback
  ├─ 按 job_type 找到 JobExecutor
  ├─ 归一化 job_params，并冻结 runtime snapshot
  ├─ 创建 queued Job 和第一个 JobAttempt
  ├─ 通过 Taskiq 发布 jobs.run_attempt(attempt_id)
  ├─ Worker 领取 attempt，推进 Job 到 running
  ├─ 调用 JobExecutor 执行自定义运行时或内置 LLM 文本运行时
  ├─ 校验 canonical result，投影 public result
  ├─ 按需把大产物写入对象存储
  ├─ 将 Job 收敛到 succeeded / failed
  └─ 通过 Callback outbox 投递终态通知
```

关键设计取舍：

- **单 Job 语义**：服务只理解一个 `job_type` 的一次执行，不编排调用方业务流程。
- **PostgreSQL 是状态权威**：Job、Attempt、Callback outbox 和事件账本都在数据库中；Taskiq 只负责异步投递和执行触发。
- **`JobExecutor` 是能力边界**：`job_type` 来自 executor registry；Prompt YAML 只服务模板发现和 LLM prompt 校验，不是 Job 类型注册表。
- **Attempt 隔离执行尝试**：Taskiq 消息只携带 `attempt_id`；Worker 必须先在数据库中 claim 当前 active attempt，claim 成功才有执行权。
- **整 Job 收敛**：执行失败、Worker 崩溃或租约过期时，由 recovery 基于 Attempt 账本重新发布或创建新 attempt，最终收敛到 `succeeded` 或 `failed`。
- **Callback + 轮询双通道**：Callback 是主动通知，`GET /jobs/{job_id}` 是查询和兜底通道；Callback 失败不改变 Job 终态。

## 二、服务边界

本服务负责：

- 受保护 API：模型列表、Prompt 模板、创建 Job、查询 Job。
- Job 幂等：同一 `caller_id + client_request_id` 在 24 小时内按请求指纹判断重复或冲突。
- 创建校验：`job_type` 是否已注册、`job_params` 是否符合 executor schema、模型是否可用、Callback URL 是否安全。
- 可选 Prompt 校验：当 `job_type` 存在 Prompt YAML 模板时，校验 runtime fields 中的 `prompt_payload` 与模板一致。
- Job 状态机：`queued -> running -> succeeded | failed`。
- Attempt 生命周期：创建、发布、领取、租约续期、成功、失败和重试。
- 内部执行：通过 `JobExecutor._execute()` 自定义运行时，或通过内置 LLM 文本运行时执行能力逻辑。
- 产物持久化：命中 executor `large_artifact_keys` 的大产物写入对象存储。
- Callback：终态后创建 outbox 记录并发送 `job.succeeded` 或 `job.failed`。
- 恢复与清理：recovery loop 处理待发布 attempt、租约过期 attempt、Callback 补偿和已收敛过期 Job 清理。

本服务不负责：

- 用户、权限、项目、稿件版本、人工审核和业务步骤编排。
- 判断某个业务 step 失败后是否重做前置 step。
- 生产部署平台、K8s、云平台 Secret、CI/CD 发布流水线。
- 长期保存业务结果；Job 默认 24 小时过期，清理只处理已终态且 Callback 已收敛的记录。
- 对外暴露 Attempt、Worker、Lease、Taskiq message id 或内部恢复账本。

## 四、API 表面

所有业务 API 使用统一前缀：

```text
/api/v1/ai-jobs
```

端点：

| 方法 | 路径 | 说明 | 鉴权 |
|------|------|------|------|
| `GET` | `/health` | 基础存活检查 | 否 |
| `GET` | `/healthz` | DB + Redis readiness 检查 | 否 |
| `GET` | `/models` | 返回当前可用模型 | 是 |
| `GET` | `/prompt-templates` | 返回 Prompt 模板发现信息 | 是 |
| `POST` | `/jobs` | 创建 AI Job | 是 |
| `GET` | `/jobs/{job_id}` | 查询 Job 状态和结果 | 是 |

除健康检查外，请求必须携带：

```http
Authorization: Bearer <SERVICE_API_KEY>
```

本地联调可通过 `DISABLE_HTTP_AUTH_HEADER=true` 跳过 Bearer 校验；可通过 `DISABLE_CALLER_ID_HEADER=true` 忽略 `X-AI-Service-Caller-ID` 并统一使用 `default` caller。配置层只允许在 loopback DB / Redis 地址下开启这两个开关。

`X-Request-ID` 可由调用方传入，但只接受 ASCII 字母、数字、连字符和下划线，最长 128 字符；不符合规则时服务会生成新的 UUID，并在响应头返回。

## 五、Job 创建流程

```text
POST /jobs
  ↓
Pydantic schema 校验 CreateJobRequest 顶层字段
  ↓
Bearer token 校验，确定 caller_id
  ↓
get_job_executor(job_type)
  ↓
executor.normalize_job_params(job_params)
  ↓
校验 callback.url：默认必须 HTTPS，且不能指向私有网段 IP
  ↓
executor.validate_normalized_job_params(job_params)
  ↓
executor.runtime_job_fields(job_params)
  ├─ 如返回 model_id，则校验模型已启用
  └─ 如存在 Prompt YAML 模板，则校验 runtime_fields.prompt_payload
  ↓
计算 request_fingerprint
  ↓
使用 PostgreSQL advisory lock 做 client_request_id 幂等检查
  ↓
若 MAX_ACTIVE_JOBS > 0，串行化 active count 检查
  ↓
创建 jobs，status=queued
  ↓
冻结 job_params_ref、job_params_hash 和 runtime_ref
  ↓
创建 job_attempts#1，写入 jobs.active_attempt_id
  ↓
commit
  ↓
publish_job_attempt(active_attempt_id)
  ↓
Taskiq 发布 jobs.run_attempt(attempt_id)
  ↓
标记 attempt.published
  ↓
返回 202 + job_id + status_url
```

关键点是 **先提交 Job 和 Attempt 账本，再发布 Taskiq 消息**。如果 DB 已提交但发布失败，attempt 会记录发布错误和下一次可发布时间；recovery 会重新发布到期 attempt。Taskiq 消息重复时，Worker 也必须先 claim 当前 active attempt，claim 失败的消息会被跳过。

## 六、Job 状态机

```text
queued
  ├─ 创建成功后进入
  ├─ 等待 active attempt 被发布或领取
  └─ 可由 recovery 重新发布 attempt

running
  ├─ Worker 成功 claim active attempt 后进入
  ├─ 正在执行 runtime、整理结果、写入产物或执行成功前副作用
  └─ attempt 租约过期后可由 recovery 标记失败并按策略重试

succeeded
  ├─ public result 由 job_type 决定，可以是对象，也可以是 null
  ├─ progress_percent = 100
  └─ 创建 job.succeeded Callback outbox

failed
  ├─ result = null
  ├─ error 有效
  └─ 创建 job.failed Callback outbox
```

Job 对外只有这四类状态。Attempt 的 `queued / published / running / succeeded / failed` 是内部账本状态，不进入普通调用方 API 合同。

## 七、job_params、Runtime 和 Prompt

`POST /jobs` 顶层稳定字段只有：

```text
client_request_id
job_type
job_params
callback
metadata
options
```

模型、输入源、Prompt、业务 ID、领域选项都属于具体能力参数，必须放在 `job_params` 里，由对应 `JobExecutor` 解释。

`JobExecutor` 创建期负责三件事：

- `normalize_job_params()`：把外部输入校验并归一化为稳定 dict。
- `validate_normalized_job_params()`：检查归一化参数和运行前置条件。
- `runtime_job_fields()`：派生模型、Prompt、输出目标等运行时字段，并写入 runtime snapshot。

Prompt YAML 的职责只是模板发现和 LLM prompt 校验：

```text
app/core/prompts.yaml
```

它不是 Job 类型注册表。`job_type` 是否存在，以 `app/jobs/registry.py` 中的 executor registry 为准。

## 八、当前 Job 类型

当前内置示例 `job_type`：

| job_type | 说明 |
|----------|------|
| `job_test_add` | 测试用加法 Job |
| `job_test_echo` | workflow smoke 使用的 echo Job |
| `arithmetic` | 不依赖模型调用的四则运算示例 |

`POST /jobs` 对未注册类型返回 `INVALID_JOB_TYPE`。成功 Job 的 `canonical_result` 保存内部完整结果；`public_result` 是否暴露给调用方由 executor 的 `public_result_schema` 和 `public_result()` 决定。

## 九、Taskiq 执行流程

主入口是 `jobs.run_attempt`。

```text
Taskiq: jobs.run_attempt(attempt_id)
  ↓
register_all_job_types()
  ↓
claim_attempt_for_execution(attempt_id)
  ├─ 要求 attempt 是当前 jobs.active_attempt_id
  ├─ 要求 Job.status = queued
  ├─ 要求 Attempt.status in queued / published
  └─ 成功后写入 lease_token、worker_id、lease_expires_at，并将 Job 置为 running
  ↓
execute_job(job_id, execution_generation, attempt_id, lease_token)
  ↓
get_job_executor(job.job_type)
  ↓
executor.execute(job, db)
  ├─ 自定义运行时：_execute() 返回 canonical result dict
  └─ 内置 LLM 文本运行时：_execute() 返回 None 后调用 run_ai_job()
  ↓
validate_canonical_result()
  ↓
public_result()
  ↓
按 large_artifact_keys 写入大产物
  ↓
按需 run_success_side_effect()
  ↓
mark_succeeded(job, execution_token=attempt_id)
  ↓
mark_attempt_succeeded(attempt_id, lease_token)
  ↓
deliver_callback_for_job(job_id)
```

执行失败时，Worker 会用当前 `lease_token` 标记 attempt failed。若该 Job 仍可重试，会创建新的 active attempt、提升 `execution_generation` 并把 Job 放回 `queued`；否则 Job 收敛为 `failed` 并创建失败 Callback outbox。

## 十、输出结构

`GET /jobs/{job_id}` 返回统一 Job 视图。结果规则：

```text
queued/running: result = null, error = null
succeeded:      result 由 job_type 决定，可以是对象或 null；error = null
failed:         result = null；error 非空
```

Artifact 有两种交付方式：

- 短文本或 JSON：直接放在 `content`。
- 大文本：写入对象存储，响应中返回 `storage=oss_object`、`oss_bucket`、`oss_key`、`oss_region`、`content_hash`、`content_size_bytes`。

大产物默认写入当前 Job 输出前缀下的 `results/g<execution_generation>/`，让重试代次之间的结果互不覆盖。

## 十一、Callback

Job 进入终态后会创建或复用 `callback_outbox` 记录，再由 `deliver_callback_for_job(job_id)` 领取并发送 HTTP 请求。

请求头：

```http
Content-Type: application/json
X-AI-Service-Job-Id: <job_id>
X-AI-Service-Event: job.succeeded | job.failed
X-AI-Service-Timestamp: <ISO-8601 datetime>
X-AI-Service-Signature: sha256=<hmac>
```

签名内容是：

```text
timestamp + "." + raw_body
```

Callback 发送策略：

- 未配置 `callback.url` 时标记为 `not_configured`。
- `callback.events` 不包含当前终态事件时标记为 `skipped`。
- 单次 HTTP 超时由 `CALLBACK_TIMEOUT_SECONDS` 控制。
- 终态后立即尝试投递 1 次。
- 失败后由 recovery loop 按 `CALLBACK_RETRY_DELAY_SECONDS` 补偿。
- 总尝试次数由 `CALLBACK_MAX_DELIVERY_ATTEMPTS` 控制。
- 内部领取窗口由 `CALLBACK_TIMEOUT_SECONDS + _CALLBACK_DELIVERY_CLAIM_GRACE` 派生，不作为生产配置项暴露。
- Callback 最终失败不会改变 Job 终态；调用方应以轮询作为兜底。

## 十二、恢复、超时和并发保护

Worker 启动时会执行一次 recovery，之后由进程内 recovery loop 周期执行。多 Worker 通过 PostgreSQL advisory lock 保证同一轮扫描单飞。

| 场景 | 条件 | 处理 |
|------|------|------|
| due dispatch | 当前 active attempt 为 `queued` 且到达 `next_dispatch_at` | 重新发布 Taskiq 消息 |
| uncertain publish | 当前 active attempt 为 `published` 且到达 `next_dispatch_at` | 再次发布同一 attempt |
| stale running | 当前 active attempt 为 `running` 且 `lease_expires_at <= now()` | 标记 attempt failed；未超过 `max_attempts` 时创建新 attempt，否则 Job failed |
| due callback | 终态 Job 的 Callback 到达重试时间且未超过最大次数 | 重新投递 Callback |
| expired settled | `expires_at <= now()` 且终态且 Callback 已收敛 | 软删除 Job |

并发保护点：

- `caller_id + client_request_id` 使用 PostgreSQL transaction advisory lock，避免并发重复创建。
- `MAX_ACTIVE_JOBS` 检查使用 PostgreSQL advisory lock，避免明显超限。
- Worker 领取执行权必须匹配 `jobs.active_attempt_id`。
- `lease_token` 保护 Attempt heartbeat、失败标记和成功标记。
- `execution_token` 保护 Job progress、success 和 failure 状态转移。
- `execution_generation` 隔离旧执行尝试和新一轮执行记录。
- Callback outbox 使用唯一 `event_id` 和领取租约，避免同一终态事件被并发投递。

超时链条由一个 env 锚点和代码常量 buffer 派生：

```text
MODEL_CALL_TIMEOUT_SECONDS
  + _WORKER_SOFT_TIMEOUT_BUFFER
  = worker_soft_time_limit

worker_soft_time_limit
  + _WORKER_HARD_TIMEOUT_BUFFER
  = worker_hard_time_limit

worker_hard_time_limit
  + _JOB_STALE_RUNNING_BUFFER
  = job_stale_running_seconds
```

这些 buffer 是 `app/core/config.py` 内部常量，不是 `.env` 配置项。

## 十四、配置和运行形态

本项目区分 1 个本地运行入口和 2 个 compose 部署入口：

- `local`：宿主机运行 API / worker，`docker compose` 只提供 PostgreSQL / Redis。
- `compose-deps`：只启动 PostgreSQL / Redis 依赖服务。
- `compose-full`：API、worker、PostgreSQL、Redis 全部由 `docker compose` 管理。

配置加载优先级：

```text
运行时显式环境变量
> docker-compose.yml environment
> ENV_FILE 指定的 env 文件
> .env
> 应用默认值
```

关键配置：

| 配置 | 说明 |
|------|------|
| `DATABASE_URL` | PostgreSQL async 连接串 |
| `REDIS_URL` | Redis 连接串，供 Taskiq broker 使用 |
| `SERVICE_API_KEY` | 业务 API Bearer token |
| `DISABLE_HTTP_AUTH_HEADER` | 本地联调开关；`true` 时跳过 Bearer 校验，仅允许 loopback DB / Redis 地址开启 |
| `DISABLE_CALLER_ID_HEADER` | 本地联调开关；`true` 时忽略 `X-AI-Service-Caller-ID`，仅允许 loopback DB / Redis 地址开启 |
| `STORAGE_BACKEND` | `local` 或 `aliyun_oss` |
| `LOCAL_OBJECT_STORAGE_PATH` | 本地对象存储目录 |
| `OSS_*` | 阿里云 OSS 或输出路径相关配置 |
| `OPENAI_API_KEY` | 启用 OpenAI 模型列表和模型调用 |
| `OPENAI_BASE_URL` | OpenAI 兼容代理地址 |
| `DEFAULT_MODEL_ID` | 默认模型 ID |
| `MODEL_CONFIG_PATH` | 模型 YAML 路径 |
| `PROMPT_CONFIG_PATH` | Prompt YAML 路径，仅用于 Prompt 模板发现和校验 |
| `MODEL_CALL_TIMEOUT_SECONDS` | 模型调用超时锚点 |
| `MAX_ACTIVE_JOBS` | queued + running 软上限 |
| `JOB_MAX_EXECUTION_ATTEMPTS` | recovery 可创建的新执行尝试上限 |
| `JOB_RECOVERY_INTERVAL_SECONDS` | recovery loop 间隔 |
| `CALLBACK_SIGNING_SECRET` | Callback HMAC 密钥 |

生产或多节点场景应使用 `STORAGE_BACKEND=aliyun_oss` 对应的对象存储配置，避免本地磁盘导致 API / worker 节点之间看不到同一份输入和输出。

## 十五、扩展边界

新增 Job 类型时，优先横向增加 `JobExecutor`、schema 和测试，不修改通用 Job 顶层字段。

最小步骤：

1. 定义该能力的 `ParamsSchema`、`RuntimeFieldsSchema`、`CanonicalResultSchema` 和 `PublicResultSchema`。
2. 在 `app/schemas/registry.py` 登记需要反查的 schema 名称。
3. 在 `app/jobs/types/<job_type>.py` 实现 `JobExecutor` 子类，设置稳定 `name`。
4. 实现 `runtime_job_fields()`，把模型、Prompt、外部系统配置等运行时字段从 `job_params` 派生出来。
5. 选择执行方式：自定义运行时覆盖 `_execute(job, db)`；内置 LLM 文本运行时让 `_execute()` 返回 `None` 并实现 `parse_output(text)`。
6. 定义 `canonical_result_schema`、`public_result_schema`、`large_artifact_keys`、`allowed_error_codes`、`log_events`、`max_attempts` 和 `timeout_seconds`。
7. 如果需要成功前外部副作用，实现幂等的 `run_success_side_effect()`。
8. 使用 `@register_job_type` 注册 executor，并在 `app/jobs/types/register.py` 显式导入。
9. 补充参数校验、执行结果、公开投影、Callback envelope、失败错误和 registry consistency 测试。
10. 如果该能力需要 Prompt 模板发现，再把它加入对应 Prompt YAML；不需要 Prompt 的能力不要为了注册 `job_type` 去写 YAML。

不应做：

- 为具体能力扩展 `CreateJobRequest` 顶层字段。
- 把业务流程编排放进 AI Job 服务。
- 把 Taskiq result backend 当作业务状态源。
- 向普通调用方暴露 Attempt、Lease、Worker 或内部恢复状态。
- 给错误参数添加 silent fallback、默认吞错或空结果兼容。

## 十六、最小验证入口

修改代码后优先运行：

```bash
./scripts/verify.sh check
```

修改启动、任务、数据库、对象存储或 Job 流程后，还应运行：

```bash
./scripts/dev.sh start
./scripts/verify.sh workflow-smoke
./scripts/dev.sh stop
```

修改 Job 内部执行、Taskiq worker、Attempt / recovery 或 Callback 后，优先运行：

```bash
./scripts/dev.sh start
./scripts/verify.sh workflow-smoke
./scripts/dev.sh stop
```

真实模型业务 e2e 不属于当前模板核心 `scripts/` 命令面。接入正式业务 `job_type` 后，再恢复对应业务 e2e 脚本或放入 `examples/business/`。
