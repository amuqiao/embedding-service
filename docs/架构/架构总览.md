# AI Job 服务架构总览

本文用当前代码说明 AI Job 服务的架构：它是什么、边界在哪里、请求如何变成异步 Job、复杂流程如何由 Celery canvas 表达、结果如何交付，以及 Job 如何按整体恢复并收敛。

## 文档职责

本文负责说明一个核心问题：**本服务是无状态 AI 能力层，调用方提交单个 AI Job，服务按 `job_type` 找到能力实现，异步执行任务，把产物写入 DB 或对象存储，并通过状态查询和 Callback 交付终态。**

本文不负责记录临时排查过程、生产平台发布流程、用户系统编排逻辑或字段级 API 合同。字段级合同见 [通用 AI Job 接入规范](通用_AI_Job_接入规范.md)，上线判断见 [生产就绪性评审](production-readiness-review.md)。

## 一、核心心智模型

本服务不是业务流程系统，而是 AI 能力层。

```text
业务后端 / BFF
  ├─ 决定何时执行业务 step1、step2、step3
  ├─ 管理用户、项目、稿件、审核状态和业务重跑策略
  └─ 调用本服务创建单个 AI Job

AI Job Service
  ├─ 校验鉴权、Job 骨架、job_type、job_params 和 Callback
  ├─ 根据 WorkflowHandler 派生 runtime fields
  ├─ 创建 queued Job 并投递 jobs.dispatch
  ├─ 规划 execution_plan 和 work items
  ├─ 用 Celery canvas 表达 single / chain / group / chord 流程
  ├─ 执行 LLM runtime 或自定义 runtime
  ├─ 合并 canonical result，派生 public result
  ├─ 按需将大 artifacts 写入对象存储
  ├─ 记录 succeeded / failed 终态
  └─ 发送终态 Callback
```

关键设计取舍：

- **单 Job 语义**：服务只理解单个 `job_type` 的执行，不决定调用方业务流程如何串联。
- **能力注册表是源头**：`job_type` 来自 `WorkflowHandler` 注册表；Prompt YAML 只是部分 LLM 型能力的可选模板配置，不是 Job 类型总表。
- **复杂流程内部化**：复杂 Job 用 `WorkflowHandler.build_execution_plan()` 和 Celery canvas 表达，对外仍是一个 `job_id`、一个状态机、一个终态结果。
- **整体恢复**：不追求内部 step 精准恢复；Worker 重启或 stale running 时按 Job 整体重新投递、重新规划、重新执行，最终收敛到 `succeeded` 或 `failed`。
- **代次隔离**：`execution_generation` 是内部执行代次，用于隔离旧 Celery canvas 消息、旧 work items 和新一轮执行记录；不进入外部 API 合同。
- **Callback + 轮询双通道**：Callback 是主动通知，`GET /jobs/{job_id}` 是兜底查询。

## 二、服务边界

本服务负责：

- 受保护 API：模型列表、Prompt 模板、创建 Job、查询 Job。
- Job 幂等：同一 `caller_id + client_request_id` 在 24 小时内返回已有 Job。
- 创建校验：`job_type` 是否已注册、`job_params` 是否符合 handler schema、模型是否可用、Callback URL 是否安全。
- 可选 Prompt 校验：当 `job_type` 存在 Prompt YAML 模板时，校验 handler 派生出的 `prompt_payload` 与模板 key / role 一致。
- Job 状态机：`queued -> running -> succeeded | failed`。
- 内部执行：通过 LLM runtime 或 handler 自定义 runtime 执行能力逻辑。
- 产物持久化：命中 handler `large_artifact_keys` 的大产物写入对象存储。
- Callback：终态后发送 `job.succeeded` 或 `job.failed`。
- 恢复与清理：Worker recovery loop 处理 orphan queued、未确认发布、stale running、Callback 补偿和已收敛过期 Job 清理。

本服务不负责：

- 用户、权限、项目、稿件版本、人工审核和业务步骤编排。
- 判断某个业务 step 失败后是否重做前置 step。
- 生产部署平台、K8s、云平台 Secret、CI/CD 发布流水线。
- 长期保存业务结果；Job 默认 24 小时过期，清理只处理已终态且 Callback 已收敛的记录。
- work item 级别精确断点续跑承诺。

## 四、API 表面

所有业务 API 使用统一前缀：

```text
/api/v1/ai-jobs
```

端点：

| 方法 | 路径 | 说明 | 鉴权 |
|------|------|------|------|
| `GET` | `/health` | 基础存活检查 | 否 |
| `GET` | `/healthz` | DB + Redis readiness 检查 | 否 |
| `GET` | `/models` | 返回当前可用模型 | 是 |
| `GET` | `/prompt-templates` | 返回 Prompt 模板发现信息 | 是 |
| `POST` | `/jobs` | 创建 AI Job | 是 |
| `GET` | `/jobs/{job_id}` | 查询 Job 状态和结果 | 是 |

除健康检查外，请求必须携带：

```http
Authorization: Bearer <SERVICE_API_KEY>
```

`X-Request-ID` 可由调用方传入，但只接受 ASCII 字母、数字、连字符和下划线，最长 128 字符；不符合规则时服务会生成新的 UUID，并在响应头返回。

## 五、Job 创建流程

```text
POST /jobs
  ↓
Pydantic schema 校验 CreateJobRequest 顶层字段
  ↓
Bearer token 校验，确定 caller_id
  ↓
workflow_registry.get(job_type)
  ↓
handler.normalize_job_params(job_params)
  ↓
校验 callback.url：默认必须 HTTPS，且不能指向私有网段 IP
  ↓
handler.validate_normalized_job_params(job_params)
  ↓
handler.runtime_job_fields(job_params)
  ├─ 如返回 model_id，则校验模型已启用
  └─ 如存在 Prompt YAML 模板，则校验 runtime_fields.prompt_payload
  ↓
若 client_request_id 存在，使用 PostgreSQL advisory lock 做 24h 幂等查询
  ↓
若 MAX_ACTIVE_JOBS > 0，使用 advisory lock 串行化 active count 检查
  ↓
创建 ai_jobs，status=queued
  ↓
冻结 job_params_ref 和 runtime_ref
  ↓
预生成 celery task_id，写入 ai_jobs.celery_task_id
  ↓
commit
  ↓
dispatch_job_task.apply_async(args=[job_id], task_id=task_id)
  ↓
mark_celery_published
  ↓
返回 202 + job_id + status_url
```

关键点是 **先写入 `celery_task_id` 并提交，再投递 Celery**。如果 API 在 commit 后、dispatch 前崩溃，Job 会变成 `queued + celery_task_id 非空 + celery_published_at 为空`，由 recovery 扫描重新投递；如果消息重复，`jobs.dispatch` 会校验 DB 中的 `celery_task_id` 并用 CAS 防止双执行。

## 六、Job 状态机

```text
queued
  ├─ 创建成功后进入
  ├─ 等待 Celery worker 领取
  └─ 可被 recovery 重新投递

running
  ├─ worker 成功 claim queued Job 后进入
  ├─ 正在规划、执行、合并或写入产物
  └─ stale 后可被 recovery 整 Job 重新入队；超过上限后 failed

succeeded
  ├─ public result 由 job_type 决定，可以是 JobResult，也可以是 null
  ├─ progress_percent = 100
  └─ 触发 job.succeeded Callback

failed
  ├─ result = null
  ├─ error 有效
  └─ 触发 job.failed Callback
```

`ai_jobs.expires_at` 默认是创建后 24 小时。Worker recovery loop 只清理已进入终态且 Callback 已 `delivered` 或 `skipped` 的过期记录。

## 七、job_params 与 Prompt

`POST /jobs` 顶层稳定字段只有：

```text
client_request_id
job_type
job_params
callback
metadata
options
```

模型、输入源、Prompt、业务 ID、领域选项都属于具体能力参数，必须放在 `job_params` 里，由对应 `WorkflowHandler` 解释。

当前内置能力分两类：

- `novel_localization.*`：使用 `NovelLocalizationJobParams`，包含 `model_id`、`source`、`prompt`。其中 `source` 可来自 OSS 或 inline 文本；Prompt blocks 会与 `app/workflows/novel_localization/prompts.yaml` 校验。
- `generic.echo`、`short_drama.*`：使用各自 handler schema 和自定义 runtime，不要求出现在 Prompt YAML 中。

Prompt YAML 的职责只是模板发现和 LLM prompt 校验：

```text
app/workflows/novel_localization/prompts.yaml
```

它不是 Job 类型注册表。`job_type` 是否存在，以 `app/workflows/register.py` 注册到 `workflow_registry` 的 handler 为准。

## 八、当前 Job 类型

当前内置 `job_type` 来自 `WorkflowHandler` 注册表：

| Job Type | 来源 | 执行方式 | public result |
|----------|------|----------|---------------|
| `generic.echo` | `app/workflows/generic/handler.py` | 自定义 single runtime | `JobResult` |
| `novel_localization.step1_localize` | `app/workflows/novel_localization/handler.py` + Prompt YAML | LLM runtime，可 single / chunked | `JobResult` |
| `novel_localization.step2_review` | `app/workflows/novel_localization/handler.py` + Prompt YAML | LLM runtime，可 single / chunked | `JobResult` |
| `novel_localization.step3_translate` | `app/workflows/novel_localization/handler.py` + Prompt YAML | LLM runtime，可 single / chunked | `JobResult` |
| `short_drama.tagging.initial` | `app/workflows/short_drama_tagging/handler.py` | 自定义 single runtime，成功前写 RS | `null` |
| `short_drama.tagging.incremental` | `app/workflows/short_drama_tagging/handler.py` | 自定义 single runtime，成功前写 RS | `null` |
| `short_drama.tag_schema.translation` | `app/workflows/short_drama_tagging/handler.py` | 自定义 single runtime | `TagSchemaTranslationResult` |

成功 Job 的 `canonical_result` 可以保存内部完整结果；`public_result` 是否暴露给调用方由 handler 的 `public_result_schema` 决定。

## 九、Celery Canvas 执行流程

主入口是 `jobs.dispatch`，不是旧的单任务直跑。

```text
jobs.dispatch(job_id)
  ↓
校验 job_id + celery_task_id 与 DB 一致
  ↓
queued -> running CAS claim
  ↓
plan_job
  ├─ 复用当前 generation 的 execution_plan / work items
  └─ 或调用 handler.build_execution_plan() / build_job_plan()
  ↓
build_canvas(job_id, job_type, plan, item_ids)
  ├─ single: chain(execute_work_item, finalize_job)
  ├─ plain_chord: chord(group(chunks), finalize_job)
  ├─ memory_fanout: chain(memory, fanout chunks, finalize_job)
  └─ scan_chord: chain(chord(chunks, scan), finalize_job)
  ↓
jobs.execute_work_item
  ├─ 校验 item.execution_generation == job.execution_generation
  ├─ claim work item
  ├─ 执行 handler 自定义 runtime 或内置 LLM runtime
  └─ 写回 work item result
  ↓
jobs.finalize_job
  ├─ 校验 canvas 携带的 execution_generation 仍是当前 Job generation
  ├─ 只读取当前 generation 的 work items
  ├─ merge canonical result
  ├─ generation 作用域写入大 artifacts
  ├─ 执行成功前副作用
  ├─ mark_succeeded
  └─ deliver_callback_for_job
```

`execution_generation` 的作用：

- recovery 整 Job 重跑时，`ai_jobs.execution_generation += 1`，并清空旧 `execution_plan`。
- 新一轮规划会创建新 generation 的 work items。
- 旧 generation 的 work item task 即使继续运行，也不能参与新 generation 的 merge。
- progress、execution plan、success side effect 前的 claim 都要求当前 `celery_task_id + execution_generation` 匹配。
- 大产物写入带 generation scope：work item 产物写到 `work-items/g<generation>/...`，最终产物写到 `results/g<generation>/...`。

## 十、输出结构

`GET /jobs/{job_id}` 返回统一 `JobView`。字段级结构见 [通用 AI Job 接入规范](通用_AI_Job_接入规范.md)。

结果规则：

```text
queued/running: result = null, error = null
succeeded:      result 由 job_type 决定，可以是 JobResult 或 null；error = null
failed:         result = null；error 非空
```

Artifact 有两种交付方式：

- 短文本或 JSON：直接放在 `content`。
- 大文本：写入对象存储，响应中返回 `storage=oss_object`、`oss_bucket`、`oss_key`、`oss_region`、`content_hash`、`content_size_bytes`。

## 十一、Callback

Job 进入终态后会调用 `deliver_callback_for_job(job_id)`，再由 `deliver_callback(job)` 发送 HTTP 请求。

请求头：

```http
Content-Type: application/json
X-AI-Service-Job-Id: <job_id>
X-AI-Service-Event: job.succeeded | job.failed
X-AI-Service-Timestamp: <ISO-8601 datetime>
X-AI-Service-Signature: sha256=<hmac>
```

签名内容是：

```text
timestamp + "." + raw_body
```

Callback 发送策略：

- 未配置 `callback.url` 时标记为 `skipped`。
- `callback.events` 不包含当前终态事件时标记为 `skipped`。
- 单次 HTTP 超时由 `CALLBACK_TIMEOUT_SECONDS` 控制。
- 终态后立即尝试投递 1 次。
- 失败后由 Worker recovery loop 按 `CALLBACK_RETRY_DELAY_SECONDS` 补偿。
- 总尝试次数由 `CALLBACK_MAX_DELIVERY_ATTEMPTS` 控制。
- 内部领取窗口由 `CALLBACK_TIMEOUT_SECONDS + _CALLBACK_DELIVERY_CLAIM_GRACE` 派生，不作为生产配置项暴露。
- Callback 最终失败不会改变 Job 终态；调用方应以轮询作为兜底。

## 十二、恢复、超时和并发保护

Worker 启动时会执行一次 recovery，之后由进程内 recovery loop 周期执行。多 Worker 通过 PostgreSQL advisory lock 保证同一轮扫描单飞。

| 场景 | 条件 | 处理 |
|------|------|------|
| orphan queued | `queued + celery_task_id IS NULL + created_at < cutoff` | CAS 写入新 task_id 并重新投递 |
| unpublished queued | `queued + celery_task_id IS NOT NULL + celery_published_at IS NULL + created_at < cutoff` | CAS 替换 task_id 并重新投递 |
| stale running | `running + (last_heartbeat_at IS NULL OR last_heartbeat_at < stale_cutoff)` | 低于 `JOB_MAX_EXECUTION_ATTEMPTS` 时整 Job 重新入队并提升 `execution_generation`；达到上限后 `failed(JOB_TIMEOUT)` 并发送失败 Callback |
| due callback | 终态 Job 的 Callback 到达重试时间且未超过最大次数 | 重新投递 Callback |
| expired settled | `expires_at <= now()` 且终态且 Callback 为 `delivered/skipped` | 软删除 Job 和 work items |

并发保护点：

- `caller_id + client_request_id` 使用 PostgreSQL transaction advisory lock，避免并发重复创建。
- `MAX_ACTIVE_JOBS` 检查使用 PostgreSQL advisory lock，避免明显超限。
- `queued -> running` 使用 CAS UPDATE，避免同一 Job 被多个 worker 双执行。
- `jobs.dispatch` 要求消息 task_id 与 DB `celery_task_id` 一致。
- `mark_succeeded` / `mark_failed` 要求 Job 仍在当前 task claim 下。
- `execution_generation` 隔离旧 Celery canvas 消息和新一轮 work items。
- Celery 配置 `acks_late`、`task_reject_on_worker_lost`、`worker_prefetch_multiplier=1`，降低 worker 异常退出时的消息丢失和过度预取风险。

超时链条由一个 env 锚点和代码常量 buffer 派生：

```text
MODEL_CALL_TIMEOUT_SECONDS
  + _CELERY_SOFT_TIMEOUT_BUFFER
  = celery_soft_time_limit

celery_soft_time_limit
  + _CELERY_HARD_TIMEOUT_BUFFER
  = celery_time_limit

celery_time_limit
  + _JOB_STALE_RUNNING_BUFFER
  = job_stale_running_seconds
```

这些 buffer 是 `app/core/config.py` 内部常量，不是 `.env` 配置项。

## 十四、配置和运行形态

本项目区分 1 个本地运行入口和 2 个 compose 部署入口：

- `local`：宿主机运行 API / worker，`docker compose` 只提供 PostgreSQL / Redis。
- `compose-deps`：只启动 PostgreSQL / Redis 依赖服务。
- `compose-full`：API、worker、PostgreSQL、Redis 全部由 `docker compose` 管理。

配置加载优先级：

```text
运行时显式环境变量
> docker-compose.yml environment
> ENV_FILE 指定的 env 文件
> .env
> 应用默认值
```

关键配置：

| 配置 | 说明 |
|------|------|
| `DATABASE_URL` | PostgreSQL async 连接串 |
| `REDIS_URL` | Celery broker / backend |
| `SERVICE_API_KEY` | 业务 API Bearer token |
| `STORAGE_BACKEND` | `local` 或 `aliyun_oss` |
| `OSS_*` | 阿里云 OSS 或输出路径相关配置 |
| `OPENAI_API_KEY` | 启用 OpenAI 模型列表和模型调用 |
| `OPENAI_BASE_URL` | OpenAI 兼容代理地址 |
| `DEFAULT_MODEL_ID` | 默认模型 ID |
| `MODEL_CONFIG_PATH` | 模型 YAML 路径 |
| `PROMPT_CONFIG_PATH` | Prompt YAML 路径，仅用于 Prompt 模板发现和校验 |
| `MODEL_CALL_TIMEOUT_SECONDS` | 模型调用超时锚点 |
| `MAX_ACTIVE_JOBS` | queued + running 软上限 |
| `JOB_MAX_EXECUTION_ATTEMPTS` | stale running 整 Job 重跑最大次数 |
| `CALLBACK_SIGNING_SECRET` | Callback HMAC 密钥 |
| `ALLOW_INSECURE_CALLBACKS` | 是否允许本地 HTTP callback |

生产或多节点场景应使用 `STORAGE_BACKEND=aliyun_oss`，避免本地磁盘导致 API / worker 节点之间看不到同一份输入和输出。

## 十五、扩展边界

新增 Job 类型时，优先按 handler 接入，而不是改通用 Job 顶层字段。

最小步骤：

1. 在 `app/workflows/<name>/` 下实现 `WorkflowHandler` 子类，设置稳定 `job_type`。
2. 定义 `params_schema`，通过 `normalize_job_params()` / `validate_normalized_job_params()` 做创建阶段 fail-fast 校验。
3. 实现 `runtime_job_fields()`，把模型、Prompt、外部系统配置等运行时字段从 `job_params` 派生出来。
4. 选择执行方式：内置 LLM runtime 用 `parse_output()`；自定义 runtime 用 `execute_standard_item()`；复杂流程用 `build_execution_plan()` 和 `canvas_pattern`。
5. 定义 `canonical_result_schema`、`public_result_schema` 和 `large_artifact_keys`。
6. 如果需要成功前外部副作用，实现幂等的 `run_success_side_effect()`，并保证同一 `job_id` 重跑不会重复造成不可接受影响。
7. 在 `app/workflows/register.py` 注册 handler。
8. 补充 schema、创建校验、执行、finalize、artifact、Callback 和 recovery 相关测试。
9. 如果该能力需要 Prompt 模板发现，再把它加入对应 Prompt YAML；不需要 Prompt 的能力不要为了注册 `job_type` 去写 YAML。

不应做：

- 为具体能力扩展 `CreateJobRequest` 顶层字段。
- 把业务流程编排放进 AI Job 服务。
- 依赖 work item 级断点恢复作为正确性前提。
- 给错误参数添加 silent fallback 或默认吞错。

## 十六、最小验证入口

修改代码后优先运行：

```bash
./scripts/verify.sh check
```

修改启动、任务、数据库、对象存储或 Job 流程后，还应运行：

```bash
./scripts/dev.sh start
./scripts/verify.sh smoke
./scripts/dev.sh stop
```

修改 Job 内部执行、Celery workflow、分块或 merge 后，优先运行：

```bash
./scripts/dev.sh start
./scripts/verify.sh workflow-smoke
./scripts/dev.sh stop
```

需要真实模型端到端验证时，确认 `.env` 有 `OPENAI_API_KEY` 且 `.data/` 下有 `.txt` 文件，再运行：

```bash
./scripts/dev.sh start
./scripts/verify.sh e2e
./scripts/dev.sh stop
```
