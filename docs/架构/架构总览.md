# FastAPI AI Job Template 架构总览

本文用当前代码说明 FastAPI AI Job Template 的架构：它是什么、边界在哪里、请求如何变成异步 Job、Job 如何执行、结果如何交付，以及内置示例 workflow 如何接入。

## 文档职责

本文负责说明一个核心问题：**本服务是一个无状态的小说本地化 AI 执行层，调用方提交单个 AI Job，服务异步执行模型任务，把大文本产物写入对象存储，并通过状态查询和 Callback 交付终态。**

本文不负责记录临时排查过程、生产平台发布流程、用户系统编排逻辑或前端使用说明。

## 一、核心心智模型

本服务不是业务流程系统，而是 AI 能力层。

```text
业务后端 / BFF
  ├─ 决定何时执行 step1、step2、step3
  ├─ 管理用户、项目、稿件、审核状态和重跑策略
  └─ 调用本服务创建单个 AI Job

fastapi-ai-job-template
  ├─ 验证请求、模型、Prompt、Callback 和输入对象
  ├─ 创建 Job 并投递 Celery
  ├─ 从对象存储读取 UTF-8 文本
  ├─ 调用 LLM
  ├─ 解析模型输出为结构化 artifacts / signals
  ├─ 将大文本 artifacts 写回对象存储
  ├─ 记录 Job 终态
  └─ 发送 Callback
```

关键设计取舍：

- **无状态 API**：API 实例不保存内存态流程，任一实例都可创建和查询 Job。
- **异步执行**：`POST /jobs` 只负责入队，立即返回 `202 Accepted`；耗时模型调用由 Celery worker 执行。
- **单 Job 语义**：服务只理解单个 `job_type` 的执行，不决定三阶段业务流如何串联。
- **对象存储交付大文本**：输入来自对象存储，大文本输出也写入对象存储；DB 保存状态、结构化结果和对象定位信息。
- **Callback + 轮询双通道**：Callback 是主动通知，`GET /jobs/{job_id}` 是兜底查询。

## 二、服务边界

本服务负责：

- 受保护 API：模型列表、Prompt 模板、创建 Job、查询 Job。
- Job 幂等：同一 `caller_id + client_request_id` 在 24 小时内返回已有 Job。
- 请求校验：`job_type`、`model_id`、`prompt.blocks`、OSS 输入、Callback URL。
- Job 状态机：`queued -> running -> succeeded | failed`。
- 模型执行：通过 LiteLLM 调用 OpenAI 兼容模型。
- 输出解析：按 `job_type` 转换为统一 `JobResult`。
- 产物持久化：`localized_text`、`translated_text` 写入对象存储。
- Callback：终态后发送 `job.succeeded` 或 `job.failed`。
- 恢复与清理：worker 启动恢复 orphan / stuck / stale Job，Beat 每天清理过期 Job。

本服务不负责：

- 用户、权限、项目、稿件版本、人工审核和业务步骤编排。
- 判断 step2 不通过后是否重做 step1。
- 生产部署平台、K8s、云平台 Secret、CI/CD 发布流水线。
- 长期保存业务结果；Job 默认 24 小时过期。

## 三、运行时组件

```text
FastAPI API
  ├─ app/main.py
  ├─ app/api/routes/health.py
  ├─ app/api/routes/meta.py
  └─ app/api/routes/jobs.py

Celery Worker
  ├─ app/tasks/celery_app.py
  ├─ app/tasks/jobs.py
  └─ app/tasks/recovery.py

领域服务
  ├─ app/services/jobs.py
  ├─ app/services/executor.py
  ├─ app/services/callbacks.py
  ├─ app/services/job_planner.py
  ├─ app/services/job_workflow.py
  └─ app/services/job_context.py

基础设施
  ├─ PostgreSQL：ai_jobs、ai_job_work_items
  ├─ Redis：Celery broker / result backend
  ├─ ObjectStorage：local 或 aliyun_oss
  └─ LiteLLM：OpenAI 兼容模型调用
```

API 侧使用 SQLAlchemy async engine，并通过 `DB_POOL_SIZE`、`DB_MAX_OVERFLOW`、`DB_POOL_RECYCLE` 控制连接池。Worker 侧每次任务创建独立 async engine，使用 `NullPool`，避免 Celery 并发下长期持有连接。

## 四、API 表面

所有业务 API 使用统一前缀：

```text
/api/v1/ai-jobs
```

端点：

| 方法 | 路径 | 说明 | 鉴权 |
|------|------|------|------|
| `GET` | `/health` | 基础存活检查 | 否 |
| `GET` | `/healthz` | DB + Redis readiness 检查 | 否 |
| `GET` | `/models` | 返回当前可用模型 | 是 |
| `GET` | `/prompt-templates` | 返回可提交的 Prompt 模板 | 是 |
| `POST` | `/jobs` | 创建 AI Job | 是 |
| `GET` | `/jobs/{job_id}` | 查询 Job 状态和结果 | 是 |

除健康检查外，请求必须携带：

```http
Authorization: Bearer <SERVICE_API_KEY>
```

`X-Request-ID` 可由调用方传入，但只接受 ASCII 字母、数字、连字符和下划线，最长 128 字符；不符合规则时服务会生成新的 UUID，并在响应头返回。

## 五、Job 创建流程

```text
POST /jobs
  ↓
Pydantic schema 校验
  ↓
Bearer token 校验
  ↓
校验 job_type 是否存在于 Prompt YAML
  ↓
校验 model_id 是否在当前启用模型列表
  ↓
校验 prompt.blocks 是否与模板 key / role 完全一致
  ↓
校验 callback.url：默认必须 HTTPS，且不能指向私有网段 IP
  ↓
若 client_request_id 存在，使用 PostgreSQL advisory lock 做 24h 幂等查询
  ↓
若 MAX_ACTIVE_JOBS > 0，使用 advisory lock 串行化 active count 检查
  ↓
创建 ai_jobs，status=queued
  ↓
预生成 celery task_id，写入 ai_jobs.celery_task_id
  ↓
commit
  ↓
dispatch_job_task.apply_async(args=[job_id], task_id=task_id)
  ↓
返回 202 + job_id + status_url
```

这里的关键点是 **先写入 `celery_task_id` 并提交，再投递 Celery**。如果 API 在 commit 后、dispatch 前崩溃，Job 会变成 `queued + celery_task_id 非空`，由 worker 启动恢复扫描重新投递；如果 dispatch 成功但 worker 并发或消息重复，`mark_running_if_queued` 会用 CAS 防止双执行。

## 六、Job 状态机

```text
queued
  ├─ 创建成功后进入
  ├─ 等待 Celery worker 领取
  └─ 可能被 recovery 重新投递

running
  ├─ worker 成功 claim queued Job 后进入
  ├─ 正在读取输入、调用模型、解析输出和写入产物
  └─ stale 后可被 recovery 标记为 failed

succeeded
  ├─ result_payload 有效
  ├─ progress_percent = 100
  └─ 触发 job.succeeded Callback

failed
  ├─ error_payload 有效
  └─ 触发 job.failed Callback
```

`ai_jobs.expires_at` 默认是创建后 24 小时。Worker 内置 recovery loop 会周期清理过期 Job，不依赖 Celery Beat。

## 七、输入与 Prompt

创建 Job 的输入必须来自对象存储引用：

```json
{
  "source": {
    "oss": {
      "oss_key": "input/novel.txt",
      "oss_url": "https://example.com/input/novel.txt",
      "content_hash": "sha256:<64 lowercase hex>",
      "content_type": "text/plain; charset=utf-8"
    }
  }
}
```

约束：

- 只接受 `text/plain; charset=utf-8`。
- `content_hash` 可选；传入时必须匹配 `sha256:<64 lowercase hex>`，执行时会校验实际内容。
- 输入大小受 `OSS_INPUT_MAX_BYTES` 限制，默认约 5 MB。
- 本地存储会防止 `../` 路径穿越。
- `aliyun_oss` 模式会校验请求 bucket / region 必须匹配服务配置。

Prompt 模板来自 `PROMPT_CONFIG_PATH`，默认是：

```text
app/workflows/novel_localization/prompts.yaml
```

当前对外模板只暴露两个可提交 block：

```text
user
work_note
```

`system` prompt 仍可在 YAML 中配置，但由服务端管理，不要求调用方在 `prompt.blocks` 中提交。执行时组装规则是：

```text
1. 如果 YAML 中存在 system prompt，作为 system message 加入。
2. 遍历调用方提交的 prompt.blocks。
3. user block 会追加 YAML 中的 output_contract，再追加待处理文本。
4. work_note 为空时跳过；非空时包装为“已有工作注释 / 上一轮约束”。
```

## 八、支持的 Job 类型

当前 Job 类型来自 Prompt YAML 和 `executor.py` 的解析逻辑。

| Job Type | 输入语义 | 模型输出要求 | 结构化结果 |
|----------|----------|--------------|------------|
| `novel_localization.step1_localize` | 中文原文 | 必须包含 `===本地化正文开始/结束===` 和 `===工作注释开始/结束===` | `localized_text` 大文本、`work_note` 短文本，`apply_mode=replace` |
| `novel_localization.step2_review` | 本地化中文稿 | 必须包含 `【校验结论】通过` 或 `【校验结论】不通过`；不通过时还必须有 `【问题说明】` 和 `【建议工作注释】` | `review_summary`，以及失败时的 `work_note`，`apply_mode=replace`，`signals.passed` |
| `novel_localization.step3_translate` | 本地化中文稿 | 输出非空英文终稿；当前不要求开始/结束标记 | `translated_text` 大文本 |

## 九、异步执行流程

```text
dispatch_job_task(job_id)
  ↓
设置 request_id = job_id
  ↓
加载 Job，规划 execution_plan 和 work items
  ↓
若 Job 已是 succeeded / failed，跳过
  ↓
queued -> running 使用 CAS claim
  ↓
读取对象存储输入文本
  ↓
asyncio.wait_for(run_ai_job(...), MODEL_CALL_TIMEOUT_SECONDS)
  ↓
run_ai_job
  ├─ 组装 messages
  ├─ 调用 LiteLLM acompletion
  ├─ 检查模型拒答
  └─ 按 job_type 解析输出
  ↓
_persist_large_artifacts
  ├─ localized_text -> <oss_prefix>/localized.txt
  └─ translated_text -> <oss_prefix>/translated.txt
  ↓
mark_succeeded + commit
  ↓
deliver_callback
```

如果执行抛出业务异常或未处理异常，任务会进入 `_fail`，写入 `error_payload` 并发送失败 Callback。超时路径会写入 `JOB_TIMEOUT`。

## 十、输出结构

`GET /jobs/{job_id}` 返回统一结构：

```json
{
  "job_id": "uuid",
  "job_type": "novel_localization.step1_localize",
  "status": "succeeded",
  "progress_percent": 100,
  "progress_text": "已完成",
  "result": {
    "artifacts": [],
    "signals": {}
  },
  "error": null,
  "created_at": "2026-06-13T00:00:00Z",
  "started_at": "2026-06-13T00:00:01Z",
  "finished_at": "2026-06-13T00:00:30Z"
}
```

Artifact 有两种交付方式：

- 短文本：直接放在 `content`，例如 `work_note`、`review_summary`。
- 大文本：写入对象存储，响应中返回 `storage=oss_object`、`oss_bucket`、`oss_key`、`oss_region`、`content_hash`、`content_size_bytes`。

失败时：

```json
{
  "error": {
    "code": "MODEL_OUTPUT_INVALID",
    "message": "step1_localize 模型输出缺少本地化正文标记或正文为空",
    "details": {}
  }
}
```

## 十一、Callback

Job 进入终态后会调用 `deliver_callback(job)`。Callback URL 来自创建 Job 时的 `callback.url`。

请求头：

```http
Content-Type: application/json
X-AI-Service-Job-Id: <job_id>
X-AI-Service-Event: job.succeeded | job.failed
X-AI-Service-Timestamp: <unix seconds>
X-AI-Service-Signature: sha256=<hmac>
```

如果 `CALLBACK_SIGNING_SECRET` 为空，服务不会发送 `X-AI-Service-Signature`，并会在启动配置校验时记录 warning。Callback 接收方应按 `job_id + event` 做幂等去重。

Callback 发送策略：

- 单次 HTTP 超时由 `CALLBACK_TIMEOUT_SECONDS` 控制，默认 5 秒。
- 终态后立即尝试投递 1 次。
- 失败后由 Worker recovery loop 按 `CALLBACK_RETRY_DELAY_SECONDS` 补偿重试。
- 总尝试次数由 `CALLBACK_MAX_DELIVERY_ATTEMPTS` 控制。
- 内部领取窗口由 `CALLBACK_TIMEOUT_SECONDS` 加代码内 grace 派生，不作为生产配置项暴露。
- 非 2xx 视为失败并继续重试。
- Callback 最终失败不会改变 Job 终态；调用方应以轮询作为兜底。

## 十二、恢复、超时和并发保护

Worker 启动时会执行 recovery 扫描：

| 场景 | 条件 | 处理 |
|------|------|------|
| orphan queued | `queued + celery_task_id IS NULL + created_at < cutoff` | CAS 写入新 task_id 并重新投递 |
| stuck dispatched | `queued + celery_task_id IS NOT NULL + created_at < 2 * orphan timeout` | CAS 替换 task_id 并重新投递 |
| stale running | `running + started_at < stale cutoff` | CAS 标记 failed，发送失败 Callback |

并发保护点：

- `caller_id + client_request_id` 使用 PostgreSQL transaction advisory lock，避免并发重复创建。
- `MAX_ACTIVE_JOBS` 检查使用 PostgreSQL advisory lock，避免明显超限。
- `queued -> running` 使用 CAS UPDATE，避免同一 Job 被多个 worker 双执行。
- stale recovery 使用行锁和状态检查，避免多个 worker 重复失败同一 Job。
- Celery 配置 `acks_late`、`task_reject_on_worker_lost`、`worker_prefetch_multiplier=1`，降低 worker 异常退出时的消息丢失和过度预取风险。

超时链条由锚点和 buffer 派生，启动时校验 buffer 必须大于 0：

```text
MODEL_CALL_TIMEOUT_SECONDS
  + CELERY_SOFT_TIMEOUT_BUFFER_SECONDS
  = celery_soft_time_limit

celery_soft_time_limit
  + CELERY_HARD_TIMEOUT_BUFFER_SECONDS
  = celery_time_limit

celery_time_limit
  + JOB_STALE_RUNNING_BUFFER_SECONDS
  = job_stale_running_seconds
```

buffer 不合法会启动失败；低于推荐值时会记录 warning。

## 十四、配置和部署形态

本项目维护 3 种部署模式：

- `local`：宿主机运行 API / worker，`docker compose` 只提供 PostgreSQL / Redis。
- `compose-deps`：只启动 PostgreSQL / Redis 依赖服务。
- `compose-full`：API、worker、PostgreSQL、Redis 全部由 `docker compose` 管理。

配置加载优先级：

```text
运行时显式环境变量
> docker-compose.yml environment
> ENV_FILE 指定的 env 文件
> .env
> 应用默认值
```

关键配置：

| 配置 | 说明 |
|------|------|
| `DATABASE_URL` | PostgreSQL async 连接串 |
| `REDIS_URL` | Celery broker / backend |
| `SERVICE_API_KEY` | 业务 API Bearer token |
| `STORAGE_BACKEND` | `local` 或 `aliyun_oss` |
| `OSS_*` | 阿里云 OSS 或输出路径相关配置 |
| `OPENAI_API_KEY` | 启用 OpenAI 模型列表和模型调用 |
| `OPENAI_BASE_URL` | OpenAI 兼容代理地址 |
| `DEFAULT_MODEL_ID` | 默认模型 ID |
| `MODEL_CONFIG_PATH` | 模型 YAML 路径 |
| `PROMPT_CONFIG_PATH` | Prompt YAML 路径 |
| `MAX_ACTIVE_JOBS` | queued + running 软上限 |
| `CALLBACK_SIGNING_SECRET` | Callback HMAC 密钥 |
| `ALLOW_INSECURE_CALLBACKS` | 是否允许本地 HTTP callback |

生产或多节点场景应使用 `STORAGE_BACKEND=aliyun_oss`，避免本地磁盘导致 API / worker 节点之间看不到同一份输入和输出。

## 十五、扩展边界

新增 Job 类型时，需要同时修改：

1. `app/workflows/<name>/prompts.yaml` 或 `PROMPT_CONFIG_PATH` 指向的 YAML：新增 `job_type`、`prompt_blocks` 和 `output_contract`。
2. `app/services/executor.py`：新增模型输出解析和 `JobResult` 组装。
3. `tests/`：补充 schema、解析、artifact 或契约测试。
4. README 或本文：说明输入、输出、错误和调用方职责。

新增模型时，优先修改 `app/core/models.yaml`，并确认 LiteLLM model id、上下文窗口、所需环境变量和调用参数配置。

接入真正分块 workflow 时，不应只设置 `WorkflowHandler.chunking_enabled`。还需要明确：

- `POST /jobs` 如何选择单任务路径或 workflow 路径。
- Celery task 如何覆盖 plan、work item、chunk、merge、scan。
- `AIJobWorkItem` 的失败传播和主 Job 终态规则。
- 大文本 artifact 在 chunk 和 merge 阶段的存储策略。
- recovery 如何识别 work item 级别的 orphan / stale 状态。

## 十六、最小验证入口

修改代码后优先运行：

```bash
./scripts/dev.sh check
```

修改启动、任务、数据库、对象存储或 Job 流程后，还应运行：

```bash
./scripts/dev.sh start
./scripts/dev.sh smoke
./scripts/dev.sh stop
```

修改 Job 内部执行、Celery workflow、分块或 merge 后，优先运行：

```bash
./scripts/dev.sh start
./scripts/dev.sh workflow-smoke
./scripts/dev.sh stop
```

需要真实模型端到端验证时，确认 `.env` 有 `OPENAI_API_KEY` 且 `.data/` 下有 `.txt` 文件，再运行：

```bash
./scripts/dev.sh start
./scripts/dev.sh e2e
./scripts/dev.sh stop
```
