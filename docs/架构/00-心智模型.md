# 小说本地化 AI 服务 - 核心心智模型

## 一句话定义

**无状态 AI 执行网关**：接收本地化任务（输入文本+提示词），通过 LLM 执行转换，返回结构化结果和回调通知。

---

## 核心概念体系

### 1. 服务定位

```
用户侧应用 (BFF/后端)
    ↓ POST /jobs (源文本+任务类型+提示词)
    ↓
小说本地化 AI 服务 (本项目)
    ├─ 验证请求 (job_type, model_id, prompt blocks)
    ├─ 加载输入 (OSS 对象)
    ├─ 组装提示词 (system + user + work_note)
    ├─ 调用 LLM (OpenAI API)
    ├─ 解析输出 (提取artifacts和signals)
    ├─ 保存大文本 (OSS)
    └─ 发送 Callback (异步通知)
    ↓
用户侧应用
    ├─ GET /jobs/{job_id} (轮询查询，兜底)
    └─ 接收 POST callback (主动通知)
```

**关键属性**：
- **无状态**: 不维护业务编排逻辑，每个 Job 独立执行
- **异步**: 立即返回 202，后台执行，Callback 通知完成
- **可幂等**: 支持 client_request_id 防重复
- **自包含**: 输入、配置、回调地址都在请求中

---

## 2. 业务概念层次

### 小说本地化全景流程

```
原文 (中文) 
    ↓
[Step 1: 本地化] → 美国文化改写稿 (中文)
    ↓
[Step 2: 校验] → 质量评估 (通过/建议修改)
    ↓
[Step 3: 翻译] → 英文终稿
    ↓
成品
```

**每个 Step 是独立的 Job**：
- Step 1: 将中文故事改写为美国语境（中文输出）
- Step 2: 检验 Step 1 的质量，给出建议
- Step 3: 翻译为英文

**关键点**：
- 用户侧应用负责 Step 间的编排和决策（如是否重做 Step 1）
- AI 服务只负责单个 Step 的执行，不知道上下文

### 工作注释流向

```
Step1 输出: work_note (apply_mode=replace)
    ↓ 用户确认
Step2 建议: work_note (apply_mode=append, 仅失败时)
    ↓ 用户合并到当前完整注释
Step1 重做: 使用合并后的 work_note 作为输入
```

## 3. 数据流转模型

### 请求输入 (CREATE)

```json
{
  "job_type": "novel_localization.step1_localize",
  "model_id": "gpt-4.1",
  "source": {
    "oss": {
      "oss_key": "s3://bucket/input.txt",
      "oss_url": "https://...",
      "content_hash": "sha256:...",
      "content_type": "text/plain; charset=utf-8"
    }
  },
  "callback": {
    "url": "https://backend.example.com/ai-callbacks",
    "events": ["job.succeeded", "job.failed"]
  },
  "prompt": {
    "blocks": [
      { "key": "system", "role": "system", "content": "" },
      { "key": "user", "role": "user", "content": "完整方法论..." },
      { "key": "work_note", "role": "user", "content": "上一步建议或空" }
    ]
  },
  "client_request_id": "optional-idempotency-key"
}
```

### 响应输出 (RESULT)

```json
{
  "artifacts": [
    {
      "key": "localized_text",
      "type": "text",
      "label": "本地化正文",
      "storage": "oss_object",
      "oss_key": "s3://bucket/output/...",
      "content_hash": "sha256:...",
      "content_size_bytes": 123456
    },
    {
      "key": "work_note",
      "type": "work_note",
      "label": "工作注释",
      "apply_mode": "replace",
      "content": "模型生成的注释..."
    }
  ],
  "signals": {
    "passed": true  // 仅 step2 有
  }
}
```

## 4. Job 生命周期状态机

```
创建 (CREATE)
    ↓
[queued] ── 已排队，等待处理
    ↓ dispatch to celery
[running] ── 正在处理文本，调用 LLM
    ↓
成功分支:
    ↓
[succeeded] ── 完成，包含 result + artifacts
    ↓ send callback
    ↓
终态（24h 后自动删除）

失败分支:
    ↓
[failed] ── 失败，包含 error
    ↓ send callback
    ↓
终态（24h 后自动删除）
```

**关键状态属性**：
- `status`: queued|running|succeeded|failed
- `progress_percent`: 0-100（succeeded 时必须 100）
- `progress_text`: 可读的状态描述
- `result`: 仅 succeeded 时有效
- `error`: 仅 failed 时有效

## 5. 核心逻辑点

### 提示词组装规则

```python
messages = [
  { "role": "system", "content": "" },  # 固定为空
  { "role": "user", "content": user_prompt + output_contract + input_text },
  { "role": "user", "content": work_note_wrapper(work_note) }  # 非空时
]
```

**说明**：
- system block 为空（业务约定）
- user block = 用户提示词 + AI 能力层追加的输出格式契约 + 实际输入文本
- work_note block = 上一步建议或当前确认的工作注释（为空时跳过）

### 输出解析规则

**step1_localize**：
```
查找标记:
  ===本地化正文开始=== ... ===本地化正文结束===
  ===工作注释开始=== ... ===工作注释结束===
验证:
  正文必须是中文，不能是英文
生成:
  localized_text + work_note (apply_mode=replace)
```

**step2_review**：
```
查找标记:
  【校验结论】 通过/不通过
  【问题说明】...
  【建议工作注释】...
验证:
  必须明确给出通过/不通过结论
生成:
  signals.passed + review_summary + work_note(仅失败时，apply_mode=append)
```

**step3_translate**：
```
查找标记:
  ===英文翻译开始=== ... ===英文翻译结束===
验证:
  必须是英文
生成:
  translated_text
```

## 6. Callback 通知机制

### 触发条件

Job 进入 succeeded 或 failed 后，异步发送 POST callback

### 请求格式

```http
POST https://backend.example.com/ai-callbacks
Content-Type: application/json
X-AI-Service-Job-Id: {job_id}
X-AI-Service-Event: job.succeeded | job.failed
X-AI-Service-Timestamp: 2026-06-10T12:00:00Z
X-AI-Service-Signature: sha256={hmac}

{
  "event": "job.succeeded",
  "job_id": "{job_id}",
  "job_type": "novel_localization.step1_localize",
  "status": "succeeded",
  "result": { /* 同 GET /jobs/{job_id} */ },
  "error": null,
  "finished_at": "2026-06-10T12:00:00Z"
}
```

### 重试机制

失败时重试 3 次：
- 延迟: 10s、30s、60s
- 幂等性: 后端应按 job_id + event 去重

## 7. 限制和边界

| 项 | 限制 | 说明 |
|---|------|------|
| 输入大小 | 5 MB | 超过返回 INPUT_TOO_LARGE |
| 编码 | UTF-8 | 必须，否则 INVALID_INPUT |
| 模型调用超时 | 300s (可配) | MODEL_CALL_FAILED |
| Job 排队超时 | 10 分钟 | JOB_TIMEOUT |
| Job 执行超时 | 30 分钟 | JOB_TIMEOUT |
| 数据保留期 | 24 小时 | 之后自动删除 |
| 轮询频率 | 推荐 2s | queued/running 时 |

## 8. 关键设计决策

### 为什么是无状态？

- ✅ 易于水平扩展（无 session 或内存状态）
- ✅ 易于容错恢复（任何实例都能处理任何请求）
- ✅ 易于观察监控（每个 Job 独立，日志清晰）
- ❌ 不支持多 Step 协调（用户侧负责）

### 为什么是异步+Callback？

- ✅ LLM 调用可能耗时（模型推理 30-60s），同步会超时
- ✅ Callback 主动通知，用户侧不需要持续轮询
- ✅ 轮询作为兜底，24h 内容错可查
- ❌ 需要用户侧配置可达的 HTTPS 地址

### 为什么提示词中 system 为空？

- ✅ 所有约束通过 user block 传达，更清晰
- ✅ 减少了"哪些是系统约束、哪些是用户定制"的混淆
- ✅ 用户完全控制提示词内容，无隐藏逻辑
- ❌ user block 会比较长

## 9. 服务边界明确

### 服务负责 ✅

```
✓ 参数验证 (job_type, model_id, prompt 结构)
✓ 输入读取 (OSS 拉取、hash 验证、大小检查)
✓ 提示词组装 (system + user + work_note)
✓ LLM 调用 (OpenAI API，重试，超时控制)
✓ 输出解析 (按 job_type 格式约定)
✓ 结果持久化 (大文本写 OSS，结构化结果写 DB)
✓ Callback 通知 (重试、签名、幂等去重)
```

### 用户侧负责 ❌

```
✗ 业务编排 (Step 1→2→3 的流程控制)
✗ 状态机理 (决定是否重做 Step 1)
✗ 结果存储 (应在 Callback 中保存完整数据)
✗ 模型管理 (选择哪个模型，成本控制)
✗ 提示词优化 (user block 的内容质量)
```

---

## 总结：三个理解维度

1. **技术视角**：无状态 HTTP + Celery 异步执行 + OSS 存储 + HMAC 签名
2. **业务视角**：并行 3-step 流程，每个 step 1 个独立 Job，支持迭代决策
3. **用户视角**：Send 请求 → 等待 Callback → 拿结果 → 决定下一步
