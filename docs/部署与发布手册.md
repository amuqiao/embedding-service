# 部署与发布手册

本文把 FastAPI AI Job Template 已维护的本地开发和 compose 部署路径整理成可复制的操作参考，帮助维护者按当前任务选择正确命令，并理解这些命令会影响哪些服务、配置和数据。

## 文档职责

本文覆盖：

- 本地开发环境启动、停止、状态查看和验证。
- `compose-deps` 与 `compose-full` 两种 compose 运行方式。
- 配置文件、密钥、端口、对象存储和配置覆盖关系。
- 代码、配置、数据库迁移、Dockerfile 和 compose 变更后的发布路径。
- PostgreSQL、Redis、本地对象存储和 compose volume 的数据风险边界。
- 高频部署故障的检查入口。

本文不覆盖：

- 生产部署、远程数据库、K8s、云平台 Secrets 或 CI/CD 发布流水线。
- 用户系统、项目管理、前端页面状态或业务步骤编排。
- Docker、Linux、PostgreSQL、Redis 的通用教程。

## 快速入口

| 当前任务 | 入口 |
| --- | --- |
| 首次准备本地环境 | `./scripts/dev.sh bootstrap` |
| 启动完整本地开发栈 | `./scripts/dev.sh start` |
| 查看本地服务状态 | `./scripts/dev.sh status` |
| 运行最小检查 | `./scripts/verify.sh check` |
| 验证模板 Job workflow | `./scripts/verify.sh workflow-smoke` |
| 查看部署模式 | `./scripts/deploy.sh modes` |
| 校验 Dockerfile 和 compose 配置 | `./scripts/deploy.sh check` |
| 只启动 PostgreSQL / Redis | `./scripts/deploy.sh up compose-deps` |
| 启动 compose 全量服务 | `./scripts/deploy.sh up compose-full` |

## 运行方式

本项目只维护 3 种运行方式。

| 模式 | 启动内容 | 适用场景 | 入口 |
| --- | --- | --- | --- |
| `local` | 宿主机运行 FastAPI API 和 Celery worker，`docker compose` 只提供 PostgreSQL / Redis | 日常本地开发、调试、测试 | `./scripts/dev.sh` |
| `compose-deps` | 只启动 PostgreSQL / Redis | 给宿主机上的应用进程提供依赖 | `./scripts/deploy.sh up compose-deps` |
| `compose-full` | API、worker、PostgreSQL、Redis 全部由 compose 管理，并在应用启动前执行 Alembic 迁移 | 验证容器化运行形态 | `./scripts/deploy.sh up compose-full` |

默认端口：

| 服务 | 宿主机端口 | 容器内端口 |
| --- | --- | --- |
| API | `8100` | `8100` |
| PostgreSQL | `25432` | `5432` |
| Redis | `26379` | `6379` |

健康检查入口：

```bash
curl -fsS http://127.0.0.1:8100/health
curl -fsS http://127.0.0.1:8100/healthz
```

`/healthz` 用于兼容部署平台健康检查；除 `/health` 和 `/healthz` 外，API 请求都需要携带 `Authorization: Bearer <SERVICE_API_KEY>`。本地联调可通过 `DISABLE_HTTP_AUTH_HEADER=true` 跳过 Bearer 校验；可通过 `DISABLE_CALLER_ID_HEADER=true` 忽略 `X-AI-Service-Caller-ID` 并统一使用 `default` caller。配置层只允许在loopback DB/Redis 地址下开启这两个开关；生产环境应保持为 `false`。

## 配置规则

配置加载优先级：

```text
运行时显式环境变量
> docker-compose.yml environment
> ENV_FILE 指定的 env 文件
> .env
> 应用默认值
```

配置文件职责：

| 文件或变量 | 职责 |
| --- | --- |
| `.env.example` | 可提交的配置模板 |
| `.env` | 本地私有配置，不提交 |
| `.env.dev` | 可选的本地开发私有配置，不提交 |
| `ENV_FILE` | 指定 compose 读取的 env 文件，默认 `.env` |
| `docker-compose.yml environment` | 只覆盖容器网络地址、容器内端口和容器内路径 |

必须关注的配置：

| 配置 | 说明 |
| --- | --- |
| `DATABASE_URL` | API、worker 和迁移使用的 PostgreSQL 地址 |
| `REDIS_URL` | Celery broker / backend 使用的 Redis 地址 |
| `SERVICE_API_KEY` | 调用受保护 API 时使用的 Bearer Token |
| `DISABLE_HTTP_AUTH_HEADER` | 本地联调开关；`true` 时跳过 Bearer 校验，仅允许loopback DB/Redis 地址开启 |
| `DISABLE_CALLER_ID_HEADER` | 本地联调开关；`true` 时忽略 `X-AI-Service-Caller-ID` 并使用 `default` caller，仅允许loopback DB/Redis 地址开启 |
| `STORAGE_BACKEND` | `local` 或 `aliyun_oss` |
| `LOCAL_OBJECT_STORAGE_PATH` | `local` 存储后端的对象文件目录 |
| `OPENAI_API_KEY` | 真实模型调用必填 |
| `DEFAULT_MODEL_ID` | 默认模型，开发默认 `gpt-5.5` |
| `MODEL_CONFIG_PATH` | 模型 YAML 路径，默认 `app/core/models.yaml` |
| `MODEL_CALL_TIMEOUT_SECONDS` | 单次模型 API 调用超时；代码默认 `300` 秒，`.env.example` 推荐本地示例值 `600` 秒 |
| `CALLBACK_SIGNING_SECRET` | Callback 签名密钥 |
| `ALLOW_INSECURE_CALLBACKS` | 本地可为 `true`，非本地环境应谨慎打开 |

`docker-compose.yml` 会在容器内覆盖：

```text
DATABASE_URL=postgresql+asyncpg://postgres:postgres@postgres:5432/ai_jobs
REDIS_URL=redis://redis:6379/0
LOCAL_OBJECT_STORAGE_PATH=/app/storage/objects
```

因此 `compose-full` 使用的是容器内 `postgres` / `redis` 地址，不属于 loopback DB/Redis 地址；如果开启 `DISABLE_HTTP_AUTH_HEADER` 或 `DISABLE_CALLER_ID_HEADER`，配置校验会拒绝启动。

业务配置、密钥、模型参数和限制参数应来自 `.env`、`ENV_FILE` 指定文件或运行时显式环境变量，不应写死到 `docker-compose.yml environment`。

## 常用操作

### 本地开发

首次准备：

```bash
./scripts/dev.sh bootstrap
```

启动完整本地服务栈：

```bash
./scripts/dev.sh start
```

`start` 会启动 PostgreSQL / Redis，执行 Alembic 迁移，启动 API 和 worker，并检查 `/health`。

本地 API 默认通过 `uvicorn --reload` 启动，修改 `app/` 下代码会自动重载；设置 `DEV_API_RELOAD=false` 时恢复为调用 `start-api.sh`。reload 默认设置 `WATCHFILES_FORCE_POLLING=true`，避免 macOS 或受限目录中文件监听失败；如需使用系统文件事件，可设为 `false`。worker 不做自动热更新，代码变更后使用 `./scripts/dev.sh restart worker`。

查看状态：

```bash
./scripts/dev.sh status
./scripts/dev.sh status api
./scripts/dev.sh status worker
```

查看日志：

```bash
./scripts/dev.sh logs api
./scripts/dev.sh logs worker
```

重启服务：

```bash
./scripts/dev.sh restart
./scripts/dev.sh restart api
./scripts/dev.sh restart worker
```

停止服务：

```bash
./scripts/dev.sh stop
./scripts/dev.sh stop api
./scripts/dev.sh stop worker
```

验证：

```bash
./scripts/verify.sh check
./scripts/verify.sh workflow-smoke
```

`check` 是模板级最小质量门，覆盖脚本语法、三个稳定入口的 `--help`、Python 语法、env 配置、registry consistency 和 pytest。需要外部资源或真实模型的验证不进入默认 `check`，应通过显式命令单独运行。

脚本入口采用“中控脚本 + 子目录原子脚本 + 公共库”的结构：`scripts/dev.sh` 只管理本地服务生命周期，`scripts/verify.sh` 只承接一次性验证，`scripts/deploy.sh` 只管理 `compose-deps` / `compose-full`。公共 shell 能力位于 `scripts/lib/`，其中 `common.sh` 放输出、错误和基础校验，`runtime.sh` 放本地 API / Python venv 等运行时变量，`compose.sh` 放 docker compose 包装。

业务/供应商扩展示例放在 `examples/business/`，不进入 `scripts/` 稳定命令面。阿里云 OSS 连通性示例可显式运行：

```bash
./.venv/bin/python examples/business/check_aliyun_oss.py --env-file .env.dev
```

模板内置 `workflow-smoke` 使用 `job_test_echo` 验证本地 Job 创建、异步执行和状态轮询流程，不调用真实模型或外部供应商。

真实模型业务 e2e 不属于当前模板核心 `scripts/` 命令面。接入正式业务 `job_type` 后，再恢复对应业务 e2e 脚本或放入 `examples/business/`。

### compose-deps

启动依赖服务：

```bash
./scripts/deploy.sh up compose-deps
```

查看状态：

```bash
./scripts/deploy.sh status compose-deps
```

停止依赖服务：

```bash
./scripts/deploy.sh down compose-deps
```

`compose-deps` 只管理 PostgreSQL / Redis，不启动 API、worker，也不执行 Alembic 迁移。

### compose-full

启动全量服务：

```bash
./scripts/deploy.sh up compose-full
```

指定 env 文件启动：

```bash
ENV_FILE=.env.dev ./scripts/deploy.sh up compose-full
```

查看状态：

```bash
./scripts/deploy.sh status compose-full
```

停止全量服务：

```bash
./scripts/deploy.sh down compose-full
```

`compose-full` 会构建镜像，启动 PostgreSQL / Redis，运行一次性 `migrate` 服务执行 `alembic upgrade head`，再启动 API 和 worker。

## 发布路径

发布前先确认部署入口和配置仍然有效：

```bash
./scripts/deploy.sh check
```

按变更类型选择发布路径：

| 变更类型 | 本地验证 | compose-full 发布 |
| --- | --- | --- |
| API 代码 | `./scripts/dev.sh restart api` 后跑 `./scripts/verify.sh check`，必要时跑 `workflow-smoke` | `./scripts/deploy.sh up compose-full` |
| worker / Job 执行逻辑 | `./scripts/dev.sh restart worker` 后跑 `./scripts/verify.sh workflow-smoke` | `./scripts/deploy.sh up compose-full` |
| 数据库 migration | `./scripts/dev.sh migrate` 后跑 `./scripts/verify.sh check` | `./scripts/deploy.sh up compose-full`，由 `migrate` 服务执行迁移 |
| `.env.example` 或配置读取逻辑 | `./scripts/verify.sh check`，必要时重新 `start` | 使用目标 `ENV_FILE` 执行 `./scripts/deploy.sh up compose-full` |
| `Dockerfile` / `docker-compose.yml` | `./scripts/deploy.sh check` | `./scripts/deploy.sh up compose-full` |
| 对象存储逻辑 | `./scripts/verify.sh check`，必要时运行 `examples/business/check_aliyun_oss.py` | 使用目标 env 启动后跑业务冒烟 |
| 依赖变更 | `./scripts/dev.sh bootstrap` 后跑 `./scripts/verify.sh check` | `./scripts/deploy.sh up compose-full` 重新构建镜像 |

API 和 worker 使用同一份应用代码和同一份镜像。涉及共享代码、配置、模型调用、对象存储、Job 状态流转或数据库 schema 的变更，不应只验证单个进程。

## 数据安全

持久化数据边界：

| 数据 | 默认位置 | 风险说明 |
| --- | --- | --- |
| PostgreSQL 数据 | compose volume `postgres_data` | `stop` 不删除数据；删除 volume 会丢失数据库 |
| Redis 数据 | Redis 容器内数据 | 本项目不把 Redis 当长期持久化存储 |
| 本地对象存储 | `storage/objects/` 或 compose volume `object_storage` | 保存 Job 输出产物；删除目录或 volume 会丢失本地对象 |
| 运行日志 | `logs/` | 本地排障使用，不作为长期审计存储 |
| PID 文件 | `.run/` | 仅用于本地进程管理 |
| 测试输入 | `.data/` | 本地 e2e 输入，不提交 |

安全边界：

- `.env`、`.env.dev`、`.data/`、`storage/objects/`、`logs/` 都不提交。
- `./scripts/dev.sh` 会拒绝明显非本地的 `DATABASE_URL` 和 `REDIS_URL`，避免误操作远程资源。
- `./scripts/dev.sh stop` 和 `./scripts/deploy.sh down ...` 当前只停止服务，不删除 compose volume。
- 删除 `postgres_data`、`object_storage`、`storage/objects/` 或手工清空数据库都属于高风险操作，执行前必须确认是否需要备份。
- Alembic 迁移是日常发布步骤；不可逆 migration、手工改表或数据修复应先单独评估备份和回滚路径。

## 故障排查

### API 端口被占用

现象：`./scripts/dev.sh start` 报 `api port 8100 is already used`。

检查：

```bash
./scripts/dev.sh status api
lsof -nP -iTCP:8100 -sTCP:LISTEN
```

处理：

```bash
./scripts/dev.sh stop api
```

如果端口由其他进程占用，停止该进程或通过 `API_PORT` 改用其他端口。

### PostgreSQL 或 Redis 未就绪

现象：启动卡在依赖健康检查，或 API / worker 连接失败。

检查：

```bash
./scripts/dev.sh status
./scripts/deploy.sh status compose-deps
```

处理：

```bash
./scripts/dev.sh restart
```

如果 compose 配置本身异常，先运行：

```bash
./scripts/deploy.sh check
```

### 配置不生效

现象：容器内仍连接 `postgres` / `redis`，或对象存储路径与 `.env` 不一致。

判断：`compose-full` 中 `DATABASE_URL`、`REDIS_URL`、`LOCAL_OBJECT_STORAGE_PATH` 会被 `docker-compose.yml environment` 覆盖，这是预期行为。

检查：

```bash
ENV_FILE=.env.example docker compose --profile app config
```

处理：业务配置放入 `.env` 或 `ENV_FILE` 指定文件；只有容器网络地址、容器内端口和容器内路径放入 `docker-compose.yml environment`。

### 迁移失败

现象：`./scripts/dev.sh migrate` 或 compose `migrate` 服务失败。

检查：

```bash
./scripts/dev.sh status
./scripts/dev.sh logs api
```

处理：

```bash
./scripts/dev.sh migrate
./scripts/verify.sh check
```

如果失败来自新 migration，先检查 `alembic/versions/` 中的迁移脚本和模型变更是否匹配。不要通过删除数据库或 volume 来绕过迁移问题。

### worker 不处理 Job

现象：Job 长时间停留在排队或执行中。

检查：

```bash
./scripts/dev.sh status worker
./scripts/dev.sh logs worker
./scripts/verify.sh workflow-smoke
```

处理：

```bash
./scripts/dev.sh restart worker
```

如果近期修改了 Job planner、Celery workflow、分块或 merge 逻辑，优先用 `workflow-smoke` 复现。

### 真实模型调用失败

现象：真实模型业务 Job 调用失败，或 Job 返回 `MODEL_CALL_FAILED` / `MODEL_OUTPUT_INVALID`。

检查：

按业务项目提供的 e2e 脚本或 `examples/business/` 下的示例工具复现。

确认 `.env` 中 `OPENAI_API_KEY`、`OPENAI_BASE_URL` 和 `DEFAULT_MODEL_ID` 是否符合本次验证目标。若错误详情包含 `APITimeoutError`，优先调大 `MODEL_CALL_TIMEOUT_SECONDS`，或在对应 `WorkflowHandler` 中调小 `chunk_size`。真实模型调用可能产生费用。

### 阿里云 OSS 连接失败

现象：`STORAGE_BACKEND=aliyun_oss` 后上传、读取或产物 URL 异常。

检查：

```bash
./.venv/bin/python examples/business/check_aliyun_oss.py --env-file .env.dev
```

确认 `OSS_BUCKET`、`OSS_REGION`、`OSS_ACCESS_KEY_ID`、`OSS_ACCESS_KEY_SECRET`、`OSS_PROJECT_ROOT`、`OSS_PUBLIC_ENDPOINT`、`OSS_ENDPOINT` 和 `OSS_ENDPOINT_STYLE`。

## 同步维护规则

修改以下内容时，必须同步检查本文档、`README.md`、`docs/README.md` 和 `.env.example` 是否需要更新：

- `scripts/dev.sh` 或 `scripts/deploy.sh` 的命令、参数、成功标准或副作用。
- `Dockerfile`、`docker-compose.yml`、compose service 名称、profile、端口、volume 或健康检查。
- 配置项、默认值、配置加载优先级、密钥来源或 `.env.example`。
- API 健康检查路径、认证边界或默认端口。
- Alembic 迁移策略、数据库连接方式或数据持久化位置。
- 对象存储后端、本地对象存储目录或 OSS 配置。
- Job 执行方式、Celery worker 命令、队列依赖、workflow smoke 或 e2e 验证方式。

本文只记录长期稳定的部署和发布路径。一次性排查命令、临时环境说明和未验收的生产部署设想，不应写入本文。
