# 测试环境发布流程

本文说明 `chapters-short-lang-detector` 项目发布代码到测试环境的实际流程，重点解释 `dev` 分支、`test` 分支、代码镜像构建和 Kuboard 更新镜像之间的关系。

本文只负责本项目测试环境发布流程；Kuboard 平台的登录、集群选择、名称空间选择、日志查看等通用操作，参考 [`容器发版平台的使用.md`](容器发版平台的使用.md)。

## 一、发布模式

本项目测试环境采用以下发布模式：

```text
dev 分支开发代码
  -> 合入 test 分支
  -> test 分支提交触发 GitLab CI 构建代码镜像
  -> 钉钉群收到代码镜像版本
  -> 在 Kuboard 手动调整初始化容器镜像版本
  -> 验证测试环境服务
```

这里的 `test` 分支不是单纯的代码备份分支，而是测试环境的发版入口。测试环境是否更新，不只取决于代码是否合入 `test`，还取决于是否成功构建镜像，以及是否在 Kuboard 中切换到了新镜像版本。

本项目当前职责边界：

| 角色 | 负责内容 | commit 标记 | Kuboard 对应位置 |
| --- | --- | --- | --- |
| 开发 | 代码镜像 | `[ci build]` | 初始化容器 `test-chapters-short-lang-detector` |
| 运维 | 运行环境镜像 | `[build:os]` | 工作容器 `os-chapters-short-lang-detector` |

开发日常发布只处理代码镜像，不调整工作容器的 `OS-*` 运行环境镜像。

## 二、分支职责

| 分支 | 职责 |
| --- | --- |
| `dev` | 日常开发分支，业务代码和文档主要先在这里变更 |
| `test` | 测试环境发版分支，包含运维维护的 CI 与 Docker 构建文件 |

当前仓库远程分支主要是：

```text
origin/dev
origin/test
```

测试环境发布时，通常是将 `dev` 中已经确认要测试的业务改动合入 `test`，再由 `test` 分支触发镜像构建。

## 三、发版文件说明

`test` 分支中有运维维护的发版文件，发布时需要特别保护：

| 文件 | 用途 | 注意事项 |
| --- | --- | --- |
| `.gitlab-ci.yml` | GitLab CI 构建配置 | 不要用 `dev` 分支版本覆盖 |
| `Dockerfile` | 代码镜像构建入口 | 开发发布 `[ci build]` 时使用，保留 `test` 分支版本 |
| `Dockerfile_OS` | 运行环境镜像构建入口 | 运维发布 `[build:os]` 时使用，开发通常不处理 |

如果从 `dev` 合入 `test` 时出现冲突，业务代码可以按需求合入，但上述发版文件应优先保留 `test` 分支上的版本。除非已经与运维确认，否则不要自行重写这些文件。

## 四、CI 触发规则

`test` 分支上的 `.gitlab-ci.yml` 有提交信息限制。不是所有提交都会构建镜像。

CI 触发需要同时满足：

1. 提交所在分支匹配 CI 规则，测试环境使用 `test` 分支。
2. commit message 中包含 `build`。
3. commit message 中包含具体构建标记。

当前支持的构建标记：

| commit message 标记 | 构建文件 | 镜像仓库路径 |
| --- | --- | --- |
| `[ci build]` | `Dockerfile` | `cms-images/.../test-<project>:<timestamp>` |
| `[build:os]` | `Dockerfile_OS` | `os/<project>:OS-<timestamp>` |

如果只提交普通信息，例如：

```text
merge dev changes
```

则很可能不会触发镜像构建。开发发布代码时应明确带上 `[ci build]`，例如：

```text
[ci build] release dev changes to test
```

`[build:os]` 用于生成运行环境镜像，通常由运维处理。

## 五、推荐发布步骤

### 5.1 准备本地 test 分支

进入用于操作测试分支的工作目录：

```bash
cd /Users/admin/Downloads/Code/chapters-short-lang-detector-test
git fetch origin
```

如果本地已有 `test` 分支：

```bash
git switch test
git pull --ff-only origin test
```

如果本地还没有 `test` 分支：

```bash
git switch -c test origin/test
```

### 5.2 合入 dev 改动

将开发分支中准备发布的内容合入 `test`：

```bash
git merge origin/dev
```

如果出现冲突，按以下原则处理：

| 冲突类型 | 处理原则 |
| --- | --- |
| 业务代码冲突 | 根据本次发布需求合入，例如 `main.py`、`detectors/*` |
| 接口文档冲突 | 根据测试环境实际地址和接口行为更新 |
| CI / Docker 文件冲突 | 优先保留 `test` 分支版本，必要时先咨询运维 |

对于发版文件，通常保留 `test` 分支版本：

```bash
git checkout --ours .gitlab-ci.yml Dockerfile Dockerfile_OS
git add .gitlab-ci.yml Dockerfile Dockerfile_OS
```

确认差异：

```bash
git status
git diff --cached
```

### 5.3 提交并触发构建

确认合并结果后提交。开发发布代码时使用 `[ci build]` 触发 `Dockerfile` 构建：

```bash
git commit -m "[ci build] release dev changes to test"
git push origin test
```

提交后等待钉钉群中的 CI 构建通知。通常 2 到 10 分钟内会收到镜像版本信息。

如果没有收到通知，到 GitLab 项目的 **CI/CD -> Pipelines** 中查看流水线是否触发、是否失败。

## 六、更新 Kuboard 镜像版本

CI 构建成功后，钉钉群会给出代码镜像地址和版本号。测试环境需要将初始化容器切换到新代码镜像。

操作入口参考 [`容器发版平台的使用.md`](容器发版平台的使用.md)：

1. 登录容器发布平台。
2. 选择测试环境对应的 Kubernetes 集群。
3. 进入测试环境名称空间。
4. 找到本项目应用。
5. 点击 **调整镜像版本**。
6. 在 **初始化容器 `test-chapters-short-lang-detector`** 这一行填入 CI 通知中的代码镜像新版本。
7. 不要调整 **工作容器 `os-chapters-short-lang-detector`** 的 `OS-*` 版本；该运行环境镜像由运维维护。
8. 确认更新。

更新后观察应用状态：

| 状态 | 含义 |
| --- | --- |
| 绿色 | 应用启动成功 |
| 橙色 | 应用启动失败，需要查看日志和事件 |

## 七、使用发布脚本

仓库提供了测试环境发布辅助脚本：

```bash
./scripts/release-test.sh
```

脚本默认执行 `prepare`，只准备发布，不会推送：

```bash
./scripts/release-test.sh prepare
```

脚本会把主项目复制到 tmp 发布目录，再在副本中操作 `test` 分支。默认路径是：

```text
../tmp/chapters-short-lang-detector-release-test
```

这样做是为了避免测试发布流程占用日常开发目录。主项目目录继续保留在 `dev` 分支，`test` 分支的合并、检查和推送都发生在 tmp 发布目录中。tmp 发布目录出问题时可以删除重建，不影响主项目目录。

`prepare` 会执行以下动作：

1. 检查主开发工作区是否干净。
2. 检查本地 `dev` 是否已经推送到 `origin/dev`。
3. 复制主项目到 tmp 发布目录。
4. 在 tmp 发布目录切换到 `test` 分支。
5. 同步 `origin/test`。
6. 将 `origin/dev` 合入 `test`，但不提交。
7. 保留 `test` 分支上的 `.gitlab-ci.yml`、`Dockerfile`、`Dockerfile_OS`。
8. 输出当前状态和后续检查命令。

人工检查合并结果：

```bash
./scripts/release-test.sh status
```

如需查看详细 diff，进入 tmp 发布目录检查：

```bash
cd ../tmp/chapters-short-lang-detector-release-test
git status
git diff
git diff --cached
```

确认无误后，回到主项目目录执行 `--push`：

```bash
cd ../chapters-short-lang-detector
./scripts/release-test.sh --push
```

`--push` 会进入 tmp 发布目录，提交当前待发布 merge，并推送到 `origin/test`。默认使用 `[ci build]` 触发代码镜像 CI：

```text
[ci build] release origin/dev to test
```

脚本默认就是开发发代码模式，不需要额外指定 `BUILD_MODE`。如果确实需要生成运行环境镜像，应由运维确认后再显式指定：

```bash
BUILD_MODE=os ./scripts/release-test.sh --push
```

如需自定义提交信息，可以指定 `COMMIT_MESSAGE`，但必须包含对应构建标记：

```bash
COMMIT_MESSAGE="[ci build] release supported languages to test" ./scripts/release-test.sh --push
```

脚本只负责 Git 合并、提交和推送，不负责登录 Kuboard 或切换镜像。推送后仍需要等待钉钉 CI 镜像通知，并在 Kuboard 中手动调整初始化容器镜像版本。

## 八、发布后验证

镜像更新成功后，需要验证测试环境接口。

基础健康检查：

```bash
curl -s http://test-chapters-short-lang-detector.epubgame.com/healthz
```

接口文档：

```text
http://test-chapters-short-lang-detector.epubgame.com/docs
```

业务接口验证示例：

```bash
curl -s -X POST http://test-chapters-short-lang-detector.epubgame.com/language-verifications/batch \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: test-key-001' \
  -d '[
    {"id":"1","text":"Ciao","expected_language":"it-IT"}
  ]'
```

如果本次发布涉及新增接口、支持语种、鉴权规则或配置项，需要针对对应变更补充验证。

## 九、注意事项

### 9.1 不要把合入代码等同于完成发布

`dev` 合入 `test` 只代表测试分支包含了新代码。只有完成以下动作后，测试环境才真正更新：

```text
test 分支触发 CI
CI 构建镜像成功
Kuboard 切换到新镜像
应用启动成功
接口验证通过
```

### 9.2 不要覆盖运维维护的发版文件

`test` 分支中的 `.gitlab-ci.yml`、`Dockerfile`、`Dockerfile_OS` 是发布链路的一部分。随意覆盖可能导致：

- CI 不触发。
- 镜像构建失败。
- 构建出的镜像无法在测试环境运行。
- Kuboard 中切换镜像后应用启动失败。

如果确实需要调整这些文件，应先与运维确认。

### 9.3 提交信息必须包含构建标记

普通提交不一定会触发 CI。开发发布代码时需要使用类似以下格式：

```text
[ci build] release xxx to test
```

`[build:os]` 会生成运行环境镜像，通常由运维处理：

```text
[build:os] release runtime environment to test
```

### 9.4 不要直接在容器里修代码

Kuboard 提供 shell 入口，但容器内修改不具备稳定发布意义。容器重启、重新拉镜像或重新调度后，手工修改可能丢失。

正确方式是通过 Git 分支、CI 镜像和 Kuboard 镜像版本完成发布。

### 9.5 发布失败时先定位阶段

发布失败时先判断卡在哪一层：

| 阶段 | 常见问题 | 排查入口 |
| --- | --- | --- |
| Git 合并 | 冲突处理错误、发版文件被覆盖 | `git status`、`git diff` |
| CI 构建 | commit message 不符合规则、Docker 构建失败 | GitLab CI/CD Pipelines |
| 镜像更新 | Kuboard 填错镜像版本 | Kuboard 应用镜像版本 |
| 应用启动 | 依赖缺失、启动命令错误、配置缺失 | Kuboard 事件和追踪日志 |
| 接口验证 | 服务未更新、鉴权失败、接口逻辑异常 | `/healthz`、Swagger UI、业务接口 |

先确认失败阶段，再处理具体问题，避免在错误的位置反复修改。
